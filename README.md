# teampw：チーム用パスワードマネージャー（E2EE）

学習とポートフォリオのために作っている、チームで1つの Vault を共有するパスワードマネージャー。サーバー（Cloudflare Workers ＋ D1）には暗号文と公開鍵しか置かず、平文と鍵はメンバーの端末の中だけで扱う。

設計の正本は [docs/仕様書.md](docs/仕様書.md)。データの置き場所は [docs/データ一覧.md](docs/データ一覧.md)、進み具合は [docs/実装状況.md](docs/実装状況.md) にある。

| 2人の間の Vault 鍵の受け渡し（A-2、HPKE） | Chrome 拡張機能と自動入力 |

| 最小限の API（暗号文の保存と取得、楽観的ロック、承認待ちの拒否） | 鍵の登録、承認、ローテーションの API |

## 動かし方

Node.js 22.16 以上。依存は実行時が hono、開発時が typescript の2つだけ（どちらもバージョン固定）。

```
npm ci
npm run vectors:fetch   # HPKE の公開テストベクタを取得する（C-15 に必要。理由は tests/vectors/README.md）
npm test
npm run typecheck
```

## 暗号コア

<!-- ここは本人が自分の言葉で書く（docs/暗号コア実装計画.md の8章）。以下は事実の一覧。 -->

| 鎖 | 方式 | 実装 |
|---|---|---|
| マスターパスワード → マスターキー | PBKDF2-HMAC-SHA256、60万回、乱数16バイトのソルト。下限未満は拒否 | src/crypto/kdf.ts |
| マスターキー → ラップ鍵 | HKDF-SHA256（info：teampw/v1/private-key-wrap） | src/crypto/kdf.ts |
| ラップ鍵 → 秘密鍵 | AES-256-GCM、AAD：v1\|member-key\|鍵ID | src/crypto/member-key.ts |
| 秘密鍵 → Vault 鍵 | HPKE Base（DHKEM(P-256, HKDF-SHA256)、HKDF-SHA256、AES-256-GCM）、info：teampw/v1/vault-key-grant\|世代\|鍵ID | src/crypto/hpke-core.ts、hpke.ts、grant.ts |
| Vault 鍵 → アイテム | AES-256-GCM、512B〜64KB のパディング、AAD：v1\|item\|アイテムID\|世代 | src/crypto/item.ts |
| 公開鍵の固定 | フィンガープリント（6組30桁）を Discord 以外の経路で照合して固定し、グラントを作るたびに65バイトで比べる | src/crypto/public-key.ts、grant.ts |

暗号処理は WebCrypto だけで行う。HPKE が必要とする HKDF の Extract と Expand は、WebCrypto の HMAC-SHA256 で RFC 5869 どおりに組み、RFC 5869 のテストベクタで確かめた。楕円曲線の点の計算は自前で書いていない。

**HPKE の適合**：CFRG の公開テストベクタ（Base モード、KEM 0x0010・KDF 0x0001・AEAD 0x0002、257件の暗号文）と一致した（C-15）。そのため、Vault 鍵の受け渡しは RFC 9180 の Base モードに準拠していると書ける。付録 A.3 の組（AEAD 0x0001）とも一致する。

## 脅威モデル（要約）

詳しくは仕様書の「脅威モデル」。最優先は、D1 や Cloudflare アカウントが漏れても、アイテムの中身を読ませないこと。

### 守れるもの

| 攻撃 | 守り方 | 確かめるテスト |
|---|---|---|
| D1 を丸ごと盗まれる | 置いてあるのは暗号文、公開鍵、ソルトと KDF 設定だけ。復号にはマスターパスワードが要る | C-13（API 経由。D1 に平文がない） |
| 暗号文の改ざん | AES-GCM の認証タグ | C-03 |
| 暗号文を別のアイテムの場所へ移す、秘密鍵の行を入れ替える | AAD にアイテムID・世代、鍵IDを入れる | C-04、C-05、ロック解除のテスト |
| サーバーが公開鍵を攻撃者のものに差し替える | 管理者の端末に照合済みの公開鍵を固定し、グラントを作る前に比べる | P-01 |
| サーバーが KDF の反復回数を弱くする | クライアントが下限（60万回）を持つ | C-14 |
| 曲線上にない点を公開鍵として渡す | 非圧縮の点だけを受け付け、WebCrypto で検査する | C-12 |
| 同時編集で他人の変更を上書きする | リビジョンによる楽観的ロック | S-01 |
| 承認されていないメンバーが API を使う | D1 で承認済みでなければ 403 | Z-01 |

### 守れないもの（範囲外として受け入れたもの）

| 起こりうること | 受け入れた理由 |
|---|---|
| 悪意あるサーバーが、新しく参加した人に偽の Vault 鍵を渡す | 管理者署名を入れていない（Base モードでは受け手が送り手を確かめられない）。管理者1人でメンバー追加を想定しない |
| サーバーが古い版のアイテムを返す（ロールバック）、一部を返さない | E2EE だけでは防げない。MVP では検知だけ |
| マルウェアに感染した PC、拡張機能の中で悪意あるコードが動く | 端末の安全はこのシステムの外。取り出し不可の鍵でも「使われる」ことは防げない |
| 悪意あるメンバー | 共通の Vault なので、全員が全件を見られる |
| マスターパスワードを忘れる | 復元の手段はない。他のメンバーが Vault 鍵を包み直せば、データへのアクセスは回復できる |

### 範囲外とした判断

エクスポート、ページ内の入力候補 UI、iframe への入力、管理者署名、ロールバック防止などは MVP で作らない。理由は仕様書の「MVPの範囲外」と「脅威モデル」の範囲外の表にある。

## テスト結果

`npm test`：94件すべて成功（2026-10-15）。テスト名にテスト ID を入れている。提出版で結果を示す7つは次のとおり。

| ID | 内容 | 結果 |
|---|---|---|
| C-03 | 暗号文、ノンス、認証タグを1ビット改ざんすると復号に失敗する（アイテムは全バイトを試す） | 成功 |
| C-04 | 別のアイテムIDの場所に移すと AAD の検証に失敗する | 成功 |
| C-13 | 2人の間でグラントを作り、受け取った側が復号できる（暗号コアだけと、API 経由の2通り） | 成功 |
| C-15 | HPKE の公開テストベクタと一致する | 成功 |
| P-01 | 承認済み公開鍵の差し替えを検知し、グラントを作らない | 成功 |
| S-01 | 古いリビジョンでの更新・削除が 409 になる | 成功 |
| Z-01 | 承認待ちのメンバーの API アクセスが 403 になる | 成功 |

ほかに C-01、C-02、C-05〜C-10、C-12、C-14、C-16 と、関連する I、Z、A、W の一部も通る。一覧は docs/実装状況.md にある。

## 確かめていないこと、制約

- **API のテストは SQLite で行い、実際の D1 では未確認**。テストでは node:sqlite を D1 と同じ形で包んでいる。特に、バッチの中の `changes()` の動きは、実際の D1 では確かめていない。
- HPKE のテストベクタは、再配布してよいかを確認できなかったので、リポジトリには置いていない。`npm run vectors:fetch` で、コミットとハッシュを固定して取得する。
- Discord ログインを入れていないので、トークンを発行する入口はない。テストは、セッションの行を D1 に入れて本番と同じ認証を通す。
- JavaScript では、平文の鍵やパスワードを使い終わったあとの0での上書きは努力目標にとどまる（文字列やコピーは消せない）。
- マスターパスワードの Unicode 正規化は、判断待ち（docs/判断待ち.md）。
