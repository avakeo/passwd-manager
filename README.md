# teampw：チーム用パスワードマネージャー（E2EE）の暗号コアと最小 API

学習とポートフォリオのために作っている、チームで1つの Vault を共有するパスワードマネージャー。この提出版（2026年10月16日）は、その**暗号コア**と、暗号文を保存・取得する**最小限の API** を実装したもの。

エンドツーエンド暗号化（E2EE）で作っている。暗号化と復号はメンバーの端末の中だけで行い、サーバー（Cloudflare Workers ＋ D1）には暗号文と公開鍵しか渡さない。サーバーが乗っ取られても、アイテムの中身は読めない。

提出の後（2026-10-17）に、レビューで見つかった偽の Vault 鍵の配布（攻撃者レビュー #1）を防ぐため、**管理者署名と双方向の照合**を足した（[docs/設計案_グラントの送り手認証.md](docs/設計案_グラントの送り手認証.md)、[docs/review/phase-0.md](docs/review/phase-0.md)）。

設計の正本は [docs/仕様書.md](docs/仕様書.md)。データの置き場所は [docs/データ一覧.md](docs/データ一覧.md)、進み具合は [docs/実装状況.md](docs/実装状況.md) にある。

## 鍵の鎖

マスターパスワードだけを覚えていれば、アイテムまで順にたどって復号できる。鎖の途中の鍵は、すべて暗号文か、その場で作り直す値として扱う。

```
マスターパスワード（本人の頭の中。どこにも保存しない）
  │ ① PBKDF2-HMAC-SHA256（60万回、乱数16バイトのソルト）。入力は NFC で正規化する
マスターキー（保存しない）
  │ ② HKDF-SHA256（用途ラベル teampw/v1/private-key-wrap）
ラップ鍵（保存しない。取り出し不可）
  │ ③ AES-256-GCM（AAD：v1|member-key|鍵ID|公開鍵の SHA-256）
秘密鍵（P-256。D1 には暗号文で保存）
  │ ④ HPKE Base（ECDH ＋ HKDF ＋ AES-256-GCM。info：teampw/v1/vault-key-grant|世代|鍵ID）
  │   開く前に、管理者の署名（ECDSA P-256）を、照合して固定した管理者の署名用公開鍵で確かめる
Vault 鍵（チーム共通。メンバーごとに「グラント」として D1 に保存）
  │ ⑤ AES-256-GCM（AAD：v2|item|アイテムID|世代|リビジョン。512B〜64KB にパディング）
アイテム（D1 には暗号文で保存）
```

| 段 | なぜこうしたか | 実装 |
|---|---|---|
| ① | パスワードは人が覚えられる程度に弱いので、わざと遅い KDF で総当たりの1回あたりの手間を増やす。反復回数はサーバーが返すので、クライアントが下限（60万回）を持って弱い値を拒否する | src/crypto/kdf.ts |
| ② | マスターキーをそのまま使わず、用途ごとのラベルで鍵を分ける（ドメイン分離）。将来、別の用途の鍵を足しても混ざらない | src/crypto/kdf.ts |
| ③ | 秘密鍵はパスワードから作らず、乱数で生成する。パスワードを変えても包み直すだけで済み、鍵の強さがパスワードに左右されない。AAD に鍵ID を入れて、別の行の暗号文との入れ替えを防ぐ。公開鍵の SHA-256 も入れて、公開鍵だけを差し替えられた行では開けないようにする | src/crypto/member-key.ts |
| ④ | 公開鍵暗号で Vault 鍵を配るので、秘密を経路に流さずに済む。組み立て方は RFC 9180（HPKE）に従う。管理者は、照合済みの公開鍵を端末に固定し、包む前に毎回比べる。HPKE の Base モードだけでは受け手が「誰が包んだか」を確かめられないので、管理者がグラントに署名し、メンバーは照合して固定した管理者の署名用公開鍵で確かめてから開く。世代も署名の対象に入れ、端末は最後に見た世代より古いグラントを拒否する | src/crypto/hpke-core.ts、hpke.ts、grant.ts、public-key.ts、signer.ts |
| ⑤ | アイテムは JSON を1つの暗号文にし、長さをそろえて中身の量を隠す。ノンスは毎回乱数。AAD にアイテムIDと世代を入れて、別の場所への移し替えを防ぐ | src/crypto/item.ts |

暗号処理はすべて WebCrypto で行い、楕円曲線の点の計算などは自前で書いていない。ロック解除後の秘密鍵と Vault 鍵は、取り出し不可（non-extractable）の鍵オブジェクトとして持つ。

## 脅威モデルの要約

詳しくは [docs/仕様書.md の「脅威モデル」](docs/仕様書.md#脅威モデル) と [「MVPの範囲外」](docs/仕様書.md#mvpの範囲外)。最優先は、D1 や Cloudflare アカウントが漏れても、アイテムの中身を読ませないこと。

### 守れるもの

| 攻撃 | 守り方 | テスト |
|---|---|---|
| D1 を丸ごと盗まれる | D1 にあるのは暗号文、公開鍵、ソルト、KDF の設定だけ。復号にはマスターパスワードが要る | C-13（API 経由。D1 に平文が残らないことも確かめる） |
| 暗号文の改ざん | AES-GCM の認証タグ | C-03 |
| 暗号文を別のアイテムの場所へ移す、秘密鍵の行を入れ替える | AAD にアイテムID・鍵の世代、鍵ID を入れる | C-04、C-05 |
| サーバーが公開鍵を攻撃者のものに差し替える（中間者攻撃） | 承認のとき、Discord 以外の経路でフィンガープリントを照合して公開鍵を固定し、グラントを作る前に毎回比べる | P-01 |
| サーバーが宛先の公開鍵だけから偽のグラントを作り、行を差し替える（偽の Vault 鍵の配布） | 管理者がグラントに署名し、受け手は固定した管理者の署名用公開鍵で確かめてから開く。管理者自身宛てのグラントも確かめる | C-17、C-18、C-19、C-23 |
| サーバーが古い世代のグラントを返し、古い Vault 鍵を使わせる | 世代を署名の対象に入れ、端末は最後に見た世代より古いグラントを拒否する | C-20 |
| サーバーが管理者の署名用公開鍵や、自分の公開鍵を差し替える | 双方向の照合で固定した値と比べる。秘密鍵の AAD に公開鍵の SHA-256 を入れ、差し替えた行は開けない | P-04、P-05、C-21、C-03 |
| サーバーが KDF の反復回数を弱くする | クライアントが下限を持ち、重い計算の前に拒否する | C-14 |
| 曲線上にない点を公開鍵として渡す | 非圧縮の点だけを受け付け、WebCrypto で検査する | C-12 |
| 同時編集で他人の変更を黙って上書きする | リビジョンによる楽観的ロック | S-01 |
| 承認されていないメンバーが API を使う | D1 で承認済みでなければ 403 | Z-01 |

### 守れないもの

| 起こりうること | 理由 |
|---|---|
| サーバーが新しい世代のグラントを隠し、古い世代のまま使わせる | 端末は最後に見た世代より古いものは拒否するが、まだ見ていない世代を隠されたことには気づけない。端末を初期化した直後の1回も検知できない |
| メンバーが照合を省く | 管理者の署名用公開鍵を見比べずに「一致」を押すと、サーバーが差し出した偽の鍵を固定してしまう。照合が済むまで開かない形にはしたが、見比べたかどうかはコードで担保できない |
| 管理者の端末の乗っ取り | 署名鍵を使われると、偽のグラントにも本物の署名が付く |
| サーバーが古い版のアイテムを返す（ロールバック）、一部を返さない | E2EE だけでは防げない。古い暗号文も正しく暗号化されているため |
| マルウェアに感染した PC | 復号した後のデータやマスターパスワードを盗まれる。取り出し不可の鍵でも、使われることは防げない |
| 悪意あるメンバー | 共通の Vault なので、全員が全件を見られる |
| マスターパスワードを忘れる | 復元の手段はない。他のメンバーが Vault 鍵を包み直せば、データへのアクセスは回復できる |

### 範囲外とした判断

| 判断 | 理由 |
|---|---|
| アイテムのロールバックは検知だけ | 完全な対策（署名付きの変更履歴など）は大きい。端末が最後に見た Vault リビジョンより古ければ警告する。Vault 鍵の世代の巻き戻しは、管理者署名と端末の記録で拒否する |
| エクスポートを作らない | 平文がシステムの外に出る経路を作らない |
| ページ内の入力候補 UI、iframe への入力を作らない | クリックジャッキングなどの攻撃面を作らない |

## 正直に書いておく制約

- **API のテストは SQLite で行い、実際の D1 では確かめていない**。テストでは、Node の node:sqlite を D1 と同じ形で包んでいる。特に、書き込みのバッチの中で使う `changes()`（直前の文が変えた行数）が D1 でも同じに動くかは未確認。
- **手順5（HPKE とグラント）は、テストを本体の後に書いた**。ほかの手順は、テストを先に書いてから実装した。履歴は書き換えず、記録として残した。その代わりに、手順5の実装を5通りにわざと壊し、C-13 と C-15 が落ちることを確かめた。両側を同じように壊した場合、C-13 は落ちず C-15 が捕まえる、といった結果を [docs/review/step-5.md](docs/review/step-5.md) に書いた。
- **HPKE のテストベクタのライセンス表記は確認できなかった**。CFRG の test-vectors.json から、C-15 に必要な1件だけを引用した。出典のリポジトリにはライセンスファイルがない。IETF 文書由来のコード部品の扱いに準じると解釈して引用した。権利者から求めがあれば削除する（[tests/vectors/README.md](tests/vectors/README.md)）。Wycheproof のベクタは Apache-2.0。
- **RFC 9180 準拠と書ける範囲**：仕様書では「本番と同じ組の公開テストベクタで一致を確かめた場合だけ準拠と書く」と決めていた。Base モード、DHKEM(P-256, HKDF-SHA256)・HKDF-SHA256・AES-256-GCM の組で、鍵スケジュールの途中の値と257件の暗号文が一致したので、**この組の Base モードの暗号化と復号については、RFC 9180 準拠**と書ける。PSK、Auth、Exporter は実装していない。また、本番では1つの文脈で1回だけ暗号化する。
- **マスターパスワードの正規化**は、RFC 8265 の OpaqueString に合わせて NFC で行い、前後の空白は削らない。ただし、OpaqueString のほかの規則は実装していない。ASCII 以外の空白（全角スペースなど）を U+0020 に置き換える規則と、使えない文字の拒否が該当する。
- JavaScript では、使い終わった鍵やパスワードを0で上書きするのは努力目標にとどまる（文字列やエンジン内部のコピーは消せない）。
- Discord ログインを入れていないので、トークンを発行する入口はない。テストでは、セッションの行を D1 に直接入れて、本番と同じ認証を通している。

## 開発の進め方

| 役 | 担当 | やること |
|---|---|---|
| 作る | Claude Code | 実装とテスト。採用された指摘を受けて直す |
| 仕様の番人 | Codex | 仕様書の決定事項とテスト ID に合っているかを、1項目ずつ確かめる。テストを流し直す |
| 攻撃者 | DeepSeek | 乗っ取られたサーバーの立場で、「動くけど危ない」所と、それを再現する失敗テストの案を出す |
| 判定 | 本人 | 指摘を採用するかを決める。意見が割れたら仕様書を正とする |

作った会社と別の会社のモデルにレビューさせ、観点も分けている。同じ癖を持つモデルは、同じ所を見落としやすいため。レビュー役はコードを直さず、指摘を文章で返す。

手順ごとのレビュー資料は [docs/review/](docs/review/) の step-1.md〜step-7.md にある。それぞれに、変更したファイル、対応する仕様の節、テスト ID、観点表で見てほしい所を書いている。進め方の詳細は [docs/暗号コア実装計画.md](docs/暗号コア実装計画.md)。Codex と DeepSeek のレビューは、提出の時点ではまだ行っていない。
