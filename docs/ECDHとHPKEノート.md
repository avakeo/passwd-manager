# ECDH と HPKE ノート

A-2（Vault 鍵の受け渡し）で使う ECDH と HPKE の仕組みを、小さな数字で整理したメモ。数値はすべて実際に計算して確かめたもの。楕円曲線そのものの説明は「楕円曲線暗号ノート」を参照。

---

## 1. ECDH とは

**2人がそれぞれ鍵ペアを持っていれば、何も秘密を送らずに、2人だけが計算できる同じ値（共有秘密）を作れる仕組み。**

- 正式名：Elliptic Curve Diffie-Hellman（楕円曲線ディフィー・ヘルマン）
- 暗号化ではなく、**鍵を共有する方法**
- この設計では A-2 で、Vault 鍵を包む鍵の材料を作るのに使う

---

## 2. 理解に必要なのは2つの性質だけ

| 性質 | 内容 |
|---|---|
| 一方向性 | 秘密の数 k から k × G を作るのは簡単。k × G から k を戻すのは計算上不可能 |
| 順番を入れ替えても同じ | a × (b × G) と b × (a × G) は同じ点になる |

P-256 の細かい計算（点の足し算の式）は、ECDH を理解するうえでは「戻せない掛け算をしてくれる箱」として扱えば十分。

---

## 3. 3段階で理解する

### 段階1：普通の掛け算（仕組みは同じだが、安全ではない）

公開の数 g = 7。

| | 秘密の数 | 公開する数（秘密 × 7） |
|---|---|---|
| 管理者 | 3 | 21 |
| C さん | 5 | 35 |

- 管理者：自分の秘密 3 × C さんの公開値 35 ＝ **105**
- C さん：自分の秘密 5 × 管理者の公開値 21 ＝ **105**

どちらも中身は 3 × 5 × 7 なので同じになる。**相手の公開値に自分の秘密を掛けると、2人とも同じ答えにたどり着く。** これが骨組みのすべて。

安全でない理由：盗み見た人が 21 ÷ 7 = 3 と割り算すれば、秘密が分かる。

### 段階2：元祖の Diffie-Hellman（1976年）

「掛け算」を「余りの世界のべき乗」に置き換える。p = 23、g = 5 を公開。

| | 秘密の数 | 公開する数 |
|---|---|---|
| 管理者 | 4 | 5⁴ を23で割った余り ＝ 4 |
| C さん | 3 | 5³ を23で割った余り ＝ 10 |

- 管理者：10⁴ を23で割った余り ＝ **18**
- C さん：4³ を23で割った余り ＝ **18**

### 段階3：ECDH

「掛け算」を「楕円曲線の点の掛け算」に置き換える。おもちゃの曲線（y² = x³ + x + 5、p = 100003、G = (2, 86328)）。

| | 秘密の数 | 公開する点 |
|---|---|---|
| 管理者 | 31415 | 31415 × G ＝ (24436, 76404) |
| C さん | 27182 | 27182 × G ＝ (48552, 71481) |

- 管理者：31415 × C さんの点 ＝ **(642, 44637)**
- C さん：27182 × 管理者の点 ＝ **(642, 44637)**

### 3つを並べると構造は同じ

| | 公開の土台 | 戻せない操作 | 共有される値 |
|---|---|---|---|
| 普通の掛け算（安全でない） | 7 | 掛け算（実際は割り算で戻せる） | 105 |
| Diffie-Hellman | 5 と 23 | 余りの世界のべき乗 | 18 |
| ECDH | G と曲線 | 点の掛け算 | (642, 44637) |

**P-256 は「戻せない操作」をどの曲線で行うかを決めているだけ。** ECDH の仕組みは土台が変わっても同じ。

## 4. 盗み見た人が共有の点を計算できない理由

### 攻撃者が持っているもの

G、管理者の公開鍵 (24436, 76404)、C さんの公開鍵 (48552, 71481)。

### 攻撃者が試せる手と、その結果

| 攻撃者の手 | 結果 |
|---|---|
| 公開鍵から秘密鍵（31415 か 27182）を取り出す | p で割った余りの世界では点がでたらめに跳ぶので、逆算の近道がない。総当たりしかなく、P-256 では約 2¹²⁸ 回の計算が必要 |
| 2つの公開鍵を直接組み合わせる | できるのは足し算だけ。足すと (31415 ＋ 27182) × G ＝ (73184, 56938) になり、共有の点とは別物。点同士の掛け算は存在しない |

Diffie-Hellman でも同じで、公開値を掛けて 4 × 10 を23で割った余りを計算すると 17 になり、正解の 18 には届かない。

### 説明の決まり文句

> p で割った余りの世界では、点を足すたびに結果がでたらめな場所に跳ぶため、pk（sk × G）から sk を逆算する近道がない。総当たりしかなく、P-256 では約 2¹²⁸ 回の計算が必要で現実的に不可能。共有の点を作るにはどちらかの sk が必要で、公開鍵同士を足しても共有の点にはならないため、公開鍵しか見えない攻撃者には共有の点が計算できない。

---

## 5. 「近道がない」の正確な意味

1つずつ足すより賢い総当たり（ポラードのロー法など）があり、必要な回数は「点の数の平方根」くらいまで減らせる。

| 曲線 | 点の数 | 1つずつ足す場合 | 一番うまい方法 |
|---|---|---|---|
| おもちゃ（p = 100003） | 99,707 | 最大 約10万回（実測では 31,415回目で発見、0.04秒） | 約 316回 |
| P-256 | 約 2²⁵⁶ | 約 2²⁵⁶ 回 | 約 2¹²⁸ 回 |

曲線の性質を利用した近道は見つかっていない。P-256 が「128ビットの安全性」と呼ばれるのはこのため。

---

## 6. 情報理論的安全性と計算量的安全性

| 種類 | 意味 | 例 |
|---|---|---|
| 情報理論的安全性 | 答えの候補が多すぎて、計算力が無限にあっても決められない | ワンタイムパッド |
| 計算量的安全性 | 情報としては答えが決まっているが、現実的な時間では計算できない | ECDH、AES、RSA など、ほぼすべての実用暗号 |

ECDH は計算量的安全性。公開鍵に対応する秘密鍵は1つに決まっていて、情報はすべて見えている。おもちゃの曲線が 0.04秒で破れたのはそのため。

**安全性は「答えが隠れていること」ではなく、「答えを計算で取り出すのに、宇宙の年齢でも足りないこと」に支えられている。** P-256 で数を大きくしている理由はここにある。

## 7. A-2 での使われ方

### ラップ鍵と包み用の鍵は別物

| 鍵 | 作り方 | 何を包むか | 使う処理 |
|---|---|---|---|
| ラップ鍵 | マスターパスワードから PBKDF2 → HKDF | 自分の秘密鍵 | A-1、A-3 |
| 包み用の鍵（HPKE の中の鍵） | ECDH の共有秘密から HKDF | Vault 鍵 | A-2 |

どちらも「鍵を AES-GCM で包む鍵」だが、材料が違う。ラップ鍵はパスワードから、包み用の鍵は ECDH の共有秘密から作る。

### 管理者が C さん宛てに包む（A-2）

1. C さんの公開鍵が、固定した値と一致するか確認する
2. 使い捨ての鍵ペアを作る（例：秘密鍵 31415、公開鍵 (24436, 76404)）
3. ECDH：使い捨ての秘密鍵 × C さんの公開鍵 → 共有秘密 (642, 44637)
4. HKDF：共有秘密に「世代」と「宛先の鍵 ID」を混ぜて、包み用の鍵を作る
5. AES-GCM：包み用の鍵で Vault 鍵を暗号化する
6. 使い捨ての公開鍵と暗号文を、グラントとして D1 に保存する。使い捨ての秘密鍵は捨てる

### C さんが開く（A-3 の一部）

1. グラントから使い捨ての公開鍵を取り出す
2. ECDH：自分の秘密鍵 × 使い捨ての公開鍵 → 同じ共有秘密 (642, 44637)
3. 同じ HKDF で、同じ包み用の鍵を作る
4. AES-GCM で復号 → Vault 鍵

管理者が捨てた使い捨ての秘密鍵がなくても、C さんは自分の秘密鍵だけで同じ共有秘密にたどり着ける。

### 使い捨ての鍵ペアを使う理由と、その裏返し

- C さんは使い捨ての公開鍵を知るだけで開ける。管理者の長期的な鍵は関わらない
- 包むたびに共有秘密が変わるので、同じ C さん宛てでも鍵が使い回されない
- **裏返し**：使い捨ての鍵は誰のものでもないので、C さんには「誰が包んだか」が分からない。これが、提出版で範囲外にしていた「偽 Vault 鍵の配布」の正体（2026-10-17 に管理者署名で対策した）

## 8. HPKE とは

**「ECDH ＋ HKDF ＋ AES-GCM を、どう組み合わせれば安全な公開鍵暗号になるか」を細部まで決めた規格（RFC 9180）。** 正式名は Hybrid Public Key Encryption。ECDH は HPKE の中の部品の1つ。

### 部品

| HPKE の部品 | 役割 | この設計での選択 |
|---|---|---|
| KEM（鍵カプセル化） | 共有秘密を作る | DHKEM(P-256, HKDF-SHA256)。中身が ECDH |
| KDF（鍵導出） | 共有秘密から包み用の鍵とノンスを作る | HKDF-SHA256 |
| AEAD（認証付き暗号） | 実際に暗号化する | AES-256-GCM |

### 部品だけでは足りない理由

安全な部品も、組み合わせ方を間違えると安全でなくなる。HPKE は次のような細部を決めている。

- **共有秘密をそのまま AES の鍵にしない**：ECDH の結果は曲線上の点の座標で、偏りのない乱数ではない。必ず KDF に通す
- **鍵の導出に両方の公開鍵を混ぜる**：包み用の鍵を「この組み合わせ専用」に結び付ける
- **用途ラベルを混ぜる**：同じ共有秘密から作る別用途の鍵が混ざらないようにする（ドメイン分離）
- **ノンスの作り方、データの並べ方（エンコード）**

### 保証されるもの

- HPKE に準拠していれば、**組み合わせ方の正しさ**は規格の安全性の分析を借りられる
- 部品そのものの強さ（楕円曲線の離散対数問題の難しさ）は P-256 が担う
- 準拠しているかは、公開テストベクタとの一致で確かめる（テスト C-15）。確認できるまでは「HPKE を参考にした独自方式」と表記する

### モード

| モード | 送り手の確認 | この設計 |
|---|---|---|
| Base | なし（使い捨ての鍵だけ） | **これを使う** |
| PSK | 事前共有の秘密で確認 | 使わない |
| Auth | 送り手の長期的な鍵で確認 | 使わない |
| AuthPSK | 両方 | 使わない |

Base モードなので、受け手は送り手を確認できない。「偽 Vault 鍵の配布」を防ぐために、Auth モードに切り替える案と比べたうえで、Base モードのまま管理者署名（ECDSA P-256）を別に足した。比べた理由は docs/設計案_グラントの送り手認証.md の8章。

## 9. A-2 に出てくる4種類の鍵

ECDH に入る鍵は2本で、使い捨てなのは管理者側の1本だけ。ECDH で使う鍵そのものが Vault 鍵を包むわけではない。

| 鍵 | 誰のものか | 寿命 | 役割 |
|---|---|---|---|
| 使い捨ての秘密鍵（31415） | 管理者が包むたびに作る | 包んだらすぐ捨てる | ECDH の材料（管理者側） |
| C さんの公開鍵 (48552, 71481) | C さんの長期的な鍵 | ずっと使う | ECDH の材料（宛先） |
| 共有秘密 (642, 44637) | 2人だけが計算できる値 | 一時的 | 包み用の鍵の材料 |
| 包み用の鍵 | 共有秘密から HKDF で作る | 一時的 | **これが Vault 鍵を AES-GCM で包む** |

**使い捨ての秘密鍵 ＋ C さんの公開鍵 → ECDH → 共有秘密 → HKDF → 包み用の鍵 → Vault 鍵を包む**

- ECDH は「包み用の鍵を、C さんと2人だけで共有するための手段」
- C さん側では、C さんの長期的な秘密鍵と、グラントに入っている使い捨ての公開鍵で同じ共有秘密を作る

## 10. 鍵をラップする目的

### この設計でラップしている3か所

| 包まれる鍵 | 包む鍵 | 目的 |
|---|---|---|
| 秘密鍵 | ラップ鍵（パスワード由来） | 秘密鍵を D1 に安全に置く |
| Vault 鍵 | 包み用の鍵（HPKE） | Vault 鍵をメンバーごとに配る |
| Vault 鍵 | パスコード鍵 | クイックロック解除のため端末に一時保存する |

### 目的1：鍵を、信用できない場所に置けるようにする

鍵は乱数なので覚えられず、どこかに保存する必要がある。包んでしまえば、包まれた鍵はただの暗号文なので、D1 のような信用していない場所に置ける。

### 目的2：外側の鍵を変えても、中身をやり直さずに済む

マスターパスワードを変える場面で比べると、次のようになる。

| | ラップしない場合 | ラップする場合 |
|---|---|---|
| 構造 | パスワード由来の鍵で全アイテムを直接暗号化 | パスワード由来の鍵は秘密鍵だけを包む |
| パスワード変更でやること | 全アイテムを復号して再暗号化。他のメンバーにも影響 | 秘密鍵（138バイト）を包み直すだけ |

外側の鍵（パスワード）と内側の鍵（データを守る鍵）を切り離しておくと、外側を変えたときの手間が、包まれた鍵1本分で済む。

### 目的3：1本の鍵を、何人にでも配れる

アイテムは Vault 鍵で1回だけ暗号化し、その Vault 鍵をメンバーの数だけ別々に包む。

- 5人なら、グラントが5つあるだけ。アイテムは1回の暗号化で済む
- 新しいメンバーが来たら、グラントを1つ足すだけ。アイテムには触らない

### 目的4：弱い鍵と強い鍵の役割を分ける

- データを守るのは、完全な乱数の強い鍵（Vault 鍵）
- 人が覚えるパスワードのような弱い材料は、一番外側の1か所だけに使う
- 重い公開鍵暗号は、鍵の受け渡しの1か所だけに使う

### エンベロープ暗号化

「データ用の鍵を、鍵用の鍵で包む」形はエンベロープ暗号化と呼ばれ、AWS KMS や Google Cloud KMS でも使われている定番の設計。

| 用語 | 意味 | この設計では |
|---|---|---|
| DEK（データ暗号化鍵） | データそのものを暗号化する鍵 | Vault 鍵 |
| KEK（鍵暗号化鍵） | DEK を包む鍵 | 包み用の鍵（メンバーごと）、パスコード鍵 |

秘密鍵をラップ鍵で包む部分も同じ形なので、この設計はエンベロープ暗号化が2段に重なった構造になっている。

### ラップしても解決しないこと

メンバーを削除するときは、包み直すだけでは済まない。抜けた人はすでに中身の Vault 鍵を知っているので、外側の包みを外しても意味がない。そのため Vault 鍵そのものを作り直し、全アイテムを再暗号化する（ローテーション）。

**外側の変更は包み直すだけで済む。内側の鍵が漏れたら中身からやり直す。**

## 11. 間違えやすかったところ

| 誤解 | 正しくは |
|---|---|
| ECDH を理解できないのは P-256 を理解していないから | P-256 の中身は不要。「一方向性」と「順番を入れ替えても同じ」の2つで足りる |
| 共有の点を作る組み合わせが無限にあるから安全 | 点の数は有限で、秘密鍵は1つに決まっている。安全なのは計算で取り出せないから（計算量的安全性） |
| 攻撃者は pk を知るために総当たりする | pk は公開されている。攻撃者が知りたいのは pk から sk |
| 1つずつ足すしかない | 平方根くらいまで減らす方法はあるが、それでも 2¹²⁸ 回。曲線の性質を使った近道がない |
| A-2 でラップ鍵を作る | A-2 で作るのは「包み用の鍵」。ラップ鍵は A-1 のパスワード由来の鍵 |
| HPKE は ECDH の品質保証 | HPKE は ECDH を部品として含む「組み立て方の規格」 |
| ECDH で使う鍵は使い捨ての鍵だけ | 使い捨てなのは管理者側だけ。もう片方は C さんの長期的な鍵 |
| ECDH で使う鍵が Vault 鍵を包む | 包むのは、ECDH の共有秘密から HKDF で作った「包み用の鍵」 |
