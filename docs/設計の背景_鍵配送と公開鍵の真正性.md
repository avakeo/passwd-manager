# 設計の背景：鍵配送問題と公開鍵の真正性

このパスワードマネージャーの設計が今の形になった理由を、暗号の基本問題から順にたどったメモ。仕様書の「なぜこうなっているのか」の部分にあたる。

---

## 0. 一言でいうと

**サーバーを信用しない（E2EE）と決めると、「鍵をどう配るか」と「届いた鍵が本物か」という2つの問題が順に出てくる。この設計は、それぞれを公開鍵暗号と、人によるフィンガープリントの照合で解いている。**

---

## 1. 出発点：サーバーを信用しない

脅威モデルでは、D1 の漏洩だけでなく、Cloudflare アカウントの乗っ取りや不正なデプロイ、つまり**サーバーそのものが敵になる場合**まで想定している。

そのため、次のことを守る必要がある。

- 平文も鍵もサーバーに渡さない（E2EE）
- サーバーが中継するものは、すべて「改ざんされているかもしれない」と考える

この2つの前提から、以下の問題が順に出てくる。

---

## 2. 問題1：鍵配送問題

### チームで暗号文を共有するには、全員が同じ鍵を持つ必要がある

アイテムは AES-GCM（対称鍵暗号）で暗号化する。対称鍵暗号は、暗号化と復号に同じ鍵を使う。つまり、チーム全員が同じ鍵（Vault 鍵）を持っていなければならない。

### その鍵をどうやって相手に渡すか

ここで問題になる。

- 鍵をそのまま送れば、途中で盗み見られたら終わり
- 鍵を暗号化して送ろうとすると、「その暗号化の鍵」を先に共有しておく必要がある
- これは堂々巡りになる

これが**鍵配送問題**。対称鍵暗号だけでは原理的に解けない。

### 対称鍵だけで作った場合（検討した案B）

チームで共通のパスワードを決め、そこから Vault 鍵を作る案。構造は単純になるが、鍵配送問題をそのまま人の手に任せることになる。

| 場面 | 何が起きるか |
|---|---|
| 新メンバーの追加 | チームのパスワード（＝全アイテムの鍵）を誰かが伝える必要がある。経路に秘密そのものが流れる |
| 盗み見られた場合 | パスワードは盗まれても手元から消えないので、誰も気づけない |
| メンバーの削除 | パスワードを変え、新しいパスワードを残り全員にまた配り直す |

---

## 3. 解決1：公開鍵暗号とハイブリッド暗号方式

### 公開鍵暗号は「秘密を運ばない」

公開鍵暗号では、鍵が公開鍵と秘密鍵のペアになる。

- 公開鍵：誰に見せてもよい。これを使えば誰でも「閉める」ことができる
- 秘密鍵：本人だけが持つ。これがないと「開けられない」

管理者は、新メンバーの**公開鍵**で Vault 鍵を包めばよい。開けられるのはその秘密鍵を持つ本人だけ。**秘密は一度も経路を通らない。**

### ハイブリッド暗号方式

公開鍵暗号は遅いので、データそのものの暗号化には向かない。そこで役割を分ける。

| 役割 | 方式 | この設計での場所 |
|---|---|---|
| データ（アイテム）の暗号化 | 対称鍵暗号（速い） | A-4：AES-256-GCM |
| 対称鍵（Vault 鍵）の受け渡し | 公開鍵暗号 | A-2：ECDH（P-256）＋ HPKE |

HTTPS（TLS）や PGP メールと同じ考え方。

### 経路に求めるものが変わる

これが一番大事な点。

| | 対称鍵だけ（案B） | 公開鍵を使う（今の設計） |
|---|---|---|
| 経路に流れるもの | 秘密（鍵そのもの） | 公開鍵（公開情報） |
| 経路に必要な性質 | 盗み見られないこと（秘匿性）と、改ざんされないこと（完全性） | 改ざんされないこと（完全性）だけ |

**公開鍵暗号は、鍵配送問題を「秘密を隠して運ぶ問題」から「本物かどうかを確かめる問題」に変える。** 隠して運ぶのは難しいが、本物か確かめるのはずっと易しい。

ただし、問題が消えたわけではなく、形が変わっただけ。それが次の問題。

---

## 4. 問題2：公開鍵の真正性（中間者攻撃）

### 公開鍵は、サーバーを通って届く

新メンバーの C さんの公開鍵は、D1 に保存され、管理者の端末にはサーバー経由で届く。ところが、この設計ではサーバーを信用していない。

### サーバーが乗っ取られていたら

1. 攻撃者が、C さんの公開鍵を**攻撃者自身の公開鍵**に差し替える
2. 管理者はそれに気づかず、本物の Vault 鍵を攻撃者の公開鍵で包む
3. 攻撃者は自分の秘密鍵でそれを開き、Vault 鍵を手に入れる
4. D1 にある全アイテムを復号できる

暗号そのものは一切破られていない。暗号化は正しく行われ、ただ「宛先」が偽物だっただけ。これが**中間者攻撃**で、公開鍵暗号の根本的な弱点。

**E2EE でも、公開鍵の真正性が保証されなければ安全とは限らない。**

---

## 5. 解決2：公開鍵が本物だと確かめる方法

公開鍵の真正性を確かめるには、最終的に**何か（誰か）を信頼する**しかない。その「信頼の根」をどこに置くかで、いくつかの方式がある。

| 方式 | 信頼の根 | 仕組み | 使われている例 | 弱点 |
|---|---|---|---|---|
| PKI（認証局） | 認証局 | 認証局が「この公開鍵はこのドメインのもの」と電子署名した証明書を発行し、ブラウザが検証する | HTTPS（TLS） | 認証局を信頼するしかない。認証局が不正をすると成り立たない |
| Web of Trust | 知人の署名の連鎖 | 信頼できる知人が署名した公開鍵を信頼する | PGP | 仕組みが難しく、普及しなかった |
| TOFU（最初の接続を信頼） | 最初の1回 | 最初に受け取った公開鍵を保存し、以後変わったら警告する | SSH の known_hosts | 最初の1回がすでに偽物だと防げない |
| 人による照合 ＋ 固定 | 利用者自身の確認 | 別の経路でフィンガープリントを見比べてから信頼し、その値を保存する | Signal の安全番号 | 人が照合を省くと意味がない |
| 鍵の透明性 | 公開された改ざんできない記録 | 公開鍵の一覧を誰でも検証できる追記専用の記録に載せる | WhatsApp、iMessage | 仕組みが大きい |

### なぜ PKI を使わないのか

Web の HTTPS は PKI で解決しているが、この設計では使えない。

- チームのメンバーの公開鍵に証明書を出してくれる認証局は存在しない
- 自前で認証局を立てる場合、それを置く場所はサーバーになる。**信用していないサーバーに「本物かどうか」を判定させることになり、本末転倒**

### この設計が選んだ方式：人による照合 ＋ 固定

Signal の安全番号と SSH の known_hosts を組み合わせた形。

1. **照合（双方向）**：承認のとき、管理者とメンバーが、フィンガープリント（公開鍵の SHA-256 を読み上げやすくしたもの）を**サーバーを通らない経路**で見比べる。管理者はメンバーの公開鍵を、メンバーは管理者の署名用公開鍵を確かめる
2. **固定**：照合できた公開鍵を、鍵 ID とメンバー ID との組でそれぞれの端末に保存する
3. **毎回の確認**：管理者はグラントを作るたび（承認時もローテーション時も）、サーバーから届いた公開鍵が固定した値と一致するかを確認する。メンバーはグラントを開くたび、管理者の署名を固定した署名用公開鍵で確かめる。違えば止めて警告する
4. **変更時は再照合**：公開鍵が変わったら（再登録など）自動では信用せず、1からやり直す

### 照合の経路に Discord を使わない理由

ログインに Discord を使っているので、Discord アカウントが乗っ取られた場合を考える必要がある。Discord で照合すると、攻撃者が「フィンガープリントは一致しています」と返事できてしまう。そのため、対面や電話など**別の経路**で照合する。

この経路に必要なのは「改ざんされないこと」だけで、「盗み聞きされないこと」は不要。フィンガープリントは公開情報なので、カフェで読み上げても問題ない。

## 6. この設計で残る限界

正直に書いておくべき部分。脅威モデルの範囲外の表とも対応している。

| 限界 | 内容 | 扱い |
|---|---|---|
| 照合が片方向（提出版。2026-10-17 に解消） | 提出版では、管理者はメンバーの公開鍵を確かめるが、メンバーは「管理者が包んだ本物の Vault 鍵か」を確かめなかった。乗っ取られたサーバーは偽の Vault 鍵を配れた（攻撃者レビュー #1） | 管理者署名と双方向の照合を入れた。管理者はグラントに ECDSA P-256 で署名し、メンバーは承認のときに照合して固定した管理者の署名用公開鍵で、署名を確かめてから開く（docs/設計案_グラントの送り手認証.md） |
| まだ見ていない新しい世代を隠される | 端末は最後に見た世代より古いグラントを拒否するが、サーバーが新しい世代のグラントを隠して古い世代のまま使わせることには気づけない | 範囲外。ローテーションの後、管理者が全員の端末の世代を対面で確かめる運用で補う |
| 固定が消える | 管理者が端末を初期化すると、固定した公開鍵が消える。メンバーが端末を初期化すると、固定した管理者の署名用公開鍵と、最後に見た世代が消える | 照合し直す。照合し直すまでグラントは作らない・開かない |
| 人が照合を省く | 面倒になって照合せずに承認すると、守りが成り立たない | 運用で守る。照合の画面を分かりやすくする |
| 照合の経路のなりすまし | 電話の相手が本人かは、声などで判断するしかない | 対面を優先する |

## 7. 設計の思想としてまとめると

この設計は、次の3つの原則でできている。

1. **サーバーを信用しない**：平文と鍵は端末の中だけ。サーバーは暗号文と公開情報しか持たない
2. **秘密は運ばない**：運ぶのは公開鍵だけ。秘密鍵もマスターパスワードも、生まれた端末や人の頭から出ない
3. **本物かどうかは人が確かめる**：信頼の根を、サーバーでも第三者でもなく、チームの人間同士の確認に置く

これは鍵の鎖の話とも対になっている。

- 鍵の鎖は「どこにも保存しないもの（人の記憶）」で終わる
- 信頼の鎖は「サーバーを通らない確認（人の照合）」で終わる

どちらも、最後の拠り所をシステムの外の人間に置いている。セキュリティの設計は、**最後に何を信頼するかを決めること**だと言える。

---

## 8. ポートフォリオでの説明例

> チームでパスワードを共有するには全員が同じ鍵を持つ必要があり、対称鍵暗号だけでは鍵配送問題が残る。そこでアイテムは AES-GCM で暗号化し、その鍵の受け渡しにだけ公開鍵暗号（ECDH、HPKE）を使うハイブリッド方式を採用した。
>
> ただし公開鍵はサーバー経由で届くため、サーバーが乗っ取られると公開鍵の差し替えによる中間者攻撃が成立する。PKI はサーバーに信頼を置くことになるため採用せず、Signal の安全番号と SSH の known_hosts に倣い、サーバーを通らない経路でのフィンガープリント照合と、照合済み公開鍵の固定で真正性を担保した。差し替えを検知できることはテスト P-01 で確認している。

## 9. 試験用語との対応

| 用語 | この設計での該当箇所 |
|---|---|
| 鍵配送問題 | 案B（チーム共通パスワード）の弱点 |
| ハイブリッド暗号方式 | AES-GCM でアイテム、ECDH ＋ HPKE で Vault 鍵の受け渡し |
| 中間者攻撃 | サーバーによる公開鍵の差し替え |
| 公開鍵の真正性 | フィンガープリントの照合で確認 |
| PKI、認証局、デジタル証明書 | HTTPS での解決方法。この設計では採用しなかった |
| TOFU、ピンニング（固定） | 照合済み公開鍵を管理者の端末に保存し、毎回比較する |
| アウトオブバンド（帯域外）認証 | 対面や電話での照合 |
