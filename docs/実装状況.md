## 4. HPKE（C-15）とテストベクタ

- CFRG の test-vectors.json に、本番の組（Base モード、KEM 0x0010・KDF 0x0001・AEAD 0x0002）があった。enc、shared_secret、key_schedule_context、secret、key、base_nonce と、257件の暗号文が、送り手と受け手の両方で一致した。2026-10-15 の時点では、付録 A.3 の組（AEAD 0x0001）も取得して一致を確かめた（今はベクタを置いていないのでテストから外した）。
- 仕様書の条件（この組で確かめた場合だけ「RFC 9180 準拠」と書く）を満たすので、README には「RFC 9180 の Base モードに準拠」と書いた。仕様書の本文は書き換えていない。
- **HPKE のベクタは、本番の組の1件だけを tests/vectors/hpke に置いた**（2026-10-16 の決定）。ライセンス表記は確認できなかった。CFRG のリポジトリにはライセンスファイルがなく、CONTRIBUTING.md に IETF の Contribution として扱うとあるだけ。IETF 文書由来のコード部品の扱いに準じると解釈して引用し、権利者から求めがあれば削除する（tests/vectors/README.md）。Simplified BSD とは断定していない。scripts/fetch-vectors.ts は、置いたファイルを出典から作り直して照合する道具で、テストの実行には要らない。
- Wycheproof（Apache-2.0）は、ライセンスの全文と一緒に tests/vectors/wycheproof に置いた。

### 8.3 Discord との通信を、テストでどう差し替えるか

本物の Discord を呼ばずに、本番と同じコードの道筋を通して自動テストする。

- **差し替えるのは fetch だけ**。src/api/discord.ts は、本番でもテストでも同じコードで `fetch('https://discord.com/api/v10/...')` を呼ぶ。テストでは `globalThis.fetch` を偽の Discord（tests/helpers/fake-discord.ts）に置き換える。本番の入口（worker.ts、createApp）には差し込み口を作らない。提出版の「本番の入口は createApp だけを使い、認証の差し込み口を持たない」という検査（guard.test.ts）は、そのまま守れる。
- **偽の Discord がすること**（本物の振る舞いのうち、こちらの守りに関わる所を再現する）：
  - 利用者の許可の代わりに、テストが `issueCode({ userId, redirectUri, codeChallenge })` で認可コードを発行する。
  - `POST /oauth2/token`：client_id とクライアントシークレット、redirect_uri の一致、認可コードの1回だけの使用、`code_verifier` の S256 が `code_challenge` と一致すること、を確かめる。違えば本物と同じ形の `invalid_grant` を返す。
  - `GET /users/@me`：発行したアクセストークン（Bearer）にだけ応える。
  - `GET /guilds/{サーバー}/members/{ユーザー}`：`Authorization: Bot <トークン>` にだけ応え、テストが決めたロールを返す。サーバーにいない人は 404。
  - 受けたリクエストを記録する。クライアントシークレットと Bot のトークンが discord.com 以外に送られていないこと、応答に Discord のトークンが含まれないことを確かめるのに使う。
  - discord.com/api/v10 以外への fetch は、テストを失敗させる（うっかり本物のネットワークに出ないように）。
- **設定の値**：テストでは `app.request(path, init, env)` の env に、テスト用の偽の値（クライアント ID、シークレット、Bot のトークン、サーバー ID、ロール ID、許可する redirect_uri、TOTP の暗号化の鍵）を渡す。本物の値はリポジトリにもテストにも入れない。
- **時刻**：TOTP の検証関数は時刻を引数に取る形にし、RFC 6238 付録 B のテストベクタ（SHA-1）で確かめる。エンドポイントのテストは、node:test の `mock.timers` で Date を固定し、期待するコードは src を使わずに node:crypto の HMAC で別に計算する。セッションの期限切れは、提出版と同じく D1 の expires_at を書き換えて確かめる。
- **D1**：提出版と同じく node:sqlite で包んだもの（tests/helpers/sqlite-d1.ts）。0002 のマイグレーションも読み込むようにする。
- **自動テストで確かめられないこと**（手で確かめる）：本物の Discord とのトークン交換、Bot の権限とインテントの設定、identity API の画面の流れ、実際の D1 と wrangler dev での動作。scripts/discord-login-check.ts で、マイルストーン1（Discord ログイン、Bot によるロール確認、セッション発行が動く）を手で確かめる。

### 8.5 あなたが用意するもの

シークレットの値はチャットに貼らず、自分の端末で登録する。下のコマンドの `npx wrangler` は、wrangler を開発依存に入れた後（6）に使える。

**1. 拡張機能の ID を固定する鍵**（Discord に登録するリダイレクト URL が、拡張機能の ID から決まるため）

Git Bash で、リポジトリの外に作る。`*.pem` は .gitignore に入っているが、リポジトリの中に置かないのが安全。

```
openssl genrsa 2048 | openssl pkcs8 -topk8 -nocrypt -out ~/teampw-extension-key.pem
# manifest.json の "key" に入れる公開鍵（フェーズ2で使う。公開鍵なのでコミットしてよい）
openssl rsa -in ~/teampw-extension-key.pem -pubout -outform DER | openssl base64 -A
# 拡張機能の ID（公開鍵の SHA-256 の先頭16バイトを16進にし、0-f を a-p に置き換えたもの）
openssl rsa -in ~/teampw-extension-key.pem -pubout -outform DER | openssl dgst -sha256 -binary | head -c 16 | xxd -p | tr '0-9a-f' 'a-p'
```

リダイレクト URL は `https://<拡張機能の ID>.chromiumapp.org/`。

**2. Discord のアプリと Bot**（https://discord.com/developers/applications）

1. New Application でアプリを作る。
2. OAuth2 の画面で Client ID を控え、Client Secret を Reset して表示する（値は5で登録する。どこにも貼らない）。
3. Redirects に次の2つを足す：`https://<拡張機能の ID>.chromiumapp.org/`（本番）と `http://localhost:8788/callback`（手動確認用。確認が終われば消してよい）。
4. 使うスコープは `identify` だけ（メールアドレスは使わない）。
5. Bot の画面で Bot を作り、Reset Token でトークンを表示する（5で登録する）。Public Bot はオフにする。Privileged Gateway Intents は、まずすべてオフのままにする。単体のメンバーの取得で 403 になったら Server Members Intent をオンにする（どちらが必要かは手動確認で確かめて記録する）。
6. Bot をチームのサーバーに招待する。権限は付けない：`https://discord.com/oauth2/authorize?client_id=<Client ID>&scope=bot&permissions=0`

**3. サーバー ID とロール ID**

Discord の設定 > 詳細設定 > 開発者モードをオンにする。サーバーのアイコンを右クリック > サーバー ID をコピー。サーバー設定 > ロールで、対象のロールを右クリック > ロール ID をコピー。この2つとクライアント ID は秘密ではないが、実際の値を書いた wrangler.toml はコミットしない（例の設定だけをコミットする）。

**4. Cloudflare の D1**

```
npx wrangler login
npx wrangler d1 create teampw-dev
# 表示された database_id を、手元の wrangler.toml（コミットしない）に書く
npx wrangler d1 migrations apply teampw-dev --local
npx wrangler d1 migrations apply teampw-dev --remote
```

本番用は、デプロイの前に別の名前で作る（仕様書「開発体制」：開発用と本番用で分ける）。

**5. シークレットの登録**

```
npx wrangler secret put DISCORD_CLIENT_SECRET
npx wrangler secret put DISCORD_BOT_TOKEN
# TOTP のシークレットを暗号化する鍵（32バイトの乱数）。画面に出さずに登録する
node -e "process.stdout.write(Buffer.from(crypto.getRandomValues(new Uint8Array(32))).toString('base64url'))" | npx wrangler secret put TOTP_ENCRYPTION_KEY
```

`wrangler dev` で手元で動かすときは、同じ3つを .dev.vars（.gitignore に入っている）に自分で書く。秘密でない設定（DISCORD_CLIENT_ID、DISCORD_GUILD_ID、DISCORD_ROLE_ID、DISCORD_REDIRECT_URIS）は、手元の wrangler.toml の `[vars]` に書く。

**6. wrangler の追加の承認**

wrangler を開発依存に入れる承認がほしい（CLAUDE.md「依存を追加する前に必ず確認を取る」）。承認されたら、その時点の安定版を `npm install --save-dev --save-exact wrangler@<版>` で固定し、package-lock.json の差分（wrangler が連れてくる esbuild、miniflare、workerd などの推移的な依存の一覧と数）を見せてからコミットする。テストは今までどおり node:sqlite で行い、wrangler はローカルでの起動、D1 の作成とマイグレーション、シークレットの登録、デプロイだけに使う。@cloudflare/workers-types は入れない（使う型だけを src/api/d1.ts に書く方針を続ける）。

**7. 最初の管理者**

最初のログインでは、自分も承認待ちのメンバーとして作られる。その後に一度だけ、手で管理者にする：

```
npx wrangler d1 execute teampw-dev --remote --command "UPDATE members SET role = 'admin', status = 'active' WHERE discord_user_id = '<自分の Discord ユーザー ID>'"
```

管理者は TOTP が必須なので、次のログインで TOTP の登録を求められる（A-11）。この手順でよいかは判断待ち6。

### 9.2 拡張機能の構成と、鍵の置き場所

| 部分 | 置き場所 | 役割 | 鍵 |
|---|---|---|---|
| Service Worker | src/extension/background/ | ログイン、トークン、API との通信、鍵、暗号と復号、同期、ロック。ポップアップと全画面ページからの指示を受ける唯一の入口 | 持つ（メモリだけ） |
| ポップアップ | src/extension/popup/ | ログイン、ロック解除（マスターパスワード・パスコード）、検索と一覧。自動入力とコピーはフェーズ3 | 持たない |
| 全画面ページ | src/extension/page/ | 一覧・編集・削除、TOTP の登録と作り直し、鍵の作成、セッションの一覧、クイックロック解除の設定 | 持たない |
| 共通 | src/extension/shared/ | メッセージの型と検査、画面の部品（文字だけで描く） | — |
| 暗号と部品 | src/crypto/、src/client/ | そのまま使う | — |

- **鍵はポップアップにも全画面ページにも渡さない**。秘密鍵・Vault 鍵の CryptoKey は Service Worker の変数だけに置き、取り出し不可のまま使う。画面には、表示に要る平文だけを渡す。
  - 一覧：タイトル、ユーザー名、URL（パスワードは渡さない）
  - 編集：開いた1件の中身（パスワードを含む）。画面を閉じたら持たない
- **マスターパスワードとパスコード**は、画面から Service Worker へ1回だけメッセージで送り、Service Worker で鍵を導いたらすぐ捨てる。画面側も送った後に入力欄を空にする。
- **トークン（アクセス・リフレッシュ）**は chrome.storage.session に置く（判断待ち3の案）。Service Worker が止まってもログインは続き、ブラウザを閉じると消える。画面には渡さない。
- **chrome.storage.local** に置くのは、暗号文のキャッシュ、最後に見た Vault リビジョン、署名鍵の固定、最後に見た世代だけ。平文と鍵は置かない。
- **書き込むのは Service Worker だけ**。暗号コアの世代の更新（raise）は、1つの JS の中で順番に処理する作りなので、書き手を Service Worker の1つに限る。
- **ロック**：明示的なロック、ブラウザの終了、一定時間の放置（判断待ち4の案は15分）。ロックすると、メモリの鍵とクイックロック解除の保存を消す。
- **クイックロック解除**（仕様書どおり）
  - マスターパスワードで解除したときに、グラントを取り出し可として開く（暗号コアの openGrantRaw）。
  - 4桁のパスコードから PBKDF2（端末ごとの乱数ソルト、60万回）で導いた鍵で、Vault 鍵を AES-256-GCM で包み、storage.session に置く。形式とアルゴリズム ID と AAD を付ける。生の鍵は包んだらすぐ消す。
  - 失敗の回数も storage.session で数え、5回で保存を消す。
  - パスコードで解除した状態は Vault 鍵だけを持ち、秘密鍵は持たない。管理操作では、常にマスターパスワードを求める（E-17）。

### 9.3 ポップアップ・全画面ページから Service Worker へのメッセージの検証

- **入口は chrome.runtime.onMessage の1つだけ**。onMessageExternal は登録しない。manifest に externally_connectable を書かない（Web ページからは届かない）。content_scripts も書かない。
- **送り元の確認**：`sender.id === chrome.runtime.id` で、`sender.url` が自分の拡張機能のページであるものだけを受け付ける。
  - 受け付けるページは popup/popup.html と page/app.html の2つ（`chrome.runtime.getURL` で作ったものと完全一致で比べる。クエリとハッシュは除く）。
  - フェーズ3で注入するスクリプトから届くもの（sender.url がページのアドレス）は、このフェーズでは全部断る。フェーズ3では、注入したスクリプトからの返事だけを、種類を限って別に受ける。
- **種類の限定**：受け付ける種類（`login`、`totp`、`unlock`、`quickUnlock`、`lock`、`listItems`、`getItem`、`saveItem`、`deleteItem`、`sync`、`status` など）を1つの表に固定する。
  - 種類ごとに、項目の名前と型と長さを、API の readJson と同じ厳しさで確かめる。知らない種類、余分な項目、型違いは、処理せずに `{ ok: false, error: 'BAD_REQUEST' }` を返す。
  - 状態を変える種類は、ロック中・ログイン前の扱いも表に書く（E-11）。
- **返事**には鍵もトークンも入れない。エラーは決めたコードだけで、内部の詳細は返さない。
- **テスト**：偽の chrome.runtime に、ページ由来・別の拡張機能・URL 違い・知らない種類・余分な項目のメッセージを入れ、処理されないことを確かめる（E-08）。

### 9.4 署名鍵の固定と最後に見た世代の保存先

- 暗号コアの `TrustStorage`（キーと文字列の値）を、chrome.storage.local で作る（src/extension/background/trust-storage.ts）。`get` は `chrome.storage.local.get(key)` の文字列だけを返し、文字列でなければ「ない」とする。`set` は文字列だけを書く。
- 組の決め方は暗号コアの `openTrust(storage, { apiOrigin, memberId })` のまま（キーは `teampw/v1/trust|<接続先>|<メンバーID>|signer` と `…|generation`）。
  - apiOrigin：ビルドのときに決めた API の接続先（https のオリジン）。
  - memberId：ログインの応答のメンバー ID。GET /v1/me の id と同じことを確かめる。
- 最後に見た Vault リビジョン（S-09）と暗号文のキャッシュも、同じ形で組ごとのキーにする（`teampw/v1/sync|<接続先>|<メンバーID>|…`）。
- 管理者の端末は、ロック解除できた自分の行の署名用公開鍵を固定する（仕様書どおり）。メンバーの固定と世代の初期化は承認の照合（フェーズ4）で行うので、このフェーズのメンバーは「照合を待っています」と出してグラントを開かない（P-04、P-07）。
- 暗号コアの openTrust は https の接続先しか受け付けない。そのため、手で確かめるときも https の API が要る（判断待ち5）。

### 9.5 TOTP の登録画面と、回復コードの表示

- **QR コード**：このフェーズでは描かない（判断待ち2の案）。全画面ページに次の3つを、文字として表示する。
  - otpauth の URI
  - シークレットの base32（4文字ずつ区切る）
  - 「認証アプリで『キーを手入力』を選ぶ」という案内
  QR の描画は依存ゼロでも書けるが、誤り訂正（リード・ソロモン）とマスクの実装が数百行になり、間違えると読めない QR が出る。手入力で困ると分かってから足す。
- シークレットはコピーのボタンを付けない（クリップボードに TOTP のシークレットを残さない）。画面を閉じたら持たない。
- **確定**の後に、回復コード10個を一度だけ表示し、「保存した」を押すまで閉じない。
- **残りの数**：ログインの応答と GET /v1/me の recovery_codes_remaining が3以下なら、作り直しを勧める表示を出す。0なら強く勧める。
  - ポップアップでは、上に1行の知らせとして出す。全画面ページでは、作り直しのボタン付きで出す。
  - 回復コードでログインした直後の5分は、コードなしで作り直しを始められる（フェーズ1の再レビューの対応）。この5分の間は、案内を「今すぐ作り直す」にする。
- 登録を求められた状態（status が totp_setup_required）では、ポップアップから全画面ページの TOTP の登録を開く。ほかの画面は出さない。

### 9.6 ビルドの方法

依存は足さない。入っている TypeScript 6.0.3 で、拡張機能の JS を作れることを確かめた。
- `rewriteRelativeImportExtensions` を有効にすると、`import … from './b.ts'` は `./b.js` に書き換わる。
- 作業用の場所で試し、出力は `import { a } from "./b.js";` になった。

- `tsconfig.extension.json`（新しく作る）：src/extension、src/crypto、src/client を、ES2022 のモジュールとして dist/extension に出す。
  - 設定は `rewriteRelativeImportExtensions`、`module: ES2022`、`moduleResolution: bundler`。
  - src/api（Workers 用）は含めない。
- `scripts/build-extension.ts`（Node の型除去で動かす）：
  1. tsc を呼ぶ。
  2. manifest.json、HTML、CSS を dist/extension に写す。
  3. manifest の `key` と、API の接続先（host_permissions）を、Git の管理外の設定ファイル（extension.config.local.json）から埋める。例の設定（extension.config.example.json）だけをコミットする。
- `npm run build:extension` を足す。dist/ は .gitignore に入れる。
- Service Worker は `"type": "module"`、画面は `<script type="module">`。インラインのスクリプトは書かない（MV3 の既定の CSP のまま）。
- 権限は storage、identity、scripting（フェーズ3）と、API の接続先の host_permissions だけ。activeTab と clipboardWrite と offscreen はフェーズ3で足す。全サイトへの権限は要求しない。
  - 一定時間の放置の検知に alarms を使うかは、判断待ち4。
- chrome の型（@types/chrome）は入れない。使う API だけを types/chrome-shim.d.ts に自分で書く。

### 9.7 拡張機能をブラウザで動かす自動テスト

このフェーズでは入れない（判断待ち6）。
- **自動テスト**：Service Worker の処理は、chrome の API を偽物（tests/helpers/fake-chrome.ts）に置き換え、Node のテストで確かめる。
  - 偽物にするのは storage.session と storage.local、runtime.onMessage の sender、identity。
  - 鍵、同期、メッセージの検査、クイックロック解除は、ここで確かめる。
- **ビルドの検査**：dist/extension の manifest をテストで読み、次を確かめる。
  - 権限が決めたものだけであること。
  - content_scripts と externally_connectable がないこと。
- **HTML として解釈しないことの検査**（持ち越しの DeepSeek #2）：画面のコードに `innerHTML`、`outerHTML`、`insertAdjacentHTML`、`document.write` がないことを、既存の guard.test.ts と同じやり方で確かめる。描画は textContent と createElement だけにする。
  - 端末名には、`<img src=x onerror=…>` の形の文字列を入れた画面の部品の単体テストも置く。部品は DOM を使わない「何を表示するか」の関数に分け、そちらで確かめる。
- **フェーズ3**：自動入力（E-01〜E-13）は、実際に拡張機能を読み込んで確かめないと意味がない。その準備として、ブラウザの自動操作の依存（例：Playwright）を入れるかを、フェーズ3の前に決める（判断待ち6）。
  - Chrome 137 以降は、通常の Chrome で `--load-extension` が効かない。自動操作には Chrome for Testing か Chromium が要る。

### 9.9 進め方（コミットの予定）

テストを先に書き、落ちることを確かめてから実装する。1つずつコミットする。

1. ci：GitHub Actions（9.11）。最初に入れて、以後の push で確かめる
2. build(extension)：tsconfig.extension.json、ビルドのスクリプト、manifest、空の Service Worker と画面。ビルドの検査のテスト（E-16 の manifest の部分）
3. feat(extension)：メッセージの入口と検査（E-08）
4. feat(extension)：chrome.storage の保存先。署名鍵の固定・世代・Vault リビジョン・キャッシュ（P-09 を chrome.storage.local の偽で）
5. feat(extension)：ログイン（identity、トークンは storage.session、更新）と TOTP（ログインの途中のコード、登録、作り直し、回復コードの残り）
6. feat(api)、feat(extension)：鍵の登録（PUT /v1/me/keys。仕様書にあるがまだない）と、マスターパスワードでのロック解除。最初の Vault の作り方（判断待ち1）
7. feat(extension)：アイテムの一覧・作成・編集・削除と同期（S-01、S-02、S-09、S-10、E-11）
8. feat(extension)：クイックロック解除と放置でのロック（E-14、E-15、E-17、E-18）
9. docs(review)：docs/review/phase-2.md（テスト ID の結果、手で確かめる項目、観点表）

### 9.11 GitHub Actions（push のたびに npm test と npm run typecheck）

- `.github/workflows/ci.yml`：push と pull_request で動かす。
  - `permissions: contents: read`。シークレットは使わない。
  - ubuntu-latest で、Node は package.json の engines に合わせて 22 系にする。テストの node:sqlite のため、22.16 以上。
- 手順：actions/checkout → actions/setup-node（npm のキャッシュ）→ `npm ci --ignore-scripts` → `npm test` → `npm run typecheck`。
  - esbuild と workerd の postinstall は、手元と同じく動かさない。テストに wrangler の実行ファイルは要らない。
  - 手順2の後に `npm run build:extension` も足す。
- 外部のアクション（actions/checkout、actions/setup-node）は、サプライチェーンの経路になる。タグではなくコミットの SHA で固定し、コメントに版を書く。SHA は入れるときに GitHub の公式のリリースから確かめる（判断待ち7）。
- 同じブランチの古い実行は止める（concurrency）。
