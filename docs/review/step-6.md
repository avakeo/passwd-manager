## 対応する仕様の節

- 暗号仕様 > メンバー鍵ペア（フィンガープリントの作り方、比較は65バイトそのもので行う）
- 暗号仕様 > Vault鍵の受け渡し（グラントを作るたびに、固定値と照合する）
- 鍵とメンバーのライフサイクル > メンバーの参加と承認（手順5：固定先は、提出版ではインターフェースだけ）

## テスト ID

| ID | テスト |
|---|---|
| P-01 | 管理者が C さんの公開鍵を固定した後、サーバーがそれを攻撃者の公開鍵に差し替える。管理者がグラントを作ろうとすると PUBLIC_KEY_MISMATCH で止まり、グラントは作られない。固定していないメンバー宛て、鍵を再登録したメンバー宛ても、照合し直して固定するまで作れない |

## 観点表で見てほしい所

| 観点 | 見てほしい所 |
|---|---|
| 公開鍵の固定 | `createGrant` は、最初の行で `assertPinned` を呼ぶ。グラントを作る export された関数はこれだけ。比較は `equalBytes` で、長さが同じなら全バイトを比べる |
| 固定の書き換え | `MemoryPinStore` は、保存するときも取り出すときもコピーを渡す。呼び出し側が後から配列を書き換えても、固定値は変わらない |
| フィンガープリント | 5バイトの整数は最大 2^40 なので、Number（2^53 まで正確）で計算できる。テストでは BigInt で別に計算して比べる。学習メモの公開鍵の SHA-256 の先頭（70dd2685e8369120b12d）とも一致する |
| 照合の経路 | フィンガープリントの照合を Discord 以外の経路で行うのは、運用と画面の話で、コードでは担保できない。コードが担保するのは「固定した後の差し替えの検知」まで |
| 検査テストの限界 | guard.test.ts は正規表現でソースを読むだけ。動的な import や、別名を付けた呼び出しまでは追えない |

### #4 の対応の中身

| 確かめたいこと | 以前 | 今 |
|---|---|---|
| `createGrant` が包む前に固定値と照合する | 正規表現 `createGrant[\s\S]*?await assertPinned\(` と P-01 | P-01 の動作のテストだけにした。正規表現は外した |
| 照合なしで包む関数を export しない | 正規表現 `export function sealGrant` | 読み込んだ grant.ts が export する関数が、`createGrant`、`grantInfo`、`openGrant`、`openGrantForAdmin` だけであることを確かめる（P-01 のテストとして pin.test.ts に置いた） |

| 取り出し不可、乱数、ログ | 正規表現 | 補助の検査として残す。取り出し不可の動作は C-16 で確かめている |

guard.test.ts のテスト名は「観点表（補助）」で始めた。

テスト用の口（`setupBaseSWithEphemeral`）は、本番のモジュールから import できない場所へは移さなかった。テスト専用のファイルへ移すと、テストベクタ（C-15）で確かめる処理と、本番の `sealBase` が通る処理が別の関数になるため。代わりに、上の import の検査を広げた。
