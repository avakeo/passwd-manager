## 補足（重大度の根拠と、仕様の範囲外表との関係）

- #1 は仕様の範囲外表「悪意あるサーバーによる偽Vault鍵の配布」と同じ種類。ただし仕様は「**新規参加者**に渡せる／その参加者が**新しく書いた**アイテムのみ読まれる」と限定し、検知の根拠を「既存アイテムが開けなくなる」に置いている。実際は (a) 新規参加者に限らず**既存メンバー全員**に、(b) 端末側には検知のコードが一切なく、気づけるかどうかは利用者が「アイテムが壊れた」ことに気づけるかに依存する。攻撃の入口が「グラントの行を書き換えるだけ（`/v1/me` も触らない）」で済む点は仕様の記述より広いので、高とした。
- #2・#3・#4 は範囲外表に**載っていない**新しい指摘。#2 は pin の意味（「承認済み公開鍵」）を鍵IDにまで広げていない穴、#3 は「自分の鍵」を誰も検証していない穴。どちらも機密の直接漏洩ではなく、静かな失敗（用意した鍵で開けない）と、#1 の成功を利用者から隠せることに効く。
- #4・#6 は「テストは通るが危ない」の指摘。`guard.test.ts` はソース文字列の正規表現なので、危ない書き方（分岐の奥・握りつぶし・動的 import・別名 export）を検知できない。M2 で info の形の誤りを C-13/C-15 が捕まえられなかったのと同じ種類の穴が、固定（P-01）と使い捨て鍵の扱いにも残っている。
- #5・#7・#8 は設計・運用寄りの低い指摘。#7 は仕様で「検知のみ」と決めている範囲だが、暗号コア側に検知の受け口が無いことを記録しておく（3章の観点表の「AAD」「エラー」では拾えない種類）。
