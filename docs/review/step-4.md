## 対応する仕様の節

- 暗号仕様 > メンバー鍵ペア（秘密鍵の AAD）
- 暗号仕様 > 鍵導出（クライアントで下限を確かめる）
- 鍵のライフサイクル（ロック解除後の秘密鍵は取り出し不可で、鍵交換だけに使う）

## 処理の順番

1. 保存形式の確認（形式 0x01、アルゴリズムID 0x01）
2. KDF の種類・回数・ソルトの確認（下限未満なら、重い計算の前に拒否する）
3. AAD `v1|member-key|鍵ID` を、行の鍵IDから組み立て直す
4. PBKDF2 → HKDF でラップ鍵を作る
5. AES-256-GCM で復号する。失敗の理由は区別しない
6. PKCS#8 を、取り出し不可の ECDH 秘密鍵として読み込む（使い道は deriveBits だけ）
7. PKCS#8 のバイト列を0で上書きする

## テスト ID

| ID | テスト |
|---|---|
| C-07 | 間違ったパスワードで DECRYPT_FAILED になる。改ざんしたときとエラーの code とメッセージが同じで、原因（cause）も付かない |
| C-16 | ロック解除後の秘密鍵は、extractable が false。pkcs8 でも jwk でも書き出せない |
| C-03 | 秘密鍵の暗号文、ノンス、認証タグの1ビットの改ざんで失敗する |
| C-14 | サーバーが弱い KDF 設定を返すと、復号を試さずに拒否する |
| C-10 | 秘密鍵の保存形式が未知なら拒否する |
| （学習メモ） | メモ10章の値（sakura-kumo-ringo-73、ソルト 9f2c…、ノンス 3b7e…、AAD v1\|member-key\|key_7f3a）で暗号文を開け、メモの秘密鍵と同じ ECDH の結果になる |

## 観点表で見てほしい所

| 観点 | 見てほしい所 |
|---|---|
| 取り出し不可 | `importKey('pkcs8', …, false, ['deriveBits'])`。usages を deriveBits だけにした |
| KDF の下限 | `unlockMemberKey` の中でも、`deriveWrapKey` より前に `assertKdfParams` を呼ぶ |
| エラー | 復号の失敗と、PKCS#8 の読み込みの失敗を、同じ DECRYPT_FAILED にまとめる。KDF の拒否と形式の拒否は別の code になるが、どちらもサーバーが返した平文のメタデータで決まる情報で、パスワードの正誤とは関係しない |
| 総当たり | パスワードの正誤はサーバーに聞かなくても、認証タグで分かる。同じことは、D1 を盗んだ攻撃者にもできる（オフラインの総当たり）。重い KDF と長いマスターパスワードは、その1回あたりの手間を増やすためのもの |
