## 結論

自動入力のオリジン・iframe・見えている欄の確認、クリップボードの1分後の消去、CSV の解析と上限、端末を覚えるの3回制限とトークンの入れ替え、正直なサーバーでのローテーションのガード、P-08 の端末側の値の確認、S-12 の作り直し、Web ページの state・PKCE・CSP・CORS・TOTP は、指定された狙いの範囲では成立しなかった。

残る重い穴は、**「対面で見比べる」という前提が、見比べる値の出どころまで守っていない**点に集まる。

1. **固定する前の公開鍵の差し替え**（#1・高）。承認待ちのメンバーの ECDH 公開鍵をサーバーが差し替えると、メンバーの画面の「あなたの公開鍵」も、管理者の画面の「メンバーの公開鍵」も、同じ差し替え後の値になる。2人が見比べても一致するので、管理者は攻撃者の鍵を固定し、本物の Vault 鍵を攻撃者の鍵に包んでしまう。鍵を持たない攻撃者が、以降のアイテムをすべて読める。
2. **固定する前の管理者署名鍵の差し替え**（#2・高）。`/v1/me` の管理者の署名用公開鍵をサーバーが差し替えると、メンバーの画面の「管理者の署名鍵」も、管理者の画面の「あなたの署名鍵」も、同じ攻撃者の値になる。メンバーは攻撃者の署名鍵を固定し、その後の本物の承認を、攻撃者の鍵で包んだ偽の Vault 鍵のグラントに差し替えられる。メンバーが以後に保存するアイテムを攻撃者が読める。
3. **ローテーションの宛先と対象を、サーバーの一覧だけで決めている**（#3・高、#4・中）。削除したメンバーをサーバーが有効なまま返せば、管理者の端末はその人に新しい世代の Vault 鍵を包む（#3）。ローテーションの取得からアイテムを1件隠せば、そのアイテムは古い世代のまま取り残され、古いグラントの削除で読めなくなる（#4）。どちらも、正直なサーバーでは rotation_guard が 409 にするが、サーバーが悪意ある場合はクライアント側に照合の口がない。
4. **Web 用トークンの「読み取り専用」が、メソッドだけの制限**（#5・低）。Web ページのクライアントは4つの GET しか呼ばないが、サーバーは Web 用トークンで任意の GET を通す。アイテムの暗号文、全員分のグラント、メンバー一覧、監査ログを取得できる。E2EE なので平文は出ないが、画面の想定より広い。

#1・#2 は、**鍵を持たない攻撃者が、利用者に気づかれずに Vault 鍵を取る**もので、このレビューで最も重い。#3・#4 は、削除・ローテーションという復旧手段そのものを無効にする。

## 補足

- 重大度の基準：**高**は、鍵を持たない攻撃者が、秘密の内容を気づかれずに差し替え・取得できるもの、または削除・ローテーションの復旧を無効にするもの。**中**は、持続する可用性の低下やデータの損失。**低**は、気づかれる DoS や、仕様で範囲と決めた制約の再確認。
- #1・#2 の根っこは同じである。**「2つの画面の値を見比べる」は、少なくとも片方の値がサーバーの今の応答から独立していないと、悪意あるサーバーに両方を揃えられる。** 実装には、サーバーから独立した値がすでにある。メンバーの `state.unlocked.publicKey`（AAD で秘密鍵と結びついている）と、管理者の `state.unlocked.signPublicKey`（P-08 の `ownSigner` が使っている）である。ところが `adminSigner` の `ownFingerprint` と `listMembers` の `signFingerprint` は `/v1/me` の値を使う。P-06 は「画面の値が DB の公開鍵と一致する」ことを確かめているが、これはサーバー由来の表示を固定しているだけで、差し替えの検知にはならない。
- #3・#4 の根っこは、**ローテーションの宛先（メンバーの集合）と対象（アイテムの集合）を、クライアントがサーバーの一覧だけで決めている**ことである。サーバー側の rotation_guard は、正直なサーバーが誤って削除済みのメンバーやアイテムを落とすのを防ぐが、悪意あるサーバーはガードを通さない。クライアントには、削除したメンバーの記録（固定を消す、削除済みの一覧を持つ）も、同期済みのアイテムの集合と比べる口もない。仕様の「サーバーが整合した古い状態全体を返された場合は検知できない」の範囲に近いが、#3 は「削除したのに新しい鍵が渡る」、#4 は「ローテーションが成功したように見えてアイテムが消える」で、どちらも復旧手段の意味を失わせる。
- #5 は、E2EE のため平文の漏洩にはならない。Web 用トークンで読めるのは暗号文とグラントと公開情報である。それでも、Web ページの XSS の被害を「閲覧」に限るという仕様の意図に対して、閲覧できる範囲が画面の4つの GET より広い。サーバー側の許可リストがないため、Web ページのクライアントを変えても範囲は変わらない。
- 自動入力・クリップボード・CSV・端末を覚える・P-08・S-12・Web の state/PKCE/CSP/CORS は、既存のテスト（E、M、A、P、S、W 系）とコード確認の範囲で成立しなかった。ブラウザでの手動確認は phase-3・phase-web の記録の範囲で、このレビューでは新たに実行していない。未実行のものは「推測」と書いた。
- このレビューの実測テストは、リポジトリを変更しないよう、`tests/extension/review-tmp.test.ts` に一時的に置いて実行し、レビューの後に削除した。再現の手順は上の表に書いたとおりで、必要な場合は同じ内容を `tests/extension/` に固定する。`npm test` は 635件成功、`npm run typecheck` も成功している。一時テストはリポジトリに残していない。
