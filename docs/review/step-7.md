## 対応する仕様の節

- API・インフラ > エンドポイント、エラーと楽観的ロック、ドメインとCORS、無料プランの制約（バッチ、バインド）
- 暗号・データ仕様 > 認証・認可フロー > 認可とセッション（ハッシュだけ保存、Bearer、Web 用は読み取り専用、ログに出さない）
- 開発・テスト・診断 > 提出版のテストの方法（app.request と node:sqlite、テスト用の認証は本番の入口に置かない）

## テスト ID

| ID | テスト |
|---|---|
| S-01 | 2人が同じリビジョンを元に編集し、後から保存した方が 409 になる。内容と Vault リビジョンは変わらない。古いリビジョンでの削除も 409 |
| Z-01 | 承認待ちのメンバーが GET /v1/items、GET /v1/vault、POST、PUT、DELETE を呼ぶと、すべて 403 |
| C-13（API 経由） | C さんが API から取った鍵情報、グラント、暗号文だけで、マスターパスワードからアイテムを復号できる。D1 に平文が残っていない |
| ついでに確かめたもの | S-02、S-10（論理削除）、I-01（413）、I-02、I-05（400 で内部情報なし）、I-03（ID の重複は 409）、Z-04（他人宛てのグラントは返さない）、Z-06（削除済みは 403）、Z-07（Web 用トークンの書き込みは 403）、A-05、A-06（期限切れ、無効化は 401）、W-01、W-02（CORS） |

## 観点表と、仕様で見てほしい所

| 観点 | 見てほしい所 |
|---|---|
| 楽観的ロック | `UPDATE … WHERE id = ? AND revision = ? AND deleted_at IS NULL` が1行も変えなければ、存在すれば 409、なければ 404 |
| Vault リビジョン | 書き込み、Vault リビジョンの更新、監査ログを1つのバッチにした。2文目と3文目は `changes() = 1` のときだけ動く。SQLite では直前の文の変更行数を返すが、**実際の D1 でも同じに動くかは確かめていない** |
| クエリ数 | 書き込みは、認証1 ＋ バッチ3文 ＋（0件のときだけ）存在確認1。仕様の目安（2〜3クエリ）より1つ多いのは、監査ログを同じバッチに入れたため |
| 暗号文の検査 | サーバーは中身を読まない。base64url であること、長さがパディング単位 ＋ 30バイトのどれかであること、先頭2バイトが 0x01 0x01 であることだけを確かめる |
| テスト用の認証 | 本番のコードに固定トークンはない。テストは sessions 表にトークンのハッシュを入れ、本番と同じ認証を通す |
| ログ | ロガーを置かない。src に console がないことを guard.test.ts で確かめる |
| 範囲外 | Discord ログイン、トークンの発行、鍵の登録、承認（グラントの保存）、ローテーションの API は、提出版では作っていない。E2E のテストでは、その部分を D1 に直接書き込んでいる |
