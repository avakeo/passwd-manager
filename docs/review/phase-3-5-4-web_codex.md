確認できた点：

- 保持が通常どおり完了する経路では、storage.session に置くのは Vault 鍵と世代だけで、秘密鍵・署名用秘密鍵は置かない。復帰した鍵は取り出し不可で、管理操作にはマスターパスワードを求める。storage.local の保持設定は接続先とメンバーごと。問題は #1・#2 の並行操作で、ディスクへの生鍵保存を追加したわけではない。
- 「この端末を覚える」は利用者の操作と直近5分のTOTPを求める。端末トークンはハッシュ、PINの値はTOTP用サーバー鍵から別ラベルのHKDFで派生したHMACで保存する。復帰で同じセッションのトークンを替え、TOTP確認時刻をNULLにし、7日の期限を延ばさない。逐次の失敗・期限切れ・ログアウト・削除・ロール剥奪拒否はテストで確認される。#7 は確認と保存の間の状態変化。
- 承認はグラントの署名・形式を確かめ、同じバッチの先頭で承認待ち・宛先鍵の有効性・署名鍵の有効性・世代を確認する。削除は状態変更、セッション・端末の無効化、グラント削除、鍵の失効を1バッチで行う。削除に rotation_guard はないが、対象の確認は先頭の条件付きUPDATEで行う。ローテーションは世代・Vaultリビジョン・未削除アイテムの集合と次のリビジョン・有効な宛先集合を guard で照合し、途中の失敗時に全体が戻る。ただし #4 の後着する旧世代書き込みと #6 は残る。
- インポートは上限500件・1.5MBで、作成と監査ログをそれぞれ json_each の1文にまとめる。認証込み4文。承認は認証1＋事前SELECT3＋バッチ5＝9文、削除は認証1＋バッチ6＝7文で、人数比例のSQL発行はない。ローテーションの問題は #5。リモートD1での計測はしていない。
- 0004は既存表の作り直しをせず、新しい表を追加する。member_id・session_idの外部キー、session_id・token_hashの一意制約があり、トークン・PINそのものの保存列はない。制約を維持するテストには #8 がある。
- CORSは WEB_ORIGIN との完全一致で1つだけを許可し、未設定なら許可しない。WebのOAuth戻り先から作った一時トークンとセッションは web scopeで、更新しても維持される。Webトークンによる書き込み・管理操作はサーバー側で拒否し、GET /v1/me は暗号化秘密鍵・KDFを返さない。Webページは鍵を開かず、セッションの無効化も行わない。管理者の監査ログは5分以内のみ。
- Webページは別Workerのアセットとして配信し、run_worker_first=true。state・PKCE検証値は移動中だけsessionStorage、アクセストークンとリフレッシュトークンはページのメモリ。戻り先のコードとstateをURLから消し、描画はtextContentを使う。通常のアセット応答には仕様のCSPなどが付く（例外は #9）。
- 追跡対象ファイルのURLと設定を走査し、サービス自身の実際の配信ドメインの混入は見つからなかった。example系の例示、localhost、Discordや参考文献・依存配布元へのURLはある。手元のwrangler・ビルド設定とdistはgit管理外。
- 2a・2bで採用した、リフレッシュの同時実行制御・セッション番号、鍵登録のバッチ内guard、メンバーID照合、未設定端末への本物のグラントの拒否、初期Vaultの署名検証、statusで放置時刻を延ばさない扱い、lockでの一時トークン消去、quickUnlockの終端確認、アイテム復号後の確認、同期の古い結果の反映抑制、0003既存行の移行テスト、ブラウザのSW停止確認は残っている。既存処理の削除による差し戻しは見つからなかったが、追加経路で同種の終端確認漏れが #1〜#3 にある。
