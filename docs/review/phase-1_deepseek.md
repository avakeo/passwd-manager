- 前提（これまでと違う点）：**攻撃者はサーバー（D1 と Workers）を乗っ取っていない**。サーバーは正直に動く。攻撃者は、(a) メンバーの Discord アカウントまたはそのログインセッションを盗んだ人、または (b) 未承認（pending）のままログインした人。端末とマスターパスワードは攻撃者の手にない
- 見たファイル：`src/api/auth.ts`、`src/api/auth-routes.ts`、`src/api/session.ts`、`src/api/discord.ts`、`src/api/totp.ts`、`src/api/app.ts`、`src/api/json.ts`、`src/api/env.ts`、`src/api/problem.ts`、`src/client/discord-login.ts`、`src/crypto/random.ts`、`migrations/0002_auth.sql`、`tests/helpers/api.ts`、`tests/helpers/fake-discord.ts`、`tests/api/authz-matrix.test.ts`、`docs/review/phase-1.md`
- この文書は「どこが・なぜ危ないか」だけを示す。本体のコードの直し方は書かない。

## 結論

サーバーが正直でも、**セッションと TOTP の守りがすべて「持ち主の Discord アカウント」と「その端末のメモリ」に載っている**。E2EE のおかげで平文（Vault）は漏れないが、メンバーは TOTP が任意なので、Discord アカウントを1つ盗むだけで共有 Vault への完全な読み書きが手に入る。壊せるのは機密ではなく、Vault 全体の完全性・可用性と、ログインの観測・締め出しである。漏洩が無いぶん目立たないが、チームの共有資産を一括で消せる点は重い。

## 補足

- 重大度の基準：E2EE のため #1〜#9 のいずれも**平文の漏洩には至らない**（Vault 鍵もマスターパスワードも攻撃者の手にない）。重いのは、共有 Vault を一括で消す・上書きする完全性と可用性（特に #1）、およびログインの観測と締め出しである。
- #1 は「メンバーの TOTP を任意にした」仕様の帰結。管理者は TOTP 必須なので、同じ手が管理者には効かない（`ADMIN_SETUP_ROUTES` とログインの `totp_required`）。守りの差がそのまま攻撃対象の差になっている。
- #2 と #3 は、トークンが盗まれた後の「被害者の気づきにくさ」に効く。ログアウトさせられる・一覧で偽装される・ステップアップが端末に紐づかない、の3つが重なると、乗っ取りが静かに続く。
- #4 は現在まだ穴が開いていない（web ログインが未実装）が、`'extension'` 固定のまま後から Web ログインを足すと読み取り専用（Z-07）が破れる。テストが `sessions` 行を直接入れて通しているため、本番経路の欠落に気づきにくい。
- #5 の `admin_signer` と `current_vault_key_version` を pending に返すのは、双方向の照合のために意図した仕様。ただし「人の目で見比べる」情報を無制限に取れる点、および管理者の人数で 409 になる点は、フェーズ0レビューの世代・固定の攻撃（未設定の端末を古い世代で初期化させる等）の下準備として記録しておく。
- #6 は「トークン更新を1世代しか覚えない」標準的な限界。仕様（A-12）は1つ前の再利用だけを想定しているので、範囲内だが、2世代前の窃取では静かなままであることを明記する。
- #7〜#9 は運用・多層防御寄り。特に #7 は、後のフェーズでレート制限を入れるときの受け口（認証系の上限）が今はどこにも無いことを示す。
