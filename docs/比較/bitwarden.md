# Bitwarden との比較

- 日付：2026-11-03
- 比べた資料：Bitwarden のセキュリティホワイトペーパーとヘルプ、論文「Zero Knowledge (About) Encryption」（USENIX Security 2026、以下「論文」）
- 選んだ理由：Bitwarden は、オープンソースで、組織（チーム）での共有を持ち、仕組みが公開されている。teampw と同じ「チームで共有する E2EE のパスワードマネージャー」で、いちばん近い

## 1. 仕組みの比較

| 項目 | teampw | Bitwarden |
|---|---|---|
| 鍵の導出 | PBKDF2-HMAC-SHA256 60万回。クライアントが下限を持ち、弱い設定を拒否する | PBKDF2-SHA256（既定60万回）か Argon2id（2023.2.0 から）。論文の報告の後、下限は5000回になった |
| 用途ごとの鍵 | HKDF でラベルを分ける | マスターキーを HKDF で512ビットに伸ばし、暗号用と MAC 用に分ける |
| ログイン | Discord ＋ TOTP。マスターパスワード由来の値はサーバーに送らない | マスターパスワードから作ったハッシュをサーバーに送って認証する。2要素認証は任意（組織の方針で必須にできる） |
| アイテムの暗号 | AES-256-GCM。JSON 1件を1つの暗号文にし、512B〜64KB の5段階にパディングする | AES-256-CBC ＋ HMAC-SHA256。欄（名前、ユーザー名、パスワード、URL など）ごとに暗号化する。アイテムごとの鍵は2024年から |
| AAD（暗号文と場所の結び付け） | 形式、アイテム ID、鍵の世代、書き込み後のリビジョン | 欄の暗号文どうしを結び付けるものはない（論文 BW05） |
| 共有の単位 | チームに Vault が1つ。全員が全件を見る | 組織とコレクションで、見られる範囲を分けられる |
| 共有の鍵の受け渡し | HPKE（RFC 9180、P-256）。グラントに管理者が ECDSA で署名する | 組織の鍵を、メンバーの RSA 公開鍵で包む。署名はない |
| 相手の公開鍵 | 承認のときに双方向で照合し、「メンバー ID、鍵 ID、公開鍵」を端末に固定する。照合が済むまでグラントを開かない | 承認のときに、管理者の画面にメンバーのフィンガープリント（5語）を出す。「次から聞かない」を選べる。メンバーの側で組織の鍵を確かめる手段はない |
| メンバーを外した後 | Vault 鍵を作り直し、残る全員に包み直す。1リクエスト・1バッチで行う | 組織の鍵を作り直す機能がない（2024年の時点。Bitwarden のコミュニティの回答と、Vaultwarden の CVE-2024-39925） |
| 古い形式 | 未知の形式とアルゴリズム ID を拒否する（C-10） | 認証のない AES-CBC の古い形式も読めるようにしていた（論文 BW11・BW12。報告の後に直した） |
| 自動入力 | ポップアップから押したときだけ。トップフレームだけ、オリジンの完全一致 | ページ内の入力候補のメニュー、ページを開いたときの自動入力（既定では切）がある |
| サーバー | Cloudflare Workers ＋ D1（無料プラン） | 自社のクラウドか、自分で立てる（オープンソース） |

## 2. 論文の攻撃を teampw に当てはめる

論文は、サーバーが乗っ取られて悪意を持って動く場合を考え、Bitwarden への攻撃を12件示した。teampw の脅威モデルも「D1 や Cloudflare アカウントが漏れても中身を読ませない」なので、同じ条件で比べられる。

| 論文 | 攻撃の中身 | teampw では | 根拠 |
|---|---|---|---|
| BW01 Malicious Auto-Enrolment | 組織に参加したとき、サーバーが偽の組織の公開鍵と「回復に自動で登録」の設定を返し、利用者の鍵を包ませて取る | 当てはまらない。アカウントの回復（鍵の預け先）の機能がない | 仕様書の「MVPの範囲外」 |
| BW02 Malicious Key Rotation | 鍵を作り直すとき、同じように偽の公開鍵で新しい鍵を包ませる | 当てはまらない。メンバーの秘密鍵をほかの鍵で包んで送る処理がない | 同上 |
| BW03 Malicious KC Conversion | Key Connector（鍵を預ける機能）への切り替えで、マスターキーを取る | 当てはまらない。鍵を預ける機能がない | 同上 |
| BW04 Unprotected Item Metadata | 暗号化していない項目（種類など）を読み書きされる | 一部は当てはまる。アイテム ID、リビジョン、世代、作った人、日時は平文で、サーバーは読める。ただし、書き換えると AAD が合わず復号に失敗する（リビジョン、世代、ID）。作った人と日時は守っていない | C-03〜C-05、S-11 |
| BW05 Item Field Swapping | 欄の暗号文を、ほかの欄やほかのアイテムと入れ替える | 当てはまらない。アイテムは1つの暗号文で、AAD にアイテム ID がある | C-04 |
| BW06 Icon URL Item Decryption | パスワードの暗号文を URL の欄に移し、アイコンの取得で平文を送らせる | 当てはまらない。欄ごとの暗号文がなく、アイコンも取得しない | C-04 |
| BW07 Remove KDF Iterations | サーバーが反復回数を減らして返し、総当たりを楽にする | 当てはまらない。クライアントが60万回の下限を持ち、重い計算の前に拒否する | C-14 |
| BW08 Organisation Injection | 利用者を勝手に組織に入れる | 当てはまらない。グラントは管理者署名がないと開かない。署名は、照合して固定した管理者の署名用公開鍵で確かめる | C-17〜C-20、P-07 |
| BW09 Organisation Overwrite | 作ったばかりの組織の鍵を、攻撃者の鍵に入れ替える | 当てはまらない。同上。さらに、端末は最後に見た世代より古いグラントを拒否する | C-23、P-08 |
| BW10 Disable Per-Item Keys | アイテムごとの鍵を使わない形に下げる | 当てはまらない。切り替えられる暗号の形がない | C-10 |
| BW11 User Key Overwriting | 認証のない CBC の形式を使って、鍵を偽る | 当てはまらない。AES-GCM の1形式だけ | C-03、C-10 |
| BW12 Downgrade to Legacy | 古い鍵の形に戻させ、パディングオラクルで鍵を取る | 当てはまらない。同上 | C-03、C-10 |

論文は対策を5つに分けている。teampw の設計との対応は次のとおり。

| 論文の対策 | 中身 | teampw |
|---|---|---|
| AE | 認証付き暗号だけを使う | AES-256-GCM だけ |
| KS | アイテムや欄ごとに鍵を分ける | Vault 鍵は1つ。代わりに AAD でアイテム ID と世代とリビジョンに結び付け、1件を1つの暗号文にしている。鍵は分けていない |
| AD | 暗号化しない項目も、認証の対象に入れる | リビジョン、世代、ID は AAD に入れている。作った人と日時は入れていない |
| PKA | 公開鍵を確かめる。すぐ打てる対策は、対面などで確かめた公開鍵を保存しておくこと | 双方向の照合と固定（P-01、P-06）。論文の言う対策そのもの |
| SC | 鍵を包むときに署名する | グラントへの管理者署名 |

## 3. teampw のほうが弱い所

| 項目 | 中身 |
|---|---|
| 総当たりへの強さ | Argon2id を選べない。D1 が漏れたとき、マスターパスワードへの総当たりの手間は PBKDF2 60万回分だけ。WebCrypto に Argon2 がないので、依存を増やさずに入れる道がない |
| 監査と実績 | 外部の監査を受けていない。実際の D1 でもまだ動かしていない。Bitwarden は外部の監査を受け、多くの利用者がいる |
| 権限 | 全員が全件を見る。悪意あるメンバーからは守れない。Bitwarden はコレクションで範囲を分けられる |
| 管理者 | 管理者は1人だけ。管理者の端末が乗っ取られると、署名鍵を使われる |
| 対応する環境 | Windows 版 Chrome の拡張機能だけ。スマートフォンやほかのブラウザはない |
| 回復 | マスターパスワードを忘れると戻せない（管理者が包み直すまで使えない）。緊急アクセスもない |
| ロールバック | サーバーが古い版のアイテムを返したり、一部を隠したりすると、防げず検知だけになる。論文が BW10 の対策の後も残ると書いた「古い版の再生」と同じ問題 |
| 機能 | エクスポート、アイテムとしての TOTP、パスキー、送信（Send）がない |

## 4. teampw のほうが強い、または違う所

| 項目 | 中身 |
|---|---|
| 照合を省けない | Bitwarden は管理者が「次から聞かない」を選べ、メンバー側に確かめる手段がない。teampw は双方向で、照合が済むまでグラントを開かない。ただし、見比べずに「一致」を押すことは防げない |
| 組織の鍵の入れ替えを防ぐ | 論文 BW08・BW09 は、teampw では管理者署名と世代の記録で防ぐ |
| 外したメンバーへの対応 | Vault 鍵を作り直す。外した人の端末に残った古いデータは読めるので、実際のサービスのパスワードも変える必要がある |
| サーバーにパスワード由来の値を送らない | ログインは Discord と TOTP で行う。代わりに、Discord のアカウントとロールに頼る |
| 長さを隠す | パディングで、暗号文の長さを5種類にそろえる。Bitwarden は欄ごとの暗号文なので、各欄のおおよその長さが分かる |
| 攻撃面を作らない | ページ内の UI、iframe への入力、ページを開いたときの自動入力、エクスポートを作らない |

## 5. 取り入れる候補

採用するかは本人が決める。

| 候補 | 理由 | 注意 |
|---|---|---|
| アイテムの作った人と日時も AAD に入れる | 論文の AD の対策。サーバーが書き換えても気づける | アイテムの形式を v3 に上げる。v2 の暗号文の移行が要る |
| 照合の画面に「省く」を作らない方針を仕様書に明記する | Bitwarden の「次から聞かない」と同じ穴を将来作らないため | 今もない。書いておくだけ |
| Argon2id | 総当たりへの強さ | 依存ゼロの方針と衝突する。仕様書の判断待ちに書く案件 |
