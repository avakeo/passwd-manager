## 1. 何を防ぐか

| 攻撃 | 今（提出版） | この設計の後 |
|---|---|---|
| #1 乗っ取られたサーバーが、宛先の公開鍵だけから偽のグラントを作り、行を差し替える | 受け手は本物と区別できずに開く（テスト「既知の弱点（範囲外）」で成功を確認済み） | 受け手は、固定した管理者の署名用公開鍵で署名を確かめる。サーバーは署名鍵を持たないので、通る署名を作れない |
| #7 サーバーが古い世代のグラントを返し、古い Vault 鍵を使わせる | 受け手は期待する世代を知らず、そのまま使う | 世代を署名の対象に入れ、端末は最後に見た世代より古いグラントを拒否する |
| サーバーが管理者自身宛てのグラントを差し替える | 管理者は偽の Vault 鍵で全アイテムを暗号化し、全員に包んで配ってしまう | 管理者の端末も、自分宛てのグラントの署名を確かめてから開く |

前提はレビューと同じ。攻撃者はサーバー（D1 と Workers）を乗っ取り、保存されたデータと API の応答を自由に書き換えられる。端末とマスターパスワードは攻撃者の手にない。

## 2. 鍵と保存形式

### 2.1 管理者の署名鍵ペア

| 項目 | 決め事 |
|---|---|
| 方式 | ECDSA、曲線 P-256、ハッシュ SHA-256（WebCrypto の `{ name: 'ECDSA', namedCurve: 'P-256' }`、署名と検証は `{ name: 'ECDSA', hash: 'SHA-256' }`） |
| ECDH の鍵との関係 | 別の鍵ペアにする。同じ秘密鍵を鍵交換と署名の両方に使わない |
| 置き場所 | 管理者の ECDH の鍵と同じ member_keys の行。鍵 ID も同じものを使う（再登録で一緒に変わり、固定する組も1つの鍵 ID で済む） |
| 公開鍵 | `ecdsa_public_key`：非圧縮形式の65バイトを base64url で保存。管理者以外は NULL |
| 秘密鍵 | `encrypted_sign_private_key`：PKCS#8 で書き出し、署名鍵のラップ鍵で AES-256-GCM により暗号化。管理者以外は NULL |
| ロック解除後 | 取り出し不可（`extractable: false`、用途は `sign` だけ）で読み込む |

### 2.2 署名鍵のラップ鍵

- マスターキーから HKDF-SHA256 で派生させる。ソルトは空、info は `teampw/v1/sign-key-wrap`。
- ECDH の秘密鍵用のラップ鍵（info `teampw/v1/private-key-wrap`）とは分ける。計画書（MVP実装計画.md 1章）は「ラップ鍵で暗号化」と書いているが、CLAUDE.md の「用途別の鍵は HKDF で派生させる」に合わせて別のラベルにした。AAD の種別でも区別はできるが、鍵そのものを分けておけば、片方の用途の誤りがもう片方に波及しない。
- KDF の種類・パラメータ・ソルトは、同じ行のもの（ECDH の秘密鍵と共通）を使う。

### 2.3 署名用秘密鍵の暗号文

| 並び | 長さ |
|---|---|
| 形式 `0x01` | 1B |
| アルゴリズムID `0x01`（AES-256-GCM） | 1B |
| ノンス（乱数） | 12B |
| 暗号文と認証タグ | 可変 |

AAD は UTF-8 の `v1|admin-sign-key|<鍵ID>|<署名用公開鍵（65バイト）の SHA-256 の16進（小文字64桁）>`。

- 種別 `admin-sign-key` が ECDH の秘密鍵の `member-key` と違うので、ECDH の秘密鍵の暗号文を署名鍵の列に移しても開けない（鍵も別なので二重に防ぐ）。
- 署名用公開鍵の SHA-256 を入れるので、サーバーが `ecdsa_public_key` だけを差し替えると、ロック解除に失敗する（C-21）。攻撃者レビュー #3 と同じ考え方。

### 2.4 グラントの署名

vault_key_grants に2列を足す。

| 列 | 中身 |
|---|---|
| `signer_key_id` | 署名した管理者の鍵 ID（平文） |
| `signature` | 形式 `0x01`（1B）、アルゴリズムID `0x03`（1B）、署名（64B）の66バイトを base64url で保存 |

- 署名は WebCrypto が出す IEEE P1363 形式（r と s を32バイトずつ）。DER は使わない。
- アルゴリズムID `0x03` を新しく表に足す（ECDSA P-256、SHA-256）。グラントの wrapped_key に `0x03` が付いている、署名に `0x02` が付いている、などは拒否する（C-10 の範囲を広げる）。
- 長さが66バイトでない、形式やアルゴリズムID が違う、列が空、はどれも「署名がない」と同じ扱いで拒否する（C-17）。

## 3. 署名する中身のバイト列の並び

### 3.1 並び

署名する中身は、次のフィールドを上から順に「長さ（2バイト、ビッグエンディアン）＋値」でつないだもの。全フィールドに長さを付けるので、区切りが曖昧にならない。

| # | フィールド | 値 | 値の長さ |
|---|---|---|---|
| 1 | ラベル | UTF-8 の `teampw/v1/grant-signature` | 25 |
| 2 | 形式 | `0x01` | 1 |
| 3 | グラントのアルゴリズムID | `0x02`（HPKE Base） | 1 |
| 4 | 署名者のメンバーID | UTF-8 | 1〜64 |
| 5 | 署名者の鍵ID | UTF-8 | 1〜64 |
| 6 | Vault 鍵の世代 | 符号なし整数、8バイト、ビッグエンディアン | 8 |
| 7 | 宛先のメンバーID | UTF-8 | 1〜64 |
| 8 | 宛先の鍵ID | UTF-8 | 1〜64 |
| 9 | 宛先の公開鍵（65バイト）の SHA-256 | バイト列 | 32 |
| 10 | 使い捨ての公開鍵（enc） | バイト列 | 65 |
| 11 | wrapped_key | ヘッダー（形式、アルゴリズムID）を含むバイト列 | 50（32バイトの Vault 鍵の場合） |

例：鍵 ID `key_A`（5文字）なら、フィールド5は `00 05 6b 65 79 5f 41`。

### 3.2 決め方の理由

| 決め事 | 理由 |
|---|---|
| ラベルを先頭に入れる | 将来、同じ署名鍵で別のもの（メンバー一覧など）に署名しても、グラントの署名と取り違えないようにする（ドメイン分離）。HPKE の info `teampw/v1/vault-key-grant` とも別の文字列にする |
| 署名者のメンバーID と鍵ID を入れる | メンバーが固定する組（管理者のメンバーID、鍵ID、署名用公開鍵）と1対1に対応させる。管理者が再登録して鍵 ID が変わったら、古い鍵の署名は新しい固定値では通らない |
| 世代を入れる | 世代への署名を兼ねる（5章）。HPKE の info にも世代が入っているが、info は開けるかどうかにしか効かず、署名の外で世代を書き換えた行を「開けない」と「偽物」とで区別できない |
| 宛先のメンバーID・鍵ID・公開鍵のハッシュを入れる | 別のメンバー宛てのグラントの行を、署名ごと自分宛てに付け替えられないようにする。攻撃者レビュー #2（鍵 ID だけを変える）の署名版も防ぐ |
| enc と wrapped_key を入れる | 保存されるバイト列そのものに署名する（暗号化してから署名）。受け手は復号を試す前に検証できる。Vault 鍵の平文や、そのハッシュには署名しない（平文の手がかりを署名の外に出さない） |
| 長さ付きのバイナリにする | アイテムや秘密鍵の AAD は `\|` 区切りの文字列だが、ここには enc や wrapped_key のようなバイナリが入る。16進や base64url に直して区切るより、長さを付けた方が実装の誤りが起きにくい |
| 世代を8バイトにする | `assertVersion` が許す範囲（JavaScript の安全な整数、2^53 − 1 まで）を必ず表せる。`DataView.setBigUint64` で書く |

### 3.3 受け手が組み立てるときの決まり

受け手は、署名する中身を **グラントの行の値ではなく、自分が知っている値から組み立てる**。サーバーが返した値は、署名を確かめた後でも信用しない。

| フィールド | 受け手が使う値 |
|---|---|
| 署名者のメンバーID・鍵ID | 端末に固定した組の値 |
| 世代 | グラントの行の値（ただし、最後に見た世代以上であることを先に確かめる） |
| 宛先のメンバーID | 自分のメンバーID |
| 宛先の鍵ID、公開鍵のハッシュ | ロック解除できた自分の行の値（AAD に公開鍵の SHA-256 が入っているので、サーバーは差し替えられない） |
| enc、wrapped_key | グラントの行の値 |

自分のメンバーID はサーバー（`/v1/me`）から受け取るが、偽られても署名が通らなくなるだけ（開けない）で、偽のグラントを通す方向には使えない。

### 3.4 ECDSA で気をつけること

- ECDSA の署名は一意でない（同じ中身に対して、正しい署名が複数ある）。署名を ID や重複の判定には使わない。検証が通るかどうかだけを見る。
- 署名のノンス（k）は WebCrypto の内部で作られる。自前で署名を組まない。
- 検証には WebCrypto の `verify` を使い、P-256 の公開鍵は `importKey('raw', …)` で読み込む。曲線上にない点は WebCrypto が拒否する。
- 正しい検証の仕方を確かめるため、Project Wycheproof の `ecdsa_secp256r1_sha256_p1363_test.json` を当てる（C-22）。ライセンスは ECDH のベクタと同じ Apache-2.0。テストベクタの追加は依存の追加ではないが、置く前に判断待ちに書いて確かめる。

## 4. 照合と固定の流れ

### 4.1 固定するもの

| 端末 | 固定するもの | 保存先（拡張機能） | 暗号コアに置くもの |
|---|---|---|---|
| 管理者 | 各メンバーの「メンバーID、鍵ID、ECDH の公開鍵」（既存の PinStore） | chrome.storage.local | 既存の `PinStore` |
| メンバー（管理者を含む） | 管理者の「メンバーID、鍵ID、署名用公開鍵」 | chrome.storage.local | 新しい `SignerPinStore`（取得と保存）とメモリ上の実装 |
| メンバー（管理者を含む） | 最後に見た Vault 鍵の世代 | chrome.storage.local | 新しい `GenerationStore`（取得と保存）とメモリ上の実装 |

### 4.2 承認のときの双方向の照合

```
メンバーの端末                     サーバー                     管理者の端末
  │ 鍵を登録（PUT /v1/me/keys）──▶ 承認待ち
  │ GET /v1/me ◀─────────────── 管理者のメンバーID・鍵ID・署名用公開鍵
  │ 「管理者の署名鍵」の                                       │ GET /v1/members
  │  フィンガープリントを表示                                  │ メンバーの公開鍵の
  │                                                            │  フィンガープリントを表示
  │◀────────── 対面・電話で、お互いの画面を見比べる ──────────▶│
  │ 一致を押す → SignerPinStore に固定                         │ 一致を押す → PinStore に固定
  │                                                            │ TOTP の再確認、マスターパスワード
  │                                                            │ グラントを作って署名
  │                              承認とグラントを保存 ◀────────│ POST /v1/members/{id}/approve
  │ GET /v1/vault ◀───────────── 署名付きのグラント
  │ 署名を確かめて開く → 最後に見た世代を保存
```

- 照合を Discord 以外の経路で行うのは、Discord のアカウントが乗っ取られていても照合をすり抜けられないようにするため（既存の方針と同じ）。
- メンバーの画面は、ECDH の公開鍵のフィンガープリントと取り違えないよう、「管理者の署名鍵」と明記する。メンバーの画面には自分の公開鍵のフィンガープリントも出すので、2つを並べて見せる（管理者に見せるのは自分の鍵、管理者から見せてもらうのは署名鍵）。
- 承認待ちのメンバーは `/v1/vault` を呼べない（Z-01）ので、照合用の管理者の鍵は `/v1/me` で返す。
- メンバーが「一致」を押す前にグラントが届いても、開かない（P-04）。

### 4.3 グラントを開くときの確認の順

受け手（管理者を含む）は、次の順で確かめる。1つでも違えば開かずに止め、利用者に警告する。

| 順 | 確かめること | 違うときのエラー |
|---|---|---|
| 1 | 管理者の署名用公開鍵を固定している | `SIGNER_NOT_PINNED`（照合を求める） |
| 2 | グラントの `signer_key_id` が固定した鍵 ID と一致する | `SIGNER_MISMATCH` |
| 3 | `signature` の長さ、形式、アルゴリズムID が正しい | `SIGNATURE_INVALID` |
| 4 | グラントの世代が、最後に見た世代以上 | `STALE_GENERATION` |
| 5 | グラントの宛先の鍵 ID が自分の鍵 ID と一致する | `DECRYPT_FAILED`（今と同じ） |
| 6 | 3.3 の決まりで組み立てた中身に対して、署名が固定した公開鍵で通る | `SIGNATURE_INVALID` |
| 7 | HPKE で開ける | `DECRYPT_FAILED`（今と同じ） |
| 8 | 開けたら、最後に見た世代を max(今の値, グラントの世代) にする | — |

- 署名の失敗を DECRYPT_FAILED にまとめないのは、「壊れている」ではなく「偽物が混ざっている」ことを利用者と管理者に知らせたいため。DECRYPT_FAILED を1つにまとめる理由（C-07：どこを変えれば通るかの手がかりを与えない）は、パスワードの総当たりに関わる話で、署名の検証には当てはまらない。署名の通らない理由（どのフィールドが違うか）までは返さない。
- 署名者の公開鍵は、サーバーが返した値ではなく固定した値を使う。サーバーが `/v1/me` で返す管理者の鍵が固定と違えば、その時点でも警告する（P-05）。

### 4.4 固定が消える・変わるとき

| 場面 | 扱い |
|---|---|
| メンバーが端末を初期化した | 署名鍵の固定と、最後に見た世代が消える。管理者と照合し直すまでグラントを開かない。世代の巻き戻しは、照合し直した後の最初の1回は検知できない（7章） |
| 管理者が再登録した（署名鍵が変わった） | 全メンバーの固定と合わなくなる。全員が照合し直す。新しい署名鍵で作り直したグラントは、照合し直すまで開かない |
| 一時管理者を立てた（管理者がマスターパスワードを忘れた） | 一時管理者が署名鍵ペアを作り、全員がそれを照合して固定し直す。元の管理者に戻したときも、もう一度照合し直す |

## 5. 世代への署名

計画書は「ローテーションで世代が変わるときは、管理者が新しい世代の番号に署名する」としている。この設計では、**グラントの署名の対象に世代を入れることで、これを満たす**。世代だけの独立した署名は作らない。

| 案 | 中身 | 判断 |
|---|---|---|
| A（この設計） | グラントの署名に世代を入れる。端末は最後に見た世代を保存し、古いものを拒否する | 採る |
| B | A に加えて、「世代 N を作った」という独立の署名（世代、前の世代、日時）を vault_key_versions に置く | 採らない |

A で足りる理由：

- メンバーが使う世代は、必ず自分宛てのグラントを通して手に入る。グラントの署名に世代が入っていれば、サーバーは管理者の知らない世代のグラントを作れない（計画書の「サーバーが勝手に世代を作れなくする」）。
- 古い世代への巻き戻しは、署名ではなく端末の記録（最後に見た世代）で防ぐ。古い世代のグラントも本物の署名を持っているので、B の独立の署名があっても、記録がなければ区別できない。
- B を足しても、サーバーが「新しい世代を隠す」ことは防げない（7章）。防ぐには、日時を入れた署名を定期的に出す、ほかのメンバーと世代を見せ合う、などが要り、MVP の範囲を超える。

B が要るのは、将来「メンバー一覧への署名」などで、グラントを持たない人に世代を伝える必要が出たとき。ラベルを分けてあるので、そのときに足せる。

## 6. 管理者が自分宛てに作るグラント

| 場面 | 流れ |
|---|---|
| 初期化 | ①管理者は ECDH の鍵ペアと署名鍵ペアを作り、D1 に登録する。②自分の「メンバーID、鍵ID、ECDH の公開鍵」を PinStore に、「メンバーID、鍵ID、署名用公開鍵」を SignerPinStore に固定する（自分で作った値なので照合は要らない）。③Vault 鍵（世代1）を作り、自分宛てに包んで署名する。④最後に見た世代を1にする |
| 通常の利用 | メンバーと同じく、4.3 の順で確かめてから開く |
| 管理者の端末を初期化した後 | マスターパスワードでロック解除できた自分の行（ECDH の鍵と署名鍵の両方）の公開鍵を、自分の固定値として入れ直す。AAD に公開鍵の SHA-256 が入っているので、サーバーが差し替えた行はロック解除に失敗し、偽の値は入らない。メンバーの固定（PinStore）は、今の仕様どおり全員を照合し直す |

自分宛てのグラントを確かめる理由：管理者は承認とローテーションのときに、自分宛てのグラントから Vault 鍵を取り出して全員に包み直す。サーバーがこの行を偽の Vault 鍵のものに差し替えると、管理者は偽の鍵を自分の署名付きで全員に配ってしまい、署名の意味がなくなる（C-23）。

## 7. ローテーションの流れ

仕様書「メンバーの削除とローテーション」に、署名の確認を足したもの。

| 順 | 管理者の端末 | サーバー |
|---|---|---|
| 1 | マスターパスワードでロック解除（ECDH の秘密鍵、署名用秘密鍵）、TOTP の再確認 | — |
| 2 | Vault リビジョン、全アイテム、有効なメンバーの鍵、自分宛ての現在の世代のグラントを取得 | — |
| 3 | 自分宛てのグラントを 4.3 の順で確かめ、取り出し可として開く（管理操作） | — |
| 4 | 有効なメンバーの鍵を PinStore と照合。1人でも違えば中止 | — |
| 5 | 新しい世代 N+1 の Vault 鍵を作り、全アイテムを再暗号化し、全員分（自分を含む）のグラントを作って署名する | — |
| 6 | 1回のリクエストで送る（POST /v1/vault/rotate） | rotation_guard で確認し、不一致なら全体を巻き戻して 409。署名は検証できない（サーバーは信用しない前提なので、検証しても守りにならない）が、署名の列の長さとヘッダーだけは確かめ、壊れたものは 400 にする |
| 7 | 409 なら 2 からやり直す。グラントと署名は作り直す | — |
| 8 | 成功したら、生の Vault 鍵を wipe し、最後に見た世代を N+1 にする | — |

各メンバーの端末は、次の同期で世代 N+1 のグラントを受け取り、4.3 の順で確かめて開き、最後に見た世代を N+1 にする。以後、世代 N のグラントは受け付けない（C-20）。

## 8. HPKE の Auth モードと比べた理由

RFC 9180 の Auth モード（mode_auth）は、送り手の静的な鍵を鍵交換に混ぜることで、受け手に「この鍵を持つ人が包んだ」と確かめさせる。

| 観点 | 署名（ECDSA）＋ HPKE Base | HPKE Auth |
|---|---|---|
| 確かめられる人 | 管理者の署名用公開鍵を持つ人なら誰でも | 宛先の秘密鍵を持つ人だけ |
| ほかのものへの広げやすさ | 同じ鍵とラベルの切り替えで、世代、将来のメンバー一覧やローテーションの記録にも署名できる | グラント（HPKE で包むもの）にしか使えない |
| 受け手の秘密鍵が漏れたとき | 管理者になりすませない（署名鍵は別） | その受け手に対して、管理者になりすましたグラントを作れる（鍵交換による認証の性質。RFC 9180 9.1.1 節の注意） |
| 鍵の使い分け | 署名専用の鍵を分けられる | 管理者の ECDH の静的鍵を、受け手としても送り手としても使う |
| 今の実装からの差分 | WebCrypto の sign と verify、署名する中身の組み立て、保存形式の列。hpke-core.ts は変えない | hpke-core.ts に AuthEncap と AuthDecap を足す（DH を2回）。C-15 と同じように Auth モードの公開テストベクタを足し、表記の条件も見直す |
| 固定の手間 | 管理者の署名用公開鍵を照合して固定 | 管理者の ECDH の公開鍵を照合して固定（手間は同じ） |
| 世代の巻き戻し | 署名と端末の記録で防ぐ | Auth モードにしても、info に世代を入れて端末の記録と比べる必要は同じ |

署名を選ぶ。決め手は、①グラント以外にも同じ仕組みを広げられること、②受け手の秘密鍵の漏洩が送り手のなりすましにつながらないこと、③今の HPKE の実装（公開テストベクタで確かめた部分）に手を入れずに済むこと。

## 9. 暗号コアの入口

実装した形。案の段階では署名鍵だけを作る `createAdminSignKey` / `unlockAdminSignKey` としていたが、ECDH の鍵と署名鍵を1回の PBKDF2 でまとめて作る・開く形にした。

| 関数 | 変わること |
|---|---|
| `createAdminKey` / `unlockAdminKey`（新規、src/crypto/member-key.ts） | 管理者の ECDH の鍵ペアと署名鍵ペアの生成と暗号化、ロック解除（どちらも取り出し不可。署名鍵の用途は sign だけ）。1回の PBKDF2 から HKDF の2つのラベルでラップ鍵を作る |
| `signMessage` / `verifySignature` / `importSignPublicKey`（新規、src/crypto/signer.ts） | WebCrypto の ECDSA の署名と検証。署名用公開鍵は取り出し不可、用途 verify で読み込む |
| `SignerPinStore` / `GenerationStore` とメモリ上の実装、`assertSignerPinned`（新規、src/crypto/signer.ts） | 管理者の組の固定と、最後に見た世代の記録。サーバーが返す管理者の組を固定と比べる（P-05） |
| `createGrant` | 引数に署名者（メンバーID、鍵ID、署名用秘密鍵）を足す。PinStore と照合 → 包む → 署名、の順。返り値に `signerKeyId` と `signature` を足す |
| `openGrant` / `openGrantForAdmin` | `OwnKey` に自分のメンバーID を足し、引数に `GrantTrust`（`SignerPinStore` と `GenerationStore`）を足す。4.3 の順で確かめる。署名を確かめない開封の入口は作らない |
| `grantSignedMessage`（新規、export する） | 3.1 の並びを組み立てる。既知解テストと、C-19 の「1つずつ書き換える」テストに使う |
| `pinSigner`（新規、src/crypto/signer.ts） | 照合が済んだ管理者の組を SignerPinStore に固定する |

## 11. この設計でも守れないこと

| 項目 | 内容 |
|---|---|
| 新しい世代を隠す | サーバーが世代 N+1 のグラントを隠し、N のまま使わせることは、端末の記録では検知できない。削除されたメンバーが世代 N の鍵を持っているので、その間にメンバーが書いたアイテムは、削除されたメンバーとサーバーが組めば読める。ローテーション後、管理者が全員の端末の世代を対面で確かめる運用で補う |
| 端末を初期化した直後 | 最後に見た世代が消えるので、その直後の1回は古い世代を受け入れてしまう |
| 照合の省略 | メンバーが見比べずに「一致」を押すと、サーバーが差し出した偽の署名鍵を固定してしまう。手順として飛ばせない形（照合が済むまで開かない）にはするが、見比べたかどうかはコードで担保できない |
| 管理者の端末の乗っ取り | 署名鍵を使われると、偽のグラントにも本物の署名が付く。範囲外の「マルウェアに感染したPC」と同じ前提 |
| アイテムの巻き戻し・隠蔽 | アイテムそのものには署名しないので、今の仕様どおり検知のみ（Vault リビジョン） |
