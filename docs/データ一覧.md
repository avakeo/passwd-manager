# データ一覧

チーム用パスワードマネージャーで扱うデータを、1つの論理的なデータにつき1行で整理したもの。暗号化前と後は同じデータの「形」として列で分けて書く。

- A（処理図）では、このデータが箱の中身になる
- B（シーケンス図）では、このデータが矢印の上に書くものになる
- 図では、平文の形と守られた形を別々の箱に描く（置き場所が違うため）

---

## 1. 守るための鍵と中身（E2EE の対象）

| # | データ | 平文の形（置き場所） | 守られた形（置き場所・守る鍵） | 保存 |
|---|---|---|---|---|
| 1 | マスターパスワード | 利用者の頭の中 | なし | 保存しない |
| 2 | パスコード（4桁） | 利用者の頭の中 | なし | 保存しない |
| 3 | マスターキー | 導出した瞬間のメモリ | なし | 保存しない |
| 4 | ラップ鍵 | メモリ（取り出し不可） | なし | 保存しない |
| 5 | パスコード鍵 | メモリ | なし | 保存しない |
| 6 | 秘密鍵 | Service Worker のメモリ（取り出し不可） | D1：ラップ鍵で暗号化 | 暗号化して保存 |
| 7 | 公開鍵 | D1、管理者の端末に固定した値 | 不要（公開してよい） | 平文で保存 |
| 8 | Vault 鍵 | Service Worker のメモリ（取り出し不可） | ① D1：グラント（各メンバーの公開鍵宛てに HPKE で包む）<br>② storage.session：パスコード鍵で暗号化 | 暗号化して保存 |
| 9 | 使い捨て鍵ペア | 包む瞬間のメモリ | 秘密側は破棄、公開側はグラントと一緒に D1 へ | 公開側のみ平文で保存 |
| 10 | アイテム | Service Worker のメモリ。入力時は1件だけ注入スクリプトへ | D1 と端末のキャッシュ：Vault 鍵で暗号化 | 暗号化して保存 |

HPKE の内部で使う共有秘密と包み用の鍵は、A-2 の処理の中だけで生まれて消える一時データなので一覧には入れない。A-2 の図の中だけで描く。

### 各データの生まれ方と使い道

| # | データ | 生まれ方 | 使い道 |
|---|---|---|---|
| 1 | マスターパスワード | 利用者が決める | マスターキーを作る |
| 2 | パスコード | 利用者が決める（端末ごとに任意） | パスコード鍵を作る |
| 3 | マスターキー | PBKDF2（マスターパスワード、ソルト、60万回） | ラップ鍵を作る |
| 4 | ラップ鍵 | HKDF（マスターキー、用途ラベル） | 秘密鍵の暗号化と復号 |
| 5 | パスコード鍵 | PBKDF2（パスコード、端末ごとのソルト） | クイックロック解除用の Vault 鍵の暗号化と復号 |
| 6 | 秘密鍵 | 乱数から生成（P-256） | グラントを開く（ECDH） |
| 7 | 公開鍵 | 秘密鍵 × G | 他のメンバーが Vault 鍵を包む宛先 |
| 8 | Vault 鍵 | 256ビットの乱数。ローテーションで作り直す | アイテムの暗号化と復号 |
| 9 | 使い捨て鍵ペア | 包むたびに乱数から生成 | Vault 鍵を包む（ECDH） |
| 10 | アイテム | 利用者が入力、または CSV インポート | 自動入力、コピー、閲覧 |

### 守りの鎖

保存されて暗号化されているのは、秘密鍵、Vault 鍵、アイテムの3つだけ。この3つは鎖になっている。

マスターパスワード → マスターキー → ラップ鍵 → 秘密鍵 → Vault 鍵 → アイテム

- アイテムは Vault 鍵が守る
- Vault 鍵は秘密鍵が守る（グラント）
- 秘密鍵はラップ鍵が守る
- ラップ鍵はマスターパスワードから作られる

クイックロック解除は、この鎖の途中（Vault 鍵）に、パスコードからの近道を端末ごとに作る仕組み。秘密鍵は近道の先にないため、管理操作には常にマスターパスワードが必要。

### E2EE の確認

一覧の「平文の形」の列に、D1 や Workers が一度も出てこない。出てくるのはメモリ、頭の中、公開してよいものだけ。

## 2. 補助データ（秘密ではない）

| データ | 置き場所 | 使い道 |
|---|---|---|
| ソルト（マスターパスワード用） | D1 | マスターキーを作り直す |
| ソルト（パスコード用） | storage.session | パスコード鍵を作り直す |
| KDF 設定（PBKDF2、60万回） | D1 | 同上。クライアントで下限を確認する |
| ノンス | 暗号文と一緒 | AES-GCM で毎回変える値 |
| AAD の要素（形式、アイテム ID、鍵の世代、アイテムのリビジョン、鍵 ID） | D1 の平文の列 | 暗号文の入れ替え対策。リビジョンは古い暗号文の書き戻しの検知（2026-10-27 追記） |
| フィンガープリント | 公開鍵から毎回計算し、表示するだけ | 承認時の照合 |
| Vault リビジョン | D1、端末（最後に見た値） | ローテーションの競合検出、ロールバック検知 |

秘密ではないが、改ざんされると困るものがある。

- KDF 設定：弱い値にすり替えられないよう、クライアントが下限を確認する
- AAD の要素：書き換えられると復号に失敗するので、改ざんは検知できる
- Vault リビジョン：古い値を返されたら、端末が最後に見た値と比べて警告する

## 3. 認証まわり（E2EE の外。サーバーが扱ってよいもの）

| データ | 置き場所 | 備考 |
|---|---|---|
| Discord の認可コード、state、PKCE | 拡張機能から Workers へ | 一時的 |
| Discord のトークン | Workers の中だけ | 一時的。保存しない |
| クライアントシークレット、Bot トークン、TOTP 暗号化用のサーバー鍵 | Workers のシークレット | D1 には置かない |
| 自前のアクセストークン、リフレッシュトークン | 拡張機能（平文）、D1（ハッシュ） | 15分、7日（仮決定） |
| TOTP シークレット | 認証アプリ、D1（サーバー鍵で暗号化） | サーバーが検証するため E2EE にできない |
| TOTP コード、回復コード | 利用者、D1（回復コードはハッシュ） | 最後に使った時間ステップを記録して再利用を拒否 |

これらが漏れても、アイテムの中身は読めない。復号には、別に守られているマスターパスワードが必要なため。

## 5. 置き場所ごとの一覧

| 置き場所 | 置かれるもの |
|---|---|
| 利用者の頭の中 | マスターパスワード、パスコード |
| 認証アプリ | TOTP シークレット |
| Service Worker のメモリ | 秘密鍵、Vault 鍵、アイテムの平文（いずれもロックで消える） |
| storage.session | パスコード鍵で暗号化した Vault 鍵、パスコード用ソルト、失敗回数 |
| 端末のローカルストレージ | 暗号化したアイテムのキャッシュ、最後に見た Vault リビジョン、承認済み公開鍵の固定値（管理者）、自前のトークン |
| Workers のシークレット | クライアントシークレット、Bot トークン、TOTP 暗号化用のサーバー鍵 |
| D1 | 公開鍵、暗号化した秘密鍵、グラント、暗号化したアイテム、補助データ、トークンのハッシュ、暗号化した TOTP シークレット |
| ミニPC | D1 のバックアップ（D1 と同じ重さで扱う） |
