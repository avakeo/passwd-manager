# 暗号コア実装計画（3つのコードエージェントで作ってレビューする）

暗号コアは、Claude Code が作り、Codex と DeepSeek が別々の観点でレビューする。自分ではコードを書かず、指摘を採用するかどうかの判定を担当する。目的は、面接で「この行は何のためか」を全部自分の言葉で説明できる状態にすること。

---

## 1. 規模

**小さい。** 暗号コアは画面も API も持たず、WebCrypto を呼ぶ処理を正しい順番で並べるだけ。

| 項目 | 目安 |
|---|---|
| まとまり | 6つ（4章の表） |
| 使う暗号の部品 | PBKDF2、HKDF、AES-GCM、ECDH（P-256）の4つだけ。すべて WebCrypto にある |
| 依存 | なし |
| テスト | 提出版で示す7つのうち、暗号コアの4つ（C-03、C-04、C-13、C-15）と P-01 ＋ 追加の C 系 |

一番重いのは手順5の HPKE。RFC 9180 の決まり（ラベルの付け方、鍵スケジュール）に合わせないと、公開テストベクタと一致しない。ここだけはレビューの往復が増える前提で見ておく。

---

## 2. 役割分担

| 役 | 担当 | やること | やらないこと |
|---|---|---|---|
| 作る | Claude Code | 実装とテスト。採用された指摘を受けて直す | 自分の書いたものの合否判定 |
| 仕様の番人 | Codex | 仕様書の決定事項とテスト ID に合っているかを1項目ずつ確認する。テストを自分の環境で流し直す | コードの書き換え |
| 攻撃者 | DeepSeek | 「動くけど危ない」所を探す。攻撃のシナリオと、それを再現する失敗テストの案を出す | 本体のコードの書き換え |
| 判定 | 自分 | 指摘を読んで採用するか決める。2人の意見が割れたら決める | 実装 |

### 決まりごと

- **書くのは Claude Code だけ**：複数が同じコードを書き換えると、誰がどこを変えたか追えなくなる
- **レビュー役はコードを直さない**：指摘は「どこが・なぜ問題か」を文章で返してもらう。直したコードを受け取ると、レビュー役も書く人になってしまう
- **観点を分ける**：Codex は仕様との照合、DeepSeek は攻撃者の目線。同じことを頼むと同じ所を見がちになる
- **作ったモデルと別の会社のモデルにレビューさせる**：同じ癖を持つモデルは同じ所を見落としやすい
- **渡すのは差分と仕様の該当部分だけ**：トークンを抑えるため、リポジトリ全体は渡さない
- **秘密は渡さない**：Workers のシークレット、.dev.vars のような設定ファイル、拡張機能 ID 用の秘密鍵は、どの AI にも渡さない

---

## 3. 共通の観点表

Codex と DeepSeek の両方に渡す。全部「動くけど危ない」種類の間違いで、テストが通っていても残りうる。

| 観点 | 確かめること | 対応する仕様 |
|---|---|---|
| ノンス | AES-GCM のたびに新しい96ビットの乱数を作っているか。使い回しや固定値がないか | C-08 |
| AAD | アイテムには形式・アイテム ID・鍵の世代、秘密鍵には形式・鍵 ID・公開鍵の SHA-256 を付けているか | C-04、C-05 |
| 取り出し不可 | ロック解除後の秘密鍵と Vault 鍵を、取り出し不可で読み込んでいるか | C-16 |
| KDF の下限 | D1 から来た反復回数を、60万回未満なら拒否しているか | C-14 |
| HKDF のラベル | 用途ごとに違うラベルを付けているか（ドメイン分離） | 暗号の決定事項 |
| 公開鍵の固定 | グラントを作る前に、固定値と比べて違えば止めているか | P-01 |
| 乱数 | WebCrypto の乱数生成だけを使っているか | 暗号の決定事項 |
| エラー | 失敗理由（パスワード違いか改ざんか）を外に出し分けていないか | C-07 |

## 4. 進める順番

易しい順に並べている。2026-10-15 の時点で作ったものはまだないので、手順ごとに Claude Code が作ってからレビューに回す。

| 手順 | まとまり | 中身 | 通すテスト | 判定のときに見返す資料 |
|---|---|---|---|---|
| 1 | 共通の土台 | 乱数、バイト列と文字列の変換、保存形式（形式バージョンとアルゴリズム ID を先頭に持つ） | C-10 | 仕様書の暗号・データ仕様 |
| 2 | A-4 アイテム | パディング、AES-256-GCM での暗号化と復号、AAD の組み立て | C-02、C-03、C-04、C-05、C-08、C-09 | 図解スライドの A-4 |
| 3 | A-1 鍵を作る | PBKDF2 → HKDF でラップ鍵、P-256 の鍵ペア生成、秘密鍵を AAD 付きで暗号化 | C-01、C-14 | 図解スライドの A-1、導出と生成ノート |
| 4 | A-3 前半 秘密鍵を開ける | 同じ手順でラップ鍵を作り直し、秘密鍵を復号して取り出し不可で読み込む | C-07、C-16 | 図解スライドの A-3（ステップ1〜6） |
| 5 | A-2 と A-3 後半 グラント | HPKE Base モードで Vault 鍵を包む・開く | C-15、C-13、C-06、C-12 | ECDH と HPKE ノート、図解スライドの A-2 |
| 6 | 公開鍵の固定 | フィンガープリントの計算、固定値の保存と比較、違えば中止 | P-01 | 設計の背景ノート |

### 時期

| 時期 | やること |
|---|---|
| 提出まで（今日） | Claude Code が手順1〜6を順に作り、手順ごとに Codex と DeepSeek にレビューさせる。重大な指摘だけ直して提出する。間に合わない手順は、docs/実装状況.md に「未着手」として残す |
| 提出後 | 残りの指摘を直し、まだないテストを足す。手順5（HPKE）と手順6は、提出版で足りない所をここで仕上げる |

## 5. 1まとまりの回し方

1. **作る**：Claude Code が実装し、テストを通す（すでにあるなら飛ばす）
2. **仕様の照合**：Codex に差分、仕様の該当部分、観点表を渡す
3. **攻撃者の目線**：DeepSeek に同じ差分と観点表を渡す
4. **判定**：2人の指摘を読み、下の「判定の手順」で採用するものを決める
5. **直す**：採用した指摘だけを Claude Code に渡して直させる
6. **確認**：テストが通り、直した所を Codex がもう一度確認したら次のまとまりへ

### 判定の手順

1. 指摘を「仕様違反」「危ない書き方」「好みの問題」の3つに分ける
2. 仕様違反は必ず採用する
3. 危ない書き方は、図解やノートと照らして「どの攻撃が通るのか」を自分で説明できたら採用する。説明できなければ、指摘した AI に攻撃の手順を文章で説明させる
4. 好みの問題は、提出までは採用しない
5. 2人の意見が割れたら、仕様書を正とする。仕様書に書いていなければ、決めた内容を仕様書に足す

---

## 6. 頼み方

### Codex（仕様の番人）に渡すもの

- CLAUDE.md の「暗号」「鍵の管理」の決定事項
- そのまとまりに対応するテスト ID の表
- 差分
- 3章の観点表

頼む内容：

- 決定事項と観点表の各項目について、守れているかを1つずつ「守れている／守れていない／判断できない」で答える
- テスト ID ごとに、そのテストが本当にその内容を確かめているかを確認する（名前だけ合っていて中身が別、をはじく）
- テストを自分の環境で流し、結果を報告する
- 直し方のコードは出さず、どこが・なぜ問題かを文章で返す

### DeepSeek（攻撃者）に渡すもの

- 脅威モデル（仕様書の該当部分）
- 差分
- 3章の観点表

頼む内容：

- 乗っ取られたサーバー（D1 と Workers を自由に書き換えられる攻撃者）の立場で、このコードから秘密を取り出す方法を考える
- 見つけた方法ごとに、手順と、それを再現する失敗テストの内容を文章で書く
- テストは通るが危ない書き方があれば指摘する
- 本体のコードの直し方は出さない

---

## 7. 自分の確認（判定役として）

コードは書かないが、判定するには理解が要る。各まとまりの判定の前に、次の問いに自分の言葉で答える。答えられなければ資料に戻る。

| 手順 | 自分に問うこと |
|---|---|
| 1 | 形式バージョンがないと、将来アルゴリズムを変えるとき何が困るか |
| 2 | ノンスを使い回すと何が起きるか。AAD を付けないと、どの攻撃が通るか |
| 3 | なぜマスターキーをそのまま使わず HKDF を挟むのか。なぜ秘密鍵はパスワードから導出しないのか |
| 4 | パスワードを間違えたとき、なぜサーバーに聞かずに分かるのか。それが攻撃者にも使えるのはなぜか |
| 5 | 管理者が作ったグラントを、管理者自身がもう開けないのはなぜか |
| 6 | 照合を Discord でやってはいけないのはなぜか |

---

## 8. 完了の条件

- 手順1〜6のテストがすべて通る
- 観点表の全項目について、Codex の確認が「守れている」になっている
- DeepSeek が出した攻撃の手順が、すべて「直した」か「範囲外として仕様書に記載した」のどちらかになっている
- 7章の問いに、資料を見ずに答えられる
- README の「暗号コア」と「レビューの進め方」の説明を、自分の言葉で書いてある
