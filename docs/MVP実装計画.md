# MVP 実装計画

提出版（v0.1-submission）の続きとして、仕様書のマイルストーン1〜7（Windows 版 Chrome の MVP）を作る。あわせて、手順5・6のレビューで攻撃者役が見つけた脆弱性を MVP の中で防ぐ。

---

## 1. 前の計画から変わること

| 項目 | 前 | これから |
|---|---|---|
| 管理者署名 | MVP では入れない（コストに見合わない） | **入れる**。攻撃者 #1（偽グラントの差し替え）を防ぐには、受け取る側が「本物の管理者が包んだ」と確かめる仕組みが要るため |
| 公開鍵の照合 | 片方向（管理者がメンバーの鍵を照合） | **双方向**。メンバーも管理者の署名用の公開鍵を照合して固定する。承認時に対面で、お互いの画面を見せ合うだけで済む |
| 固定する値 | 公開鍵だけ | メンバー ID、鍵 ID、公開鍵の組（攻撃者 #2） |
| 秘密鍵の AAD | 形式、鍵 ID | 形式、鍵 ID、自分の公開鍵の SHA-256（攻撃者 #3） |
| 巻き戻しの検知 | 端末が最後に見たリビジョンと比べる | それに加えて、Vault 鍵の世代を管理者が署名する。サーバーが勝手に世代を作れなくする（攻撃者 #7） |
| 進め方 | goal の文に進め方も書いた | **goal には完了の状態だけを書く**。進め方は CLAUDE.md に書く（判定役が進め方まで条件として読んで止まらなくなったため） |

### 管理者署名の形（フェーズ0で設計を固める）

- 管理者は、ECDH の鍵ペアとは別に、署名用の ECDSA P-256 の鍵ペアを持つ。秘密鍵はラップ鍵で暗号化して D1 に置く（AAD は形式、種別 admin-sign-key、鍵 ID、公開鍵の SHA-256）
- グラントを作るとき、管理者は「形式、世代、宛先のメンバー ID、宛先の鍵 ID、宛先の公開鍵の SHA-256、使い捨て公開鍵、包んだ Vault 鍵」に署名する
- メンバーはグラントを開く前に、固定した管理者の公開鍵で署名を確かめる。合わなければ開かずに警告する
- ローテーションで世代が変わるときは、管理者が「新しい世代の番号」に署名する。端末は、最後に見た世代より古いものや、署名のない世代を受け付けない
- 比べる案として HPKE の Auth モードもあるが、署名の方が、グラント以外（世代、将来はメンバー一覧）にも同じ仕組みを広げられるので、署名を勧める

## 2. フェーズ

各フェーズは「ブランチ → PR → レビュー → あなたが merge」で1つずつ進める。フェーズごとに Claude Code の新しいセッションを使うと、文脈が軽く保てる。

| フェーズ | 中身 | 対応する仕様 | あなたの準備 |
|---|---|---|---|
| 0 | レビュー指摘の修正（進行中の PR）、管理者署名と双方向の照合、CLAUDE.md への進め方の追記 | 攻撃者 #1〜#4、#7、Codex #5 | 設計案を読んで判定する |
| 1 | Discord ログイン、Bot によるロール確認、セッション発行、TOTP | マイルストーン1、A 系・Z 系のテスト | Discord のアプリと Bot、Cloudflare の D1 とシークレット（3章） |
| 2 | 拡張機能の土台と、アイテムの一覧・作成・編集・削除、同期と409、ロック解除、クイックロック解除。フェーズ1のレビューから持ち越した1つ：セッションの一覧の端末名は、画面で文字として表示し、HTML として解釈しない（DeepSeek #2） | マイルストーン3、S 系・E 系の一部 | 拡張機能を Chrome に読み込んで触る |
| 3 | 自動入力、クリップボード、パスワード生成、カスタム項目。client-parts のレビューから持ち越した4つ：CSV の重複は「置き換え」を初期値にせず、パスワードが既存と違う重複ははっきり警告してから選ばせる。クリップボードを消す直前に、もう一度中身を読み直してから消す。自動入力の直前に、タブのアドレスと文書 ID をブラウザから取り直して判定に渡し、ページやコンテンツスクリプトからのメッセージで自動入力を始めない（E-08 と E-13 をこの形で必ずテストする）。CSV 由来の値と端末名は、画面で HTML として解釈しない | マイルストーン4、E 系 | 実際のサイトで自動入力を試す |
| 4 | 承認（双方向の照合を含む）、メンバーの削除、ローテーション、Web ページ。PR #2 のレビューから持ち越した3つ：承認画面で「一致」を押すまで固定しない流れを必須にする（DeepSeek #3）、承認とローテーションの API で署名の列の長さとヘッダーを確かめて 400 にする（DeepSeek #9）、フィンガープリントは全部の桁を省略せずに見せる（DeepSeek #13）。フェーズ1のレビューから持ち越した2つ：メンバーの削除やロールの変更など壊す系の管理操作で、1回ごとに TOTP のコードを求めるかを決める（DeepSeek #3）、Web ページのログインでは読み取り専用のトークンを本番の経路で作り、Z-07 のテストもその経路から作る（DeepSeek #4） | マイルストーン5、P 系・S 系・W 系（P-06） | 2台目の端末かブラウザのプロファイルで、メンバー役を作る |
| 5 | CSV インポート | マイルストーン6、I 系 | 手元のパスワードマネージャーから CSV を書き出して試す |
| 6 | 自己診断とレポート | マイルストーン7 | **あなたが自分で診断する**（4章） |

### フェーズ0を最初にする理由

暗号の形（署名、AAD、固定する値）が変わると、その上に作る拡張機能や承認の流れも変わる。土台を先に固めておけば、後から作り直さずに済む。

---

### 並行作業：Codex に部品を作らせる（2026-10-17 追加）

フェーズは前のフェーズに依存するが、拡張機能にもサーバーにも依存しない「部品」は先に作れる。Claude Code がフェーズ1〜2を進める間に、Codex が部品を並行で作る。

| 担当 | 中身 | ブランチと作業場所 |
|---|---|---|
| Claude Code | フェーズ1 → 2 → 4（サーバー、拡張機能の土台、承認とローテーション） | 今のフォルダ。フェーズごとのブランチ |
| Codex | ①パスワード生成（C-11）、②CSV の読み込みと変換（I 系の解析と変換）、③自動入力してよいかの判定（E 系のうち関数で確かめられるもの）、④クリップボードを消す条件の判定、⑤カスタム項目のデータ形式と入力チェック | git の worktree で作った別のフォルダ（../passwd-manager-codex）、ブランチ feat/client-parts |

部品ができると、フェーズ3と5は「部品を拡張機能の画面につなぐ」作業だけになるので、**1つのフェーズ（3+5）にまとめる**。

ぶつからないための決まり：

- Codex が触るのは src/client/ の下の新しいファイルと tests/client/ だけ。仕様書、CLAUDE.md、AGENTS.md、src/crypto、src/api、package.json は触らない
- Codex が決めた仕様にない決めごとは、仕様書ではなく docs/判断待ち_codex.md に書く。merge のときに、判定してから仕様書に反映する
- 作った AI にはレビューさせない。Codex の PR は Claude Code（仕様の照合）と DeepSeek（攻撃者）がレビューする

### レビューの重さ

| フェーズ | レビュー |
|---|---|
| 1（認証）、2（拡張機能での鍵の扱い）、4（承認とローテーション） | 3つ（仕様の照合、攻撃者、テストの穴） |
| Codex の部品、3+5（画面につなぐ） | 2つ（仕様の照合、攻撃者） |

レビューの結果は、貼り付けではなく docs/review/ にファイルで書かせる（Claude が直接読んで判定する）。

### 往復の目安

| やり方 | 往復の目安 |
|---|---|
| 1本で順に進める | 25〜30 |
| 並行作業、レビューの重さ分け、3+5 の統合 | 12〜15 |

## 3. あなたが用意するもの

AI に秘密の値を見せないため、シークレットの登録はあなたが自分の端末で行う。

| いつ | 用意するもの | 注意 |
|---|---|---|
| フェーズ1 | Discord Developer Portal でアプリを作る。OAuth2 のクライアント ID とシークレット、Bot のトークン、サーバー ID とロール ID | リダイレクト URL は拡張機能の ID から決まる（https://＜拡張機能 ID＞.chromiumapp.org/）。拡張機能 ID を固定する鍵はフェーズ1で Claude Code に作り方を聞く |
| フェーズ1 | Cloudflare で wrangler にログインし、D1 のデータベースを作る | wrangler は開発依存として入れる（フェーズ1の準備で承認する） |
| フェーズ1 | シークレットを wrangler の secret コマンドで自分で登録する | 値をチャットや AI に貼らない |
| デプロイ時 | 実際のドメイン | 本物のドメインを書いた wrangler の設定はコミットしない。例の設定だけをコミットする |
| 常に | 拡張機能 ID 固定用の秘密鍵ファイル | .gitignore に入っているか確認する |
| デプロイ時 | ログインの入口（POST /v1/auth/discord、POST /v1/auth/totp、POST /v1/auth/refresh）に、Cloudflare の設定で回数の制限を入れる | フェーズ1のレビュー DeepSeek #7。コードの中の制限は TOTP の失敗の回数だけ |
| デプロイ時 | 本番の設定の戻り先（DISCORD_REDIRECT_URIS）に localhost を入れない | フェーズ1のレビュー DeepSeek #9。localhost は手で確かめる開発用の設定だけに置く |

## 4. 自己診断（フェーズ6）はあなたがやる

ここがポートフォリオで一番価値のある部分。AI に作らせたものを、自分で診断する。

- Burp Suite で拡張機能と API の通信を見て、OAuth（state、PKCE、リダイレクト）、CORS、認可（IDOR）、409 の扱いを試す
- 仕様書のテスト ID と OWASP ASVS の章を対応づけ、自動テストで確かめていない所を手で確かめる
- 見つけたことを、脆弱性診断のレポートの形（概要、再現手順、影響、対策、重大度）で書く
- 今回の攻撃者レビュー #1 のように「設計の穴」を見つけた経緯も書く

## 5. Claude Code に送る文

### 5.1 フェーズ0（進行中の PR が merge された後に送る）

```text
MVP の作業に入る。まず次の3つを、ブランチ feat/admin-signature で行って、PR を作って止まって。

1. CLAUDE.md の「開発の進め方」に、次を追記する。以後のセッションはこれに従う。
   - 作業ごとにブランチを切り、PR で入れる。merge は人が行う
   - テストを先に書いてから実装する。テストが落ちている状態でコミットしない
   - コミットは意味のある1まとまりごと。メッセージは「種類(範囲): 内容 (テスト ID)」
   - 依存の追加、仕様と実装の食い違い、秘密の値が要る作業は、止まらずに docs/判断待ち.md に書いて、ほかを進める
   - シークレット、実際のドメイン名、拡張機能 ID 用の秘密鍵をコミットしない
   - 各フェーズの終わりに docs/review/ にレビュー用の資料を作る

2. 仕様書と CLAUDE.md の決定事項を、docs/MVP実装計画.md の1章のとおりに書き換える。管理者署名を「入れない」から「入れる」に変え、双方向の照合、固定する値の組、秘密鍵の AAD への公開鍵のハッシュ、世代への署名を書く。脅威モデルの範囲外の表から、管理者署名で防げるようになるものを外す。新しいテスト ID（署名のないグラントや、別の鍵で署名したグラントを拒否する、など）を足す。

3. 管理者署名の設計案を docs/設計案_グラントの送り手認証.md に書く。署名する中身のバイト列の並び、鍵の保存形式、照合と固定の流れ、管理者が自分宛てに作るグラントの扱い、ローテーションの流れ、HPKE の Auth モードと比べた理由を書く。コードはまだ書かない。
```

設計案が出たら、Codex・DeepSeek・Copilot に「この設計の穴を探して」と頼み、判定してから次を送る。

```text
/goal ブランチ feat/admin-signature で、docs/設計案_グラントの送り手認証.md と仕様書の新しいテスト ID がすべて実装され、PR が作られていること。最後のターンで次を表示して示す：npm test が終了コード0で全件成功した結果、新しく足したテスト ID ごとの結果の表、攻撃者レビュー #1・#2・#3・#7 の再現テストが「攻撃が失敗する」形で通っていることの表、git status がクリーンであること、PR の URL。または60ターンで止める。
```

```text
フェーズ＜番号＞（＜中身＞）を始める。docs/MVP実装計画.md と仕様書の該当する章を読み、ブランチ＜ブランチ名＞を切って、実装の計画を docs/実装状況.md に書いて止まって。まだ実装しない。私が用意する必要があるもの（シークレット、アカウントの設定、依存の承認）があれば、一覧にして表示して。
```

```text
/goal ブランチ＜ブランチ名＞で、仕様書のマイルストーン＜番号＞の完了条件と、テスト ID ＜対象の ID＞がすべて満たされ、PR が作られていること。最後のターンで次を表示して示す：npm test が終了コード0で全件成功した結果、対象のテスト ID ごとの結果の表、自動テストで確かめられず手で確かめる項目の一覧、git status がクリーンであること、PR の URL。または60ターンで止める。
```

### 5.3 Codex に送る文（並行作業）

```text
このリポジトリで、ほかの作業とぶつからない「部品」を並行して作ってほしい。AGENTS.md の開発の進め方と、docs/MVP実装計画.md の2章「並行作業」に従って。

作業場所：今のフォルダとは別に、git の worktree で ../passwd-manager-codex を作り、main から切ったブランチ feat/client-parts で作業する。今のフォルダでは別の AI がフェーズ1を作っているので、そちらのファイルには触らない。

作るもの（どれも、拡張機能やサーバーに依存しない関数として作る）：

2. CSV の読み込みと、アイテムの形への変換（仕様書の CSV インポートの節、I 系のうち解析と変換の部分）

4. クリップボードを消す条件の判定（1分後、中身が同じときだけ）
5. カスタム項目のデータ形式と入力チェック（パスワード型、日付型を含む。サイズの上限）

決まり：
- 触ってよいのは src/client/ の下の新しいファイルと、tests/client/ だけ。仕様書、AGENTS.md、CLAUDE.md、src/crypto、src/api、package.json は変えない
- 依存を足さない。乱数は WebCrypto の乱数生成だけ
- 仕様に書いていない決めごとは、仕様書を変えずに docs/判断待ち_codex.md に書いて、案どおりに進める
- テストを先に書いてから実装する。部品ごとにコミットする
- テスト名にテスト ID を入れる。関数で確かめられない E 系の項目は、フェーズ3で確かめる項目として一覧にする

終わったら PR を作り、npm test の結果、テスト ID ごとの表、判断待ちの一覧、PR の URL を表示して止まる。
```

## 6. 完了の条件（MVP 全体）

- マイルストーン1〜6が動き、仕様書のテスト ID がすべて通るか、手で確かめた記録がある
- 攻撃者レビュー #1・#2・#3・#7 が、攻撃が失敗するテストで防げていると示せる
- 自己診断のレポートが、README から読める
- 提出版との差分（何を、なぜ変えたか）が README に書いてある
