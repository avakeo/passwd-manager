# Claude Code 用 実装プロンプト

## 使い方

1. Claude Code を auto mode にする（goal は権限モードを変えないので、manual のままだと途中で確認待ちになって止まる）
2. 「その1：準備」を貼って送る。Claude Code は現状を調べて計画を書き、実装せずに止まる
3. 判断待ちが出たら、「その1.5：判断待ちへの回答」を送る（内容は自分の判断で直してよい）。Claude Code は決定事項を仕様書に反映して止まる
4. 問題なければ、「その2：goal」を貼って送る。ここから最後まで自動で進む
5. 終わったら、ステップごとのコミットを単位にして Codex と DeepSeek にレビューさせる（暗号コア実装計画の5章、6章）

goal の判定役は会話に出た内容しか見ない。そのため、テスト結果やコミット一覧を最後に会話へ出させる条件にしてある。

## その1：準備（最初に送る）

```text
これから暗号コアと提出版の残りを実装してもらう。今回は準備だけ行い、実装はまだしないで止まって。

## 読むもの

- docs/暗号コア実装計画.md（進める順番、観点表、テスト ID）
- docs/仕様書.md の「暗号・データ仕様」「テスト」「10月16日の提出版」
- docs/データ一覧.md

## やること

2. テストを実行し、今の結果を記録する
3. 調べた結果を docs/実装状況.md にまとめる。手順ごとに「済み／一部／未着手」、足りないテスト ID、観点表（実装計画の3章）で怪しい所を書く

- まだ実装やテストの追加はしない
- このファイル作成もまだコミットしない
```

## その1.5：判断待ちへの回答（その1 の後に送る）

```text
判断待ちへの回答。決まった項目は docs/判断待ち.md から外し、決定事項として仕様書に反映して c0 のコミットに含めて。

1. ブランチは feat/crypto-core のままでよい。
2. Hono は CLAUDE.md で実行時の依存として許可済みなので、バージョンを固定して入れてよい。API は Hono で書き、テストは Hono の app.request と、node:sqlite を D1 と同じ形で包んだものを使う。wrangler と miniflare は入れない。README に「API のテストは SQLite で行い、実際の D1 では未確認」と書く。
3. typescript を開発依存として1つだけ入れてよい（ロックファイルで固定）。Node の型除去で実行するので、enum、namespace、引数プロパティなど、型除去で動かない書き方は使わない。
4. 案のとおり、HMAC-SHA256 で Extract と Expand を組んでよい。ただし自前の Extract と Expand にも RFC 5869 のテストベクタを当てる（C-01 に含める）。テストベクタ用に使い捨て秘密鍵を外から渡す経路は、固定ノンスと同じ扱いにする。テスト専用の関数に閉じ込め、本番の経路から呼べないようにする。
5. 案のとおり。info に世代と宛先の鍵 ID を入れ、aad は空にする。仕様書の「HKDF に混ぜる」はこれで満たす。
6. 案のとおり。ライセンスが確認できないものは置かず、その旨を実装状況に書く。KEM 0x0010・KDF 0x0001・AEAD 0x0002 の組で確かめられず、付録 A.3 だけで確かめた場合は、仕様書どおり「HPKE を参考にした独自方式」の表記のままにする。
7. 187行目を書き換えてよい。
8. 案のとおり。ID の作り方（乱数のバイト数と文字の表し方）も仕様書に書く。
9. 案のとおり。復号後、長さの値が範囲外なら失敗にする。
10. アイテムと秘密鍵は案のとおり。復号の前に、ヘッダーの形式バイトと AAD の形式が一致することを確かめる。グラントは違う。RFC 9180 ではノンスを鍵スケジュールから作るので、グラントは乱数のノンスを持たない。グラントの wrapped_key は「形式、アルゴリズム ID、暗号文と認証タグ」だけにし、仕様書のデータ設計（vault_key_grants の wrapped_key の「ノンスを含む」）を直す。
11. 計算が合っていない。30バイトから5桁を12組は作れない。30バイトを5バイトずつ6つに分け、それぞれを整数として10万で割った余りを5桁で表す（6組30桁、約100ビット）。比較を公開鍵のバイト列で行うのは案のとおり。
12. 案のとおり。
13. 案のとおり。テスト用の認証はテストからだけ差し込める形にし、本番の入口に固定トークンを置かない。
14. 案のとおり。docs/暗号コア実装計画.md の4章もそう直す。

c0 をコミットする前に、docs に実際のドメイン名や個人のパスが入っていないか確かめる。ここまでやったら止まる。
```

## その2：goal（その1.5 が終わってから送る）

```text
/goal docs/暗号コア実装計画.md の手順1〜6と、提出版の最小 API（仕様書「10月16日の提出版」）を、作業ブランチ feat/crypto-core 上で実装し終えること。

完了の条件（すべてを最後のターンで会話に表示して示す）:
1. package.json の test を実行し、終了コード0で全テストが通った結果を表示する
2. テスト名に次の ID が入ったテストがすべて存在し通っていることを、ID ごとの表で示す: C-01, C-02, C-03, C-04, C-05, C-06, C-07, C-08, C-09, C-10, C-12, C-13, C-14, C-15, C-16, P-01, S-01, Z-01
3. 実装計画の3章の観点表8項目それぞれについて、どのファイルのどこで守っているかを表で示す
4. git log --oneline で、手順ごとに1つ以上のコミットがあることを示す
5. git status がクリーンであることを示す
6. docs/実装状況.md が最終状態に更新され、コミット済みであること

進め方:
- 手順1から順に進める。各手順はテストを先に書き、実装して、テストが通ってからコミットする
- コミットは「1つの手順の中の、意味のある1まとまり」ごとに行う。目安は1手順あたり1〜3コミット。テストが落ちている状態ではコミットしない
- コミットメッセージは「種類(範囲): 内容 (テスト ID)」の形にする。例: feat(crypto): アイテムの AES-GCM 暗号化と AAD (C-02, C-03, C-04)
- 各手順の終わりに docs/review/step-N.md を作り、変更したファイル、対応する仕様の節、テスト ID、観点表で気になる点を書いて、その手順のコミットに含める（後で Codex と DeepSeek にレビューを頼む資料にする）
- HPKE（C-15）は RFC 9180 の公式テストベクタで確かめる。CFRG の test-vectors.json から、KEM 0x0010・KDF 0x0001・AEAD 0x0002 の Base モードを使う。その組が無ければ近い組で KEM と鍵スケジュールを確かめ、そのことを実装状況に書く
- 外部のテストベクタ（HPKE、Wycheproof）は tests/vectors に置き、出典の URL とライセンスを同じ場所に書く

守ること:
- CLAUDE.md の決定事項をすべて守る
- 依存は Hono（実行時）と typescript（開発時）だけ。ほかが必要になったら追加せず docs/判断待ち.md に書き、ほかの作業を続ける
- docs/判断待ち.md で決まった決定事項（グラントは乱数のノンスを持たない、テスト用の差し込み口を本番の経路に置かない、など）に従う
- 時間が足りないときは、提出版の7つのテスト（C-03, C-04, C-13, C-15, P-01, S-01, Z-01）に関わる作業を先にする
- 仕様と実装が食い違ったら、仕様書を書き換えずに docs/判断待ち.md に書き、仕様どおりに実装する
- シークレット、.dev.vars、拡張機能 ID 用の秘密鍵、実際のドメイン名をコミットしない。コミット前に差分を確認する
- main への merge と push はしない
- 判断待ちの項目があっても、それ以外が終われば完了とする。最後に判断待ちの一覧を表示する

または80ターンで止める。止めるときは、どこまで進んだかと残りを docs/実装状況.md に書いてコミットする。
```
