## 暗号・データ仕様

### 概要と確定事項

チーム共通の1つのVaultを、E2EE（サーバーは暗号文しか持たない）で共有するパスワードマネージャーを作る。目的は学習とポートフォリオで、実運用は後回しにする。

**MVPの範囲**：Windows版Chromeの拡張機能、D1とWorkersのAPI、鍵を使わない表示専用のWebページ。Firefox、Safariの順で後から対応する。

**機能**：チームでのログイン情報（メールアドレス、パスワード）の共有、チームメモ、ポップアップからの自動入力、パスワード生成、カスタム項目、CSVインポート。エクスポートは作らない。

| 項目 | 決定内容 |
| --- | --- |
| 暗号化方式 | E2EE。暗号処理はWebCryptoと推奨アルゴリズムのみ |
| Vault | チーム全員で共通の1つ。個人用Vaultは作らない |
| ログイン | Discord OAuth2。認証と認可のみに使い、暗号には使わない |
| 認可 | 特定のDiscordサーバーの特定ロール。Botでロールを再確認する |
| マスターパスワード紛失時 | マスターパスワード自体は復元できない。他の承認済みメンバーがVault鍵を再配布すれば、データへのアクセスは回復できる |
| 管理者 | 1人（自分）。初期登録後の通常のメンバー追加は想定しない（承認フローは初期登録と鍵の再登録で使う） |
| 鍵導出（KDF） | PBKDF2-HMAC-SHA256、60万回以上。後でArgon2idへ移行できる形にする |
| 楕円曲線 | P-256に統一（鍵の受け渡しはECDH、管理者署名はECDSA） |
| 管理者署名 | 入れる。管理者はECDSA P-256の署名鍵ペアを持ち、グラント（Vault鍵の世代を含む）に署名する。受け取る側は、固定した管理者の公開鍵で確かめてから開く（2026-10-17 決定） |
| 公開鍵の照合 | 双方向。承認時にDiscord以外の経路（対面・電話）で、管理者はメンバーの公開鍵の、メンバーは管理者の署名用公開鍵のフィンガープリントを見比べ、それぞれの端末に固定する。公開鍵が変わったら照合し直す |
| パディング | 入れる |
| 監査ログのIP記録 | しない |
| データの置き場所 | D1が唯一の正本。ミニPCはバックアップ専用 |
| 自動入力 | ポップアップ起点のみ。トップフレームのみ、オリジン（https、ホスト名、ポート）の完全一致 |
| 配布 | 身内のみ。ローカルインストール |
| Webページ | 鍵を使わない表示のみ。厳格なCSP、Cloudflareアカウントにハードウェアキーの2FA、デプロイ権限は最小限 |
| API | Workers＋Hono、REST、パスは/v1から |
| ドメイン | Webページ：pw.example.com、API：pw-api.example.com（ドメインは仮の表記） |
| プラン | Workers・D1とも無料プラン。ローテーションは1回のリクエストで完了させる |
| アイテム | ログインとメモの2種類。カスタム項目（テキスト、非表示、日付）あり。TOTPはなし |
| エクスポート | 作らない（CSVインポートのみ） |
| 開発 | TypeScript、公開リポジトリ、実行時の依存はサーバーのHonoのみ |
| 二要素認証 | 認証アプリ（TOTP）。管理者もメンバーも必須 |
| クイックロック解除 | 端末ごとの4桁パスコード。保存はブラウザのメモリ上のみ。管理操作には常にマスターパスワードが必要 |

詳細は別タブにまとめている：API・ドメイン・無料プランの制約は API・インフラ、アイテムの項目・パスワード生成・CSVインポート・画面の分担は アイテムと機能、開発体制・テスト項目・自己診断・マイルストーン・学習資料は 開発・テスト・診断。

### MVPの範囲外

MVPで実装しない機能と、その理由・将来の扱いを明記する。意図的に受け入れたセキュリティ上のリスクは、次章「脅威モデル」の範囲外の表にまとめる。

| 機能 | MVPで実装しない理由 | 将来の扱い |
| --- | --- | --- |
| Firefox・Safari対応 | MVPはWindows版Chromeに限定する | Firefox、Safariの順に対応 |
| エクスポート（CSV・暗号化JSON） | 平文がシステムの外に出る経路を作らない | 暗号化バックアップの取り出し・復元を検討 |
| アイテムとしてのTOTP（他サービスの2FAコード）の保存 | パスワードと同じ場所に置くと二要素の意味が薄れる | 必要になれば検討 |
| ページ内の入力候補UI | クリックジャッキングの攻撃面を作らない | 可視性の検証などを重ねたうえで検討 |
| iframe内への自動入力 | 安全側のデフォルトにする。実装コストが大きい | アイテムごとの許可オリジン |
| オフラインでの編集 | 復帰時の競合解決が難しい | 未定 |
| アイテムの変更履歴 | ローテーション時に再暗号化する対象が増える | 未定 |
| アイテムのロールバック・隠蔽の防止 | E2EEだけでは防げず、完全な対策は大きい | MVPでは検知のみ実施（Vault鍵の世代の巻き戻しは、管理者署名と端末の記録で防ぐ）。将来は署名付き変更履歴など |
| ローテーションの分割実行 | 1回のリクエストで完了できる規模を想定 | 上限を超える規模になったら |
| 複数の管理者 | 管理者1人で運用する | 未定 |
| Google（OIDC）でのログイン | Discordで足りる | 2つ目のログイン手段として追加 |
| Safari向けのログイン引き渡し | SafariにWeb認証フロー起動APIがない | Safari対応時 |
| Argon2id | WebCryptoに無い | PBKDF2から移行 |
| パスキー（WebAuthn PRF）でのロック解除 | MVPの範囲を絞る | 検討 |
| クイックロック解除の生体認証（Windows Helloなど） | MVPでは4桁のパスコードで足りる | パスキーと合わせて検討 |

### 脅威モデル

D1やCloudflareアカウントが漏れても、攻撃者がアイテムの中身を読めないことを最優先で守る。

**守るもの**：アイテムの中身（名前、ユーザー名、パスワード、URL、メモ）、各メンバーの秘密鍵、Vault鍵。

**想定する攻撃者**

- D1のデータを入手した人（漏洩、バックアップの盗難）
- Workers・D1を操作できる人（Cloudflareアカウントの乗っ取り、不正なデプロイ）
- 自動入力を悪用するWebサイト（クリックジャッキング、iframe、XSS、サブドメイン乗っ取り）
- 通信経路上の第三者

**対策の要点**

| 脅威 | 対策 |
| --- | --- |
| 暗号データのオフライン総当たり | 重いKDFと、14文字程度以上のマスターパスワード |
| 公開鍵のすり替え | 承認時に、管理者とメンバーがお互いのフィンガープリントを照合（双方向） |
| 偽Vault鍵の配布（グラントの差し替え） | 管理者がグラントに署名し、受け取る側は固定した管理者の署名用公開鍵で確かめてから開く。署名がない、別の鍵の署名、署名対象の改ざんは、開かずに警告する |
| 自分の公開鍵の差し替え | 秘密鍵のAADに公開鍵のSHA-256を入れ、差し替えた行ではロック解除に失敗させる |
| 暗号文の入れ替え | AADにアイテムIDとVault鍵の世代を入れる |
| 古い暗号文の書き戻し（盗んだトークンで、控えた暗号文を今のリビジョンとしてPUTする） | AADに書き込み後のリビジョンを入れる。サーバーが付けたリビジョンとAADが合わないので、ほかの端末では「読めないアイテム」になる（検知のみ。書き戻しそのものは防げない）（2026-10-27 追記。PR #6 のレビューの DeepSeek #1、判断待ち→案B） |
| 暗号文の長さからの推測 | パディング |
| クリックジャッキング | ページ内UIを作らず、ポップアップからのみ入力 |
| 埋め込みページへの入力 | トップフレームのみに入力し、iframeは無視 |
| 似たドメインやサブドメイン | ホスト名の完全一致、HTTPSのみ |
| セッションの盗用 | 短命のトークン、D1にはハッシュのみ保存、即時無効化 |
| 承認済み公開鍵の後日の差し替え | 管理者の端末に承認済み公開鍵を固定し、グラントを作るたびに照合する。変わっていれば再承認 |
| KDFパラメータの弱体化 | クライアントが下限（PBKDF2は60万回）を持ち、下回る値を拒否する |
| 照合から入力までのページ遷移 | 注入先をタブ・トップフレーム・文書IDで固定し、入力直前にオリジンを再確認する |
| ローテーション中の追加・変更・承認 | Vaultリビジョン、アイテムの集合、メンバーの集合を確認し、1つでも違えば全体を巻き戻す |
| 古いデータの返却 | 端末が最後に見たVaultリビジョンより古ければ警告する（検知のみ） |
| Vault鍵の世代の巻き戻し | 世代を管理者署名の対象に含め、端末は最後に見た世代より古いグラントを受け付けない |
| Webページのトークンの悪用 | Webページ用のトークンは読み取り専用にする |
| Discordアカウントの乗っ取りによるAPIの悪用 | 認証アプリ（TOTP）による二要素認証。全員必須で、管理者は管理操作の直前にも再確認する |

**範囲外（意図的に受け入れたリスク）**

| 項目 | 起こりうること | 受け入れた理由 | 将来の対策 |
| --- | --- | --- | --- |
| ロールバックと隠蔽 | サーバーが古い版のアイテムを返す、一部を返さない。最新の世代のグラントを隠し、古い世代のまま使わせる | 整合した古い状態全体を返された場合は検知できない。Vault鍵の世代は、最後に見た世代より古いもの、サーバーが示す今の世代と食い違うものを拒否し、未設定の端末は照合で初期化するまで開かない。ただし、照合した後にできた新しい世代を、サーバーが「今の世代」ごと隠したことには気づけない（同じ世代を使い続けるのは正常な動きと区別できない） | MVPでは、端末が最後に見たVaultリビジョンより古ければ警告し、Vault鍵の世代は上のとおり拒否する。ローテーションの後、管理者が全員の端末の世代を対面で確かめる。将来は署名付き変更履歴、外部の記録との照合 |
| 管理者の端末と署名鍵 | 管理者の端末がマルウェアに感染すると、署名鍵を使って偽のグラントに署名される | 端末の安全はこのシステムの外。管理者は1人で、署名鍵を分散させない | 複数の管理者による署名 |

| 入力先ページのXSS | 入力した値をページ側のスクリプトに読まれる | 入力先サイトの安全性はこのシステムの外。オリジン一致でも防げない | なし |
| 削除・ロール剥奪されたメンバーの手元の鍵とキャッシュ | 過去に取得したVault鍵と暗号化キャッシュは回収できない。サーバーへのアクセスはアクセストークンの有効期限（15分）まで続く | アクセス権の失効と、渡った秘密の回収は別物 | ローテーションと、実サービス側のパスワード変更 |
| マルウェアに感染したPC | 復号後のデータやマスターパスワードを盗まれる | 端末の安全はこのシステムの外 | なし |
| 悪意あるメンバー | 全アイテムを閲覧できる | 共通Vaultの仕様上、全員が全件を見る | 削除時のローテーションと、実サービス側のパスワード変更 |
| Webページ配信元の改ざん | 配信されるJavaScriptを差し替えられる | Webページは鍵を使わず、トークンも読み取り専用 | なし |
| 悪意ある拡張機能（同じブラウザに入れられた別の拡張機能） | webRequest の権限で API への通信を覗き、Authorization ヘッダーのアクセストークンや、更新の本文のリフレッシュトークンを盗む。debugger の権限で拡張機能の画面に入り、入力したマスターパスワード、TOTPのシークレット、回復コードを読む | マルウェアに感染したPCと同じ前提で、拡張機能の側では防げない（トークンを chrome.storage.session に置いても、送る瞬間は見える。debugger は Chrome が警告を出す）。盗まれたトークンでは平文は読めない（マスターパスワードと鍵は渡らない）が、アイテムの削除・上書きなど API の操作はされうる（PR #5 のレビュー DeepSeek #1・#3） | トークンを端末の鍵に結びつける仕組み（DPoP、RFC 9449）。入れる拡張機能を絞る運用 |

| Discordアカウントの乗っ取り | ログインはされるが、マスターパスワードがなければ復号できない。鍵の再登録は承認待ちになる | 承認時の照合をDiscord以外の経路で行うことで防ぐ | 2つ目のログイン手段 |
| 同じCloudflareアカウントの他サービスによる無料枠の消費 | D1の1日あたりの読み書き行数やWorkersのリクエスト数はアカウント単位。他サービスが使い切ると停止する | 可用性の問題で、機密性には影響しない。オフラインキャッシュで閲覧は続けられる | 専用アカウントへの分離、有料プラン |
| クイックロック解除の総当たり | 端末のメモリ上の保存領域を読まれると、4桁のパスコードは総当たりで破られ、Vault鍵が漏れる | マルウェアに感染したPCと同じ前提。保存はメモリ上のみで、5回の失敗・放置・ブラウザ終了で消える。秘密鍵は保存しない | 生体認証、パスキー |

**サーバーから見えるもの**：アイテムの件数、誰がいつ更新したか、メンバーは誰か。サービス名、URL、パスワードの中身や長さは見えない。

### 鍵階層

復号に必要な鍵はすべて端末の中で導出・展開し、サーバーには暗号文と公開鍵だけが残る。

```
マスターパスワード（利用者が覚える。保存しない）
  │ PBKDF2-SHA256（ソルト、60万回以上）
マスターキー（保存しない）
  │ HKDF（用途ラベル）
ラップ鍵（保存しない・取り出し不可）
  │ AES-256-GCM
秘密鍵（D1 に暗号文で保存） ── 鍵ペア ── 公開鍵（D1 に平文で保存）
  │ ECDH ＋ HPKE でグラントを開く         │ 管理者がこの公開鍵宛てに Vault 鍵を包む
  │                                       │ 包んだグラントに、管理者が署名用秘密鍵で署名する
  │                                       │ （署名用秘密鍵は、HKDF の別ラベルのラップ鍵で暗号化して D1 に保存）
  │ 開く前に、固定した管理者の署名用公開鍵で署名を確かめる
Vault 鍵（チーム共通。メンバーごとにグラントとして D1 に保存）
  │ AES-256-GCM（AAD にアイテム ID）
アイテム（D1 に暗号文で保存。パディング済み）
```

左の列を上から順にたどると、マスターパスワードだけからアイテムまで復号できる。管理者はメンバーの公開鍵を使ってVault鍵を包んで署名し、メンバーは署名を確かめてから自分の秘密鍵でそれを開く。

### 暗号仕様

暗号処理はすべてブラウザのWebCryptoで行い、PBKDF2・HKDF・P-256（ECDH、ECDSA）・AES-256-GCMの組み合わせだけを使う。

#### 鍵導出（KDF）

- マスターパスワードとユーザーごとのソルトから、PBKDF2-HMAC-SHA256でマスターキー（256ビット）を導出する。
- ソルトはWebCryptoの乱数16バイト（128ビット）。鍵ペアの登録時と、マスターパスワードの変更時に新しく作る。
- マスターパスワードは、PBKDF2に渡す前にUnicodeのNFCで正規化してからUTF-8にする（RFC 8265 のOpaqueStringに合わせる）。前後の空白は削らない。合成済みの「が」と「か」＋濁点のように、見た目が同じでバイト列が違う入力を同じ鍵にするため。正規化の方式（`NFC`）もKDFの設定として保存し、クライアントは知らない方式を拒否する。14文字の下限も、正規化した後の文字数で数える。
- OpaqueStringのうち、提出版で実装するのはNFCの正規化だけ。ASCII以外の空白（全角スペースなど）をU+0020に置き換える規則と、使えない文字（制御文字など）の拒否は実装していない（2026-10-16 決定）。
- 反復回数は60万回以上。実機（Windows版Chrome）で計測し、1回の導出が1秒前後に収まる範囲で決める。
- KDFの種類・パラメータ・ソルトはユーザーごとにD1へ平文で保存する。将来Argon2idへ移行するときは、次回のロック解除時に新方式で鍵を作り直す。
- マスターパスワードは14文字程度以上を必須にし、長さだけでなく、推測されにくいパスフレーズ（パスワード生成のパスフレーズ方式で作ったもの）を推奨する。初回は再入力させ、救済がないことを明示する。
- クライアントはKDFパラメータの下限（PBKDF2は60万回）を持ち、サーバーから受け取った値が下限を下回れば拒否する。Argon2idへの移行時に、サーバーが弱いパラメータを指定して再暗号化させる攻撃を防ぐ。

#### 用途別の鍵

- マスターキーからHKDF-SHA256で、用途ごとに別々の鍵を派生させる（ドメイン分離）。
- MVPで使うのは次の2種類。どちらもHKDFのソルトは空。
  - ラップ鍵：自分の秘密鍵（ECDH）を暗号化する。infoは `teampw/v1/private-key-wrap`。
  - 署名鍵のラップ鍵：管理者の署名用秘密鍵を暗号化する。infoは `teampw/v1/sign-key-wrap`。管理者だけが使う。ECDHの秘密鍵用のラップ鍵とは分ける（2026-10-17 決定）。
- 2つの鍵は、1回のPBKDF2で作ったマスターキーから、HKDFのinfoを変えて作る。管理者のロック解除でPBKDF2を2回しないで済む。
- このラベルは、HPKEの内部で使うラベル（RFC 9180の `HPKE-v1` で始まるもの）と重ならないようにする。

#### メンバー鍵ペア

- 各メンバーは、P-256のECDH鍵ペアを端末で1組生成する。
- 公開鍵は平文でD1へ保存する。秘密鍵はラップ鍵とAES-256-GCMで暗号化して保存する。
- 秘密鍵の暗号化にもAADを付ける。AADは「形式（形式バージョンと種別 member-key）、鍵ID、組になる公開鍵のSHA-256」で、バイト列は `v1|member-key|<鍵ID>|<公開鍵（非圧縮形式の65バイト）のSHA-256の16進（小文字64桁）>` のUTF-8。鍵IDは暗号化前にAADへ入れるため、アイテムIDと同じくクライアントで生成する（IDの作り方は「共通の規則」）。別の鍵の行（再登録前の古い鍵など）の暗号文と入れ替えられると、復号に失敗する。サーバーが公開鍵だけを別の点に差し替えた場合も、ロック解除に失敗する。
- フィンガープリントは、公開鍵（非圧縮形式の65バイト）のSHA-256から作る。表示用の文字列の作り方は次のとおりで、保存はしない。
  1. SHA-256の先頭30バイトを、5バイトずつ6つに分ける。
  2. それぞれをビッグエンディアンの整数とみなし、100000で割った余りを、先頭を0で埋めた5桁にする。
  3. 6組の30桁（約100ビット）を、空白で区切って表示する。
- 固定するのは「メンバーID、鍵ID、公開鍵」の組にする。公開鍵が同じでも、鍵IDが固定した値と違えば一致とみなさない。公開鍵を固定値と比べるときは、表示用の文字列ではなく、公開鍵の65バイトそのものを比べる。

#### 管理者の署名鍵ペア

- 管理者は、ECDHの鍵ペアとは別に、署名用のECDSA P-256の鍵ペアを端末で1組生成する。署名はECDSA（ハッシュはSHA-256）で、WebCryptoが出す64バイト（r と s を32バイトずつ並べたもの）をそのまま使う。
- 署名鍵ペアは、管理者のECDHの鍵と同じ member_keys の行に置き、鍵IDも同じものを使う（別の表にはしない。2026-10-17 決定）。再登録ではECDHの鍵と一緒に作り直し、マスターパスワードの変更では一緒に暗号化し直す。
- 署名用秘密鍵は、生成時だけ取り出し可にしてPKCS#8で書き出し、署名鍵のラップ鍵とAES-256-GCMで暗号化する。AADは `v1|admin-sign-key|<鍵ID>|<署名用公開鍵（非圧縮形式の65バイト）のSHA-256の16進（小文字64桁）>` のUTF-8。署名用公開鍵だけを差し替えた行では、ロック解除に失敗する。
- ロック解除後の署名用秘密鍵は取り出し不可で読み込み、署名だけに使う。
- 署名用公開鍵のフィンガープリントは、メンバーの公開鍵と同じ作り方（6組30桁）。画面には「管理者の署名鍵」と明記し、ECDHの公開鍵のフィンガープリントと取り違えないようにする。
- メンバーの端末は、「管理者のメンバーID、鍵ID、署名用公開鍵」の組を固定する。比べるのは65バイトそのもの。固定がないとき、固定と違うときは、グラントを開かない。
- 固定するのと同時に、照合で見比べた「今の世代」で、最後に見た世代を初期化する。最後に見た世代が未設定の端末は、固定していないのと同じ扱いでグラントを開かない（2026-10-17、PR #2 のレビューの DeepSeek #1）。
- 固定と最後に見た世代は、APIの接続先（httpsのオリジン）とメンバーIDの組ごとに分けて保存する。同じブラウザのプロファイルを別のメンバーが使っても、前のメンバーの値は効かない（DeepSeek #4）。
- 最後に見た世代の更新は、保存先の1つの操作（今の値より大きいときだけ上げる）にする。同時に呼ばれても順に処理し、下げる口は作らない（Codex #1）。
- 管理者自身の端末は、ロック解除できた自分の行の署名用公開鍵を正しいものとして使う（AADに公開鍵のSHA-256が入っているので、サーバーが差し替えた行は開けない）。最後に見た世代は、メンバーの端末に出ている世代と対面で見比べて初期化する。初期化するまでは、自分宛てのグラントを開かず、グラントも作らない（承認とローテーションができない。DeepSeek #7）。
- 署名する中身のバイト列、照合と固定の流れの細部は docs/設計案_グラントの送り手認証.md にまとめる。

#### Vault鍵の受け渡し

RFC 9180（HPKE）のBaseモードに準拠して実装する。組み合わせはDHKEM(P-256, HKDF-SHA256)（KEM 0x0010）、HKDF-SHA256（KDF 0x0001）、AES-256-GCM（AEAD 0x0002）。公開テストベクタで適合を確認し、確認できるまでは「HPKEを参考にした独自方式」と表記する。CFRGの test-vectors.json にあるこの組（Baseモード）で一致を確かめた場合だけ「RFC 9180準拠」と書く。別の組（RFCの付録A.3、AES-128-GCM）だけで確かめた場合は、「HPKEを参考にした独自方式」の表記のままにする。部品を組み合わせただけではRFC準拠とは言えないため、鍵スケジュール、エンコード、ノンスの扱いもRFCに従う。流れは次のとおり。

1. 管理者が使い捨てのP-256鍵ペアを生成する。
2. 使い捨ての秘密鍵と、受け取る人の公開鍵でECDHを行い、共有秘密を作る。
3. 共有秘密をHKDFに通して包み用の鍵を作る。HKDFには「Vault鍵の世代」と「宛先の鍵ID」を混ぜる。
4. 包み用の鍵とAES-256-GCMでVault鍵を暗号化する。
5. 使い捨ての公開鍵と暗号文をD1に保存し、使い捨ての秘密鍵は捨てる。

実装上の決まり：

- 手順3の「HKDFに世代と宛先の鍵IDを混ぜる」は、HPKEの `info` を `teampw/v1/vault-key-grant|<Vault鍵の世代>|<宛先の鍵ID>`（UTF-8）にすることで満たす。info は鍵スケジュールに入る。Seal・Openの `aad` は空にする。
- グラントは1つの文脈で1回だけ暗号化する。ノンスはRFCどおり鍵スケジュールから作る（シーケンス番号0）ので、乱数のノンスは持たない。
- WebCryptoのHKDFは、ExtractとExpandを別々に呼べない。そのため、RFC 9180の LabeledExtract と LabeledExpand は、WebCryptoのHMAC-SHA256を使ってRFC 5869どおりに組む。標準の構成なので、独自の暗号プリミティブには当たらない。この自前のExtractとExpandにも、RFC 5869のテストベクタを当てる（C-01に含める）。
- ECDHと点の計算はWebCryptoに任せる。テストベクタを確かめるときの使い捨て秘密鍵は、JWK（d と、pkEm から取った x、y）でWebCryptoに読み込む。
- 使い捨て秘密鍵を外から渡す経路は、固定ノンスと同じ扱いにする。テスト専用の関数に閉じ込め、本番の経路からは呼べないようにする。

HPKEのBaseモードだけでは、受け取る側は「誰が包んだか」を確かめられない。そこで、管理者はグラントを作るたびに署名する。

- 管理者の端末は、承認時に照合した公開鍵を鍵IDと組にして固定しておき、グラントを作るたびにサーバーから受け取った鍵IDと公開鍵の組と一致するかを確認する（鍵の固定）。一致しなければ処理を止めて警告する。
- 照合を通ったら包み、署名する。署名の対象は「形式、署名者のメンバーIDと鍵ID、Vault鍵の世代、宛先のメンバーID、宛先の鍵ID、宛先の公開鍵のSHA-256、使い捨ての公開鍵（enc）、包んだVault鍵（wrapped_key）」。並びは設計案に書く。
- 受け取る側は、開く前に次の順で確かめる。1つでも違えば、開かずに警告する。HPKEで開く処理には、すべて通ってから進む。
  1. グラントの形：使い捨ての公開鍵が65バイト、包んだVault鍵が50バイト（形式、アルゴリズムID、32バイトの鍵、認証タグ）、行のformat_versionが知っている値（v1）。違えば、署名の確認より先に `MALFORMED` か `UNSUPPORTED_FORMAT` にする（DeepSeek #11・#12）。
  2. 管理者の署名用公開鍵を固定し、最後に見た世代も初期化してある。グラントの署名者の鍵IDが、固定した鍵IDと一致する。
  3. グラントの世代が、端末が最後に見た世代以上で、サーバーが `/v1/vault` で示す今の世代と一致する（DeepSeek #2）。
  4. 署名を、固定した署名用公開鍵で確かめる。署名する中身は、グラントの行の値ではなく、固定した署名者、自分のメンバーID、自分の鍵ID、自分の公開鍵のSHA-256から組み立てる。
- どんな形の入力でも、暗号コアは決めたエラー（CryptoError）以外を投げない（C-25）。
- 署名の確認で止めたときは、DECRYPT_FAILEDとは別のエラーにする（2026-10-17 決定）。固定がない `SIGNER_NOT_PINNED`（照合を求める）、署名者の鍵IDや管理者の鍵が固定と違う `SIGNER_MISMATCH`、署名がない・形が違う・通らない `SIGNATURE_INVALID`、最後に見た世代より古い `STALE_GENERATION`、今の世代と食い違う `GENERATION_MISMATCH`。最後に見た世代が未設定のときも `SIGNER_NOT_PINNED`。「壊れている」ではなく「偽物が混ざっている」ことを知らせるため。どのフィールドが違うかまでは返さない。DECRYPT_FAILEDを1つにまとめる理由（C-07）は、パスワードの総当たりに関わる話で、署名の確認には当てはまらない。
- 開けたら、端末が最後に見た世代を更新する（今の値より大きいときだけ上げる）。保存先は、暗号コアにはキーと値のインターフェースとメモリ上の実装だけを置き、拡張機能で chrome.storage.local に差し替える。
- 管理者がグラントを作るときも、管理者自身の端末に、自分の組の固定と最後に見た世代がそろっていなければ作らない。最後に見た世代より古い世代のグラントも作らない。
- 管理者が自分宛てに作るグラントにも署名し、管理者の端末も同じ手順で確かめる。サーバーが管理者宛てのグラントを差し替えると、偽のVault鍵が管理者の署名付きで全員に配られてしまうため。
- 世代への署名は、グラントの署名の対象に世代を入れることで行う。世代だけの独立した署名は作らない（2026-10-17 決定）。サーバーは管理者の署名鍵を持たないので、新しい世代のグラントを作れない。古い世代の巻き戻しは、署名ではなく端末の記録（最後に見た世代）で防ぐ。古い世代のグラントも本物の署名を持つため、独立の署名を足しても区別できない。
- サーバーは署名を検証しない（サーバーは信用しない前提なので、検証しても守りにならない）。承認とローテーションのAPIでは、署名の列の長さとヘッダーだけを確かめ、壊れたものは400にする。

#### アイテムの暗号化

- アイテムの中身（種類、名前、ユーザー名、パスワード、URL、メモ）をまとめて1つのJSONにし、1つの暗号文にする。
- 暗号化の前に、512B、1KB、4KB、16KB、64KBの段階のうち、収まる最小の大きさまでパディングする。
- パディングの方式：先頭4バイトに本体（JSONのUTF-8）の長さをビッグエンディアンで入れ、続けて本体を置き、残りを0で埋める。上限の64KBにはこの4バイトも含めるので、JSONは最大65,532バイト。超える場合、クライアントは暗号化の前に拒否する。APIは、上限を超える本文を413で拒否する。
- 復号後、長さの値が「パディング後の大きさ − 4」を超えていたら、失敗にする。
- AES-256-GCMで暗号化する。ノンスは暗号化のたびに96ビットの乱数を使う。
- AADは「形式バージョン、アイテムID、Vault鍵の世代、リビジョン」で、バイト列は `v2|item|<アイテムID>|<世代>|<リビジョン>` のUTF-8。世代とリビジョンは10進数で書く。暗号文を別のアイテムの場所に移すと、復号に失敗する。
  - 2026-10-27 追記。PR #6 のレビューの DeepSeek #1、判断待ち→案B。前は `v1|item|<アイテムID>|<世代>` で、リビジョンを入れていなかった。そのため、盗んだトークンで控えた古い暗号文を今のリビジョンとして PUT すると、ほかの端末は古い中身を新しい版として出した。
  - リビジョンは、その暗号文を書き込んだ後にサーバーの行が持つ値にする。作成は1、更新は元にしたリビジョン + 1。409 の後に上書きを選んだときも、送るリビジョン + 1 で暗号化し直す。ローテーションの書き換えは、各アイテムのリビジョンを1増やすので、増やした後の値を入れる。
  - 読むときは、サーバーの行の revision で AAD を作り直す。合わなければ、改ざんと区別せずに「読めないアイテム」にする。
  - アイテムの保存形式の形式バイトは 0x02 にする（AAD の `v2` に対応する）。形式バイトが 0x01 のアイテムは、復号を試さずに拒否する。公開前で、保存済みのアイテムがないため、v1 を読む処理は残さない。

#### 共通の規則

- 乱数は必ずWebCryptoの乱数生成を使う。
- 暗号文と鍵の保存形式には、すべて形式バージョンとアルゴリズムIDを持たせる。バイトの並びは次のとおり。

  | 対象 | 並び |
  | --- | --- |
  | アイテム（items.ciphertext）、秘密鍵（member_keys.encrypted_private_key） | 形式（1B）、アルゴリズムID（1B）、ノンス（12B）、暗号文と認証タグ |
  | グラント（vault_key_grants.wrapped_key） | 形式（1B）、アルゴリズムID（1B）、暗号文と認証タグ。ノンスはHPKEの鍵スケジュールから作るので持たない。使い捨ての公開鍵（65B）は別の列（ephemeral_public_key）に置く |
  | 管理者の署名用秘密鍵（member_keys.encrypted_sign_private_key） | 形式（1B）、アルゴリズムID（1B）、ノンス（12B）、暗号文と認証タグ |
  | TOTPのシークレット（members.totp_secret_encrypted、totp_pending_secret_encrypted） | 形式（1B）、アルゴリズムID（1B、0x01 AES-256-GCM）、ノンス（12B）、暗号文と認証タグ。E2EEではなく、Workersのシークレットの鍵で暗号化する（認証・認可フロー > 二要素認証） |
  | グラントの署名（vault_key_grants.signature） | 形式（1B）、アルゴリズムID（1B）、署名（64B） |

  形式の値は 0x01（AADの `v1` に対応する）。アイテムだけは 0x02（AADの `v2` に対応する）（2026-10-27 追記。PR #6 のレビューの DeepSeek #1、判断待ち→案B）。アルゴリズムIDは、保存形式の全体で次の1つの表を使う。

  | アルゴリズムID | 方式 | 使う所 |
  | --- | --- | --- |
  | 0x01 | AES-256-GCM | アイテム、秘密鍵 |
  | 0x02 | HPKE Base（KEM 0x0010・KDF 0x0001・AEAD 0x0002） | グラント |
  | 0x03 | ECDSA P-256、SHA-256（署名は64バイト） | グラントの署名 |

  管理者の署名用秘密鍵の暗号化は AES-256-GCM なので 0x01 を使う。表にない値、または使う所が違う値（アイテムに 0x02 が付いているなど）なら拒否する（C-10）。
- 復号の前に、ヘッダーの形式バイトとAADの形式（`v1`）が一致することを確かめる。一致しなければ、復号を試さずに拒否する。
- アイテムIDと鍵IDは、クライアントでWebCryptoの乱数16バイト（128ビット）を作り、base64url（パディングなし、22文字）で表したものに接頭辞を付ける。接頭辞はアイテムが `item_`、鍵が `key_`。IDとして受け付ける文字は `[A-Za-z0-9_-]` だけで、長さは64文字までにする。AADの区切りの `|` がIDに入らないので、区切りが曖昧にならない。
- メモリ上の鍵は、可能な限り取り出し不可（non-extractable）の鍵オブジェクトとして扱う。
- 既知の入力と期待される出力の組（テストベクタ）を作り、テストで固定する。
- 独自の暗号プリミティブは作らない。

#### 鍵のライフサイクルと取り出し可否

WebCryptoで鍵を包む操作は、内部で鍵を書き出すため、包まれる鍵は取り出し可能でなければならない。そのため、鍵ごとに取り出し可否を切り替える場面を決めておく。

| 鍵 | 生成・取得 | 保存形式 | ロック解除後 | 他メンバーへの配布 |
| --- | --- | --- | --- | --- |
| マスターキー・ラップ鍵 | マスターパスワードから導出 | 保存しない | 取り出し不可 | しない |
| メンバーの秘密鍵 | 生成時のみ取り出し可。PKCS#8で書き出し、ラップ鍵で暗号化（AADは形式、鍵ID、公開鍵のSHA-256） | D1に暗号文 | 取り出し不可で読み込む（鍵交換のみに使う） | しない |
| メンバーの公開鍵 | 秘密鍵と同時に生成 | D1に平文 | — | 公開鍵として配布 |
| 管理者の署名用秘密鍵 | 生成時のみ取り出し可。PKCS#8で書き出し、署名鍵のラップ鍵で暗号化（AADは形式、種別 admin-sign-key、鍵ID、署名用公開鍵のSHA-256） | D1に暗号文 | 取り出し不可で読み込む（署名のみに使う） | しない |
| 管理者の署名用公開鍵 | 署名用秘密鍵と同時に生成 | D1に平文 | — | 公開鍵として配布。メンバーが照合して固定する |
| Vault鍵（通常利用） | 自分宛てのグラントを開いて取得 | D1にグラントとして | 取り出し不可で読み込む | — |
| Vault鍵（管理操作） | 承認・ローテーションのときだけ、グラントを取り出し可として開き直す | 保存しない | 操作が終われば破棄 | HPKEで各メンバー宛てに包む |
| 新しいVault鍵（ローテーション） | 管理者の端末で生成（取り出し可） | 保存しない | 全員分を包んだ後、取り出し不可で読み込み直す | HPKEで各メンバー宛てに包む |
| 使い捨て鍵ペア | 包むたびに生成 | 公開鍵のみD1 | 破棄 | — |
| Vault鍵（クイックロック解除） | マスターパスワードでの解除時に、グラントを取り出し可として開き、パスコード由来の鍵で暗号化 | chrome.storage.sessionのみ（サーバーに送らない） | 復帰時に取り出し不可で読み込む | しない |
| Vault鍵（ロック解除を保つ。2026-10-29 追記） | オンにしたときと、オンの状態でマスターパスワードで解除したときに、グラントを取り出し可として開く | chrome.storage.sessionのみ、暗号化しない（サーバーに送らない） | 復帰時に取り出し不可で読み込む | しない |

取り出し不可は、鍵の中身を書き出されないための仕組みで、拡張機能の中で悪意あるコードが動いた場合に鍵を使われることまでは防げない。

### 鍵とメンバーのライフサイクル

メンバーの登録は初回セットアップと鍵の再登録のときだけで、承認・ローテーションなど暗号を伴う操作は、すべて拡張機能の中の管理画面で行う。

#### 初期化（管理者）

1. 管理者がDiscordでログインし、マスターパスワードを設定する。
2. 管理者のECDHの鍵ペアと署名鍵ペアを生成し、公開鍵と暗号化した秘密鍵をD1に登録する。
3. Vault鍵（世代1）を生成し、管理者自身宛てに包んで署名し、保存する。管理者の端末は、最後に見た世代を1にする。

API（2026-10-17 決定。フェーズ2の判断待ち1）：
- 鍵の登録は PUT /v1/me/keys。公開鍵と暗号化した秘密鍵、KDFの設定を送る。管理者は署名鍵ペアの列も必須、メンバーは送れない。前の鍵は revoked にし、新しい鍵を active にする。
  - すでに有効な鍵がある人の登録し直しは、直近5分以内にTOTPを確かめたセッションだけができる（盗まれたトークンで鍵を差し替えて、承認待ちに落とせないように）。
  - 「有効な鍵があるか」「あれば5分以内にTOTPを確かめたか」「管理者ならグラントがないか」は、保存と同じバッチの先頭で rotation_guard に入れて確かめる。初めての登録を同時に2回送っても、後の方がTOTPの確認なしに前の鍵を無効にできない（PR #5 のレビュー Codex #2）。
  - メンバーが登録し直すと、承認待ちに戻る（P-02）。前の鍵宛てのグラントは使えなくなり、照合と承認をやり直すまで復号できない。
  - 管理者の登録し直しは、グラントがまだ1つもないときだけ（MVPは管理者が1人で、管理者の鍵の作り直しは範囲外）。グラントがあれば409。
- 最初のVaultは POST /v1/vault/init。管理者だけが、直近5分以内にTOTPを確かめたセッションで呼べる。世代1の、管理者自身の有効な鍵宛て・同じ鍵での署名付きのグラントを1つ送る。
  - 「グラントがまだ1つもない」ことの確認と保存は、1つのバッチ（トランザクション）で行う。バッチの先頭で確認の結果を rotation_guard に入れ、グラントがあれば制約違反でバッチ全体を巻き戻して409にする。同時に2回呼んでも、片方しか通らない（P-11）。
  - 同じバッチで、vault_meta（世代1、リビジョン0）と vault_key_versions（世代1）の行がなければ作る。
  - サーバーもグラントの署名を確かめる。署名する中身は暗号コアと同じ関数（grantSignedMessage）で組み立て、登録済みの管理者の署名用公開鍵で検証する。使い捨て公開鍵が曲線上の点かも確かめる。違えば400で何も保存しない（形だけ合わせた偽のグラントで Vault を作らせ、正規の端末が開けないまま作り直せなくなるのを防ぐ。PR #5 のレビュー DeepSeek #2）。ローテーションの API でも同じく確かめる（フェーズ4）。

#### メンバーの参加と承認

1. メンバーがDiscordでログインする（ロールを持っていない人はここで拒否）。
2. マスターパスワードを設定し、鍵ペアを生成して公開鍵を登録する。状態は承認待ちになる。
3. Discord以外の経路（対面・電話）で、お互いの画面を見比べる（双方向の照合）。Discordアカウントが乗っ取られていても照合をすり抜けられないようにするため。
   - 管理者の承認画面には、メンバーの公開鍵のフィンガープリントを表示し、メンバー本人の画面と見比べる。
   - メンバーの画面には、サーバーから受け取った管理者の署名用公開鍵のフィンガープリントと今の世代を表示し、管理者の画面（管理者の端末が持つ、最後に見た世代）と見比べる。一致したら、メンバーの端末は「管理者のメンバーID、鍵ID、署名用公開鍵」の組を固定し、同時にその世代で最後に見た世代を初期化する。
4. 一致したら承認する。承認のリクエストにはそのメンバー宛ての署名付きのグラントを含め、承認とグラントの保存を同時に行う。グラントのない承認状態は作らない。メンバーの端末は、固定した管理者の鍵で署名を確かめてからグラントを開く。
5. 管理者の端末は、照合済みの公開鍵を、メンバーIDと鍵IDとの組で保存して固定する。以降グラントを作るときは、サーバーから受け取った鍵IDと公開鍵が固定した組と一致するかを確認し、どちらかが違えば処理を止めて警告する。提出版は拡張機能がないので、暗号コアには保存先のインターフェース（取得と保存）だけを置き、テストはメモリ上の実装で行う。拡張機能を作るときに chrome.storage.local に差し替える。
6. 公開鍵が変わった場合（再登録など）は自動では信用せず、3から再承認する。管理者が端末を初期化した場合も固定情報が消えるため、全メンバーを照合し直す。
7. メンバーが端末を初期化した場合は、管理者の署名用公開鍵の固定と、最後に見た世代が消える。3と同じ流れ（フィンガープリントと今の世代を見比べ、固定と同時に世代を初期化する）で照合し直すまで、グラントを開かない。管理者の署名鍵が変わった場合（管理者の再登録など）も、全メンバーが照合し直す。
8. 管理者が端末を初期化した場合は、メンバーの端末に出ている世代と対面で見比べ、その値で管理者の端末の最後に見た世代を初期化する。それまでは、承認とローテーションをさせない（グラントを作らない）。

#### メンバーの削除とローテーション

1. 管理者がメンバーを削除し、そのメンバーのセッションを無効にする。
2. 管理者の端末が、Vaultリビジョン、全アイテム、有効なメンバーの公開鍵を取得する。公開鍵は固定した値と照合する。
3. 管理者の端末は、自分宛ての現在の世代のグラントの署名を確かめてから開く。新しい世代のVault鍵を生成し、全アイテムを再暗号化し、有効なメンバー全員分（管理者自身を含む）のグラントを作って署名する。
4. これを1回のリクエストで送る。サーバーは1つのバッチ（トランザクション）の先頭で次をすべて確認し、1つでも違えば、わざと失敗する文を実行してバッチ全体を巻き戻し、409を返す（D1テーブル設計のrotation_guardを参照）。
   - Vaultリビジョンが、管理者が取得したときの値のまま（途中でアイテムの追加・更新・削除がない）
   - 送られたアイテムの集合が、削除されていない全アイテムと一致する
   - グラントの宛先の集合が、有効なメンバーの鍵の集合と一致する（途中で承認・削除がない）
5. 確認が通れば、新しい世代の登録、グラントの保存、全アイテムの書き換え、古いグラントの削除、Vaultリビジョンの更新を同じバッチで行う。
   - 全アイテムの書き換えでは、各アイテムのリビジョンを1増やす。管理者の端末は、増やした後のリビジョンを AAD に入れて暗号化する（2026-10-27 追記。PR #6 のレビューの DeepSeek #1、判断待ち→案B）。
6. 409が返った場合、管理者は最新を取得して2からやり直す。
7. 1回で送れる大きさに上限を設け、超えれば413で拒否する。目安は送信データ1.5MB（ログインアイテムで約1,000件）で、実測して確定する。
8. 抜けたメンバーが見たパスワードは、実サービス側でも変更する。対象を一覧表示する。
9. 各メンバーの端末は、新しい世代のグラントの署名を確かめてから開き、最後に見た世代を更新する。以後、それより古い世代のグラントは受け付けない。

Discordのロールを外されたメンバーは、次のセッション更新時にBotの確認で弾かれる。それまでの間、つまりアクセストークンの有効期限（15分）までは、サーバーへのアクセスが続く。Vault鍵のローテーションは自動では行わず、管理者に通知する。サーバーへのアクセス権を止めても、そのメンバーが過去に取得したVault鍵や暗号化キャッシュは回収できない（アクセス権の失効と、渡った秘密の回収は別物）。

#### マスターパスワードを忘れたメンバー

1. マスターパスワード自体は復元できない。古い鍵を無効にし、新しい鍵ペアで再登録する。
2. 管理者がDiscord以外の経路でフィンガープリントを照合して承認し、Vault鍵を包み直す。チームのデータへのアクセスは回復できる。

#### 管理者がマスターパスワードを忘れた場合

1. D1を直接編集し、別のメンバーを一時的に管理者にする。
2. 管理者が新しい鍵ペア（ECDHの鍵ペアと署名鍵ペア）で再登録する。
3. 一時管理者は署名鍵ペアを作り、全メンバーにその署名用公開鍵を照合し直してもらう。そのうえで、Discord以外の経路でフィンガープリントを照合し、新しい鍵宛てにVault鍵を包み直して署名する。
4. 元の管理者に戻し、一時管理者のロールを外す。管理者の署名鍵が変わったので、全メンバーが元の管理者の新しい署名用公開鍵を照合し直す。

#### マスターパスワードの変更

1. 現在のマスターパスワードで秘密鍵を復号する。管理者は署名用秘密鍵も復号する。
2. 新しいソルトで導出したラップ鍵で、秘密鍵を暗号化し直す。管理者は署名用秘密鍵も、新しいソルトで導出した署名鍵のラップ鍵で暗号化し直す。
3. member_keysの暗号化秘密鍵とKDF情報を、楽観的ロック付きで更新する。

鍵ペアは変わらないため、再承認とローテーションは不要。

#### rotation_guard（ローテーションの検証用）

| 列 | 状態 | 内容 |
| --- | --- | --- |
| ok | 平文 | 「1でなければならない」という制約付きの列 |

条件付きのUPDATEが0件になってもSQLエラーにはならず、バッチは巻き戻らない。そこでローテーションのバッチの先頭で、確認結果（すべて一致なら1、1つでも違えば0）をこの表に挿入する。不一致なら制約違反でバッチ全体が巻き戻る。挿入した行はバッチの最後に削除する。

アイテムの変更履歴テーブルはMVPでは作らない。誤操作からの復旧は、D1の過去時点への復元機能とミニPCのバックアップで代替する。

管理者署名の列（member_keys の ecdsa_public_key と encrypted_sign_private_key、vault_key_grants の signer_key_id と signature）を足したとき、提出版で作った署名のないグラントは移行しない（2026-10-17 決定）。本番のデータがないため、migrations/0001_init.sql をそのまま書き換え、テスト用のデータベースは作り直す。本番を動かし始めた後の変更は、新しいマイグレーションのファイルで足す。

### 認証・認可フロー

ログインはDiscord OAuth2で行い、Workersがロールを確認して自前のセッショントークンを発行する。Discordのトークンとクライアントシークレットは、Workersの外に出さない。

#### ログイン（Chrome拡張機能）

1. 拡張機能がstateを生成し、ブラウザのWeb認証フロー起動API（identity API）でDiscordの認可画面を開く。PKCEも付ける。
2. ユーザーがDiscordでログインし、許可する。
3. Discordが拡張機能専用のリダイレクトURLへ戻す。ブラウザがこれを横取りし、拡張機能に最終URLを返す。
4. 拡張機能がstateの一致を確認し、認可コードとPKCEの検証値をWorkersへ送る。
5. Workersがクライアントシークレットを使ってトークンを交換し、DiscordのユーザーIDとロールを確認する。redirect_uri は、Workersの設定（DISCORD_REDIRECT_URIS）に書いたものだけを受け付け、ほかは400（A-13）。Discordのアクセストークンは、ユーザーIDとロールを確かめるためだけに使い、保存も応答もしない（A-14）。
6. 問題なければ、自前のアクセストークンとリフレッシュトークンを発行する。初めてのログインでは、members に承認待ち（pending）の行を作る。TOTPを登録している人には、先に5分の一時トークンだけを返し、POST /v1/auth/totp でコードを確かめてから発行する（2026-10-17 決定）。

state は拡張機能が作って照合する（サーバーは state を持たない）。A-01 は、拡張機能が使うクライアント側の関数（src/client/discord-login.ts）で確かめる。PKCE の検証値は Discord が照合する。A-02 は、Workersが検証値を Discord に渡し、Discord の拒否を受けてログインを拒否することを確かめる（2026-10-17 決定）。

最初の管理者は、最初のログインの後に `wrangler d1 execute` で自分の行を admin・active に手で書き換えて作る（2026-10-17 決定）。

#### 準備と制約

- 拡張機能IDを固定する。リダイレクトURLに含まれ、Discord Developer Portalへの登録とCORSの設定に使う。
- manifestにidentity権限を入れる。
- Discordアプリの作成と利用は無料。5人規模ならレート制限の心配はない。
- Firefoxは同じAPIがあるが、リダイレクトURLのドメインが異なるため別途登録する。
- SafariはこのAPIが無いため、後で「Webページでログインし、トークンを拡張機能へ引き渡す」方式を足す。認証部分は差し替えられる設計にしておく。

#### 認可とセッション

- 認可条件は「チームのDiscordサーバーで特定のロールを持っていること」と、D1上でメンバーが承認済みであること。
- チームのDiscordサーバーにBotを置く。セッション更新のたびに、WorkersがBotの権限でロールを再確認する。ユーザーごとのDiscordトークンは保存しない。
- アクセストークンは15分、リフレッシュトークンは7日（仮決定。運用して調整する）。ロールを外された人がアクセスできる最大時間は、アクセストークンの有効期限になる。
- 更新（POST /v1/auth/refresh）のたびに、アクセストークンとリフレッシュトークンを新しくし、古いものは使えなくする。使用済みのリフレッシュトークンが来たら、直前のものでなくても、セッションごと無効にする（A-12。2026-10-17 決定。使い終わったものはセッションごとに used_refresh_tokens に覚える）。同じリフレッシュトークンで同時に更新され、条件付きの更新に負けた側も使い回しとみなし、勝った側に発行したトークンも含めてセッションごと無効にする（フェーズ1のレビュー Codex #1）。更新のたびに、Botでロールを確かめ直す（A-04）。
- D1にはトークンのハッシュだけを保存する。セッション表の行を無効にすれば、即時にログアウトさせられる。

#### この端末を覚える（2026-10-29 追記）

ブラウザを閉じるとログインのトークン（chrome.storage.session）が消え、起動のたびに Discord と TOTP からやり直しになるのが手間だったため足した。

1. ログインの直後（TOTPを確かめてから5分以内）に、利用者が4桁のパスコードを決めて「覚える」を押す（POST /v1/me/devices）。過ぎたら TOTP の再確認をしてから。サーバーは端末のトークンを作り、拡張機能は chrome.storage.local に接続先ごとに1つ置く（A-16）。
2. パスコードそのものは送らない。送るのは `v1|device-pin|<接続先>|<メンバーID>|<パスコード>` の SHA-256（pin_proof）。
3. ブラウザを開き直したら、端末のトークンと pin_proof で同じセッションに戻る（POST /v1/auth/resume）。アクセストークンとリフレッシュトークンと端末のトークンを新しくする。前のリフレッシュトークンは使い終わったものとして覚え、使われたらセッションごと無効にする（A-12 と同じ。A-17）。
4. 戻ったセッションは TOTP を確かめた扱いにしない。管理操作とセッションの無効化の前には、今までどおり TOTP の再確認が要る。
5. 間違いの回数はサーバーで数える。確かめる前に回数を1つ増やし（同時に送られても3回まで）、3回間違えたら端末のトークンを無効にする。成功したら0に戻す。手元で数えるだけでは、ディスクを読める人が拡張機能を通さずにトークンを使えるため（A-18）。
6. ログアウト、セッションの無効化、ログインから7日の期限、削除、ロールを外されたときは戻れない。戻るときも、セッションの更新と同じく Bot でロールを確かめる（A-19）。新しくログインしたら、手元の前の端末のトークンは消す。
7. 戻った状態はロックされている。鍵を開くにはマスターパスワードが要る（ロック解除を保つ設定の保存は、ブラウザを閉じたときに消えている）。

トレードオフ：端末のトークンはディスクに置く。端末やプロファイルを盗まれると、7日の間、パスコードを3回まで試される。当てられると API を使える（暗号文の取得、書き込み、削除）が、中身を読むにはマスターパスワードが要る。TOTP は7日に1回になる。
- APIはBearerトークンで認証する。クッキーを使わないので、CSRFの考慮がほぼ不要になる。
- CORSはWebページのオリジン（https://pw.example.com）だけを許可する。CORSは防御機構ではないので、認可はすべてサーバー側で確認する。
- レート制限をかける。
- トークンには用途（拡張機能用／Webページ用）を持たせる。Webページ用は読み取り専用で、書き込みや管理操作のAPIは呼べない。WebページにXSSがあっても、被害を閲覧に限る。
- Webページのログインは、pw.example.comでの通常のリダイレクト方式（state・PKCE付き）で行い、トークンはページのメモリにだけ置く。
- Botの権限は、サーバーメンバーとロールの読み取りに限る。Botトークンが漏れても書き込み操作はできない。
- ログ（Workersのログを含む）に、Authorizationヘッダー、トークン、リクエスト本文を出力しない。

#### 二要素認証（TOTP）

認証アプリ（Proton AuthenticatorなどRFC 6238のTOTPに対応したもの）による二要素認証を入れる。管理者もメンバーも必須（フェーズ1のレビュー DeepSeek #1 で、メンバーの任意をやめた。メンバーのDiscordアカウントを1つ盗むだけで、共有Vaultのアイテムを消したり上書きしたりできたため）。

- **方式**：RFC 6238（HMAC-SHA1、30秒、6桁）。シークレットは乱数20バイト（160ビット）。
- **登録**：サーバーが乱数のシークレットを作る。拡張機能は、otpauth形式のURIとシークレット（base32を4文字ずつ区切る）を文字として表示し、認証アプリで手入力してもらう。QRコードは描かない（依存ゼロで描くと数百行になるため。困ったら後で足す。2026-10-17 決定、フェーズ2の判断待ち2）。シークレットにはコピーのボタンを付けない。表示されたコードを1回入力して登録を確定する。同時に使い捨ての回復コードを発行する。
- **作り直し**：解除はできない。登録済みの人は、今のコードか回復コードを1つ確かめてから、新しいシークレットで登録をやり直せる（POST /v1/me/totp に code か recovery_code を付ける）。認証アプリをなくした人が、回復コードを使い切って締め出されないようにする。使った回復コードは消え、失敗はログインと同じように数える（A-08）。直近5分以内にTOTPを確かめたセッション（回復コードでのログイン直後を含む）なら、コードなしでも始められる。最後の回復コードでログインした人が、作り直しを始めるコードを持たずに締め出されないようにする（フェーズ1の再レビュー Codex #1）。確定するまでは今のシークレットのままで、確定すると回復コードも新しくする。
- **回復コード**：10個。それぞれWebCryptoの乱数10バイト（80ビット）以上から作り、1回だけ使える。D1にはSHA-256だけを置き、使ったものから消す（2026-10-17 決定）。ログインの応答（セッションを発行するもの）と GET /v1/me に、残りの数（recovery_codes_remaining）を入れる。少なくなったら、拡張機能が作り直しを勧める。
- **確認する場面**：Discordログイン後のセッション発行時。管理者は加えて、承認・削除・ロール変更・ローテーションの直前にも再確認する（ステップアップ認証）。再確認の有効時間は5分で、セッションにTOTPを確かめた時刻を持つ（A-10。2026-10-17 決定）。自分の別のセッションの無効化（DELETE /v1/me/sessions/{id}）も、直近5分以内にTOTPを確かめたセッションだけができる。盗まれたトークンで、持ち主の別の端末を締め出せないようにする（A-15。フェーズ1のレビュー DeepSeek #2）。
- **登録前**：TOTPは全員必須。登録するまでは（承認待ち、メンバー、管理者のどれでも）、TOTPの登録（POST /v1/me/totp、POST /v1/me/totp/confirm）とログアウトしかできない。管理操作だけでなく、アイテムやVaultの読み書き、GET /v1/me、セッションの一覧も403にする（A-11）。ログインの応答は、登録していなければ status が totp_setup_required になる。
- **検証**：WorkersでWebCryptoのHMACを使って行う（依存なし）。時刻のずれは前後1ステップまで許容する。最後に使った時間ステップを記録し、同じコードの再利用を拒否する。失敗はレート制限する：メンバーごとに5回まで（A-08。2026-10-17 決定）。TOTPのコードと回復コードを確かめる前に、上限未満のときだけ回数を1つ増やす1つの更新を行い、増やせなければ確かめずに429にする（同時に送られても5回を超えて試せない）。前の試行から15分あくと数え直す。5回目の試行の時刻から15分間は締め出す。成功したら回数を戻す（フェーズ1のレビュー Codex #2）。
- **シークレットの保管**：サーバーが検証に使うためE2EEにはできない。Workersのシークレットに置いた鍵（TOTP_ENCRYPTION_KEY、32バイト）とAES-256-GCMで暗号化してD1に保存する。暗号文の先頭に形式とアルゴリズムIDを持たせ（共通の規則の表）、AADは `v1\|totp-secret\|<メンバーID>`（登録の途中のものは `v1\|totp-pending-secret\|<メンバーID>`）にして、別のメンバーの行への移し替えを防ぐ。鍵の差し替えの仕組みはMVPでは作らない（2026-10-17 決定）。D1だけが漏れた場合は守れるが、サーバー全体を乗っ取られた場合は守れない。
- **効果**：Discordアカウントを乗っ取られても、APIのセッションを得られない。復号はもともとマスターパスワードで守られているため、主に書き込み・削除・管理操作の悪用を防ぐ。

### 拡張機能と自動入力の方針

自動入力はポップアップでの操作を起点に、アドレスバーに表示されたページ本体（トップフレーム）にだけ行う。ページ内に独自のUIは差し込まない。

#### 入力の流れ

1. ユーザーがポップアップでアイテムを選ぶ（またはキーボードショートカットを押す）。キーボードショートカットはフェーズ3では作らない（2026-10-27 決定、フェーズ3の判断待ち3）。
2. バックグラウンドが、ブラウザから渡される「今のタブのURL」とアイテムのURLを照合する。
3. 一致したときだけ、照合したタブ・トップフレーム・文書（ドキュメントID）を指定してスクリプトを注入する。注入したスクリプトは入力直前にもう一度ページのオリジンを確認し、違えば入力しない（照合から入力までの間のページ遷移対策）。

ポップアップでの操作がユーザー操作になるため、今のタブへの一時的な権限で済む。全サイトへのアクセス権限は要求しない。

判定の関数（src/client/autofill-policy.ts）は、ポップアップでの操作の有無、ロックの状態、トップフレームか、タブID、文書ID、入力直前のURLを引数で受け取り、httpsのオリジンを正規化して比べる。これらの値は、呼び出す側（Service Worker）がブラウザから取得して渡す。値の取得元が信頼できるかは、拡張機能の側で確かめる（docs/判断待ち_codex.md #3。2026-10-17 決定）。

#### 入力の条件

- HTTPSのページのみ。HTTPのページには入力しない。
- オリジン（https、ホスト名、ポート）の完全一致。eTLD+1単位での一致は使わない。
- トップフレームのみ。iframe（埋め込まれた別ページ）は無視する。
- 判定に使うURLやオリジンは、ブラウザが付ける送信元情報を使う。ページの自己申告は信用しない。
- 見えていない入力欄には入れない。
- ユーザー名とパスワードが別の画面に分かれるログインでは、見えている欄にだけ入れる。パスワードの画面に移ったら、利用者がもう一度入力を選ぶ。ページの変化を待って続けて入れる処理は作らない（2026-10-27 決定、フェーズ3の判断待ち4）。

#### iframeを無視する理由

- 安全側のデフォルトになる。アドレスバーと違うドメインのページにパスワードが渡る事故を防げる。
- 対応すると、フレームごとの注入、オリジンの二重照合、全サイトへの権限、許可オリジンの設定画面が必要になり、コストが大きい。
- チームの共有アカウントで、ログイン欄がiframe内にあるケースは少ない。入力できない場合はクリップボードコピーで対応する。

#### クリップボードコピー

- 入力できない場面の予備として用意する。
- 1分後に、中身がまだ自分のコピーした値のままなら消去する。中身はオフスクリーンドキュメントで、コピーから60秒後に1回だけ読み直し、消すかどうかの判定だけに使う。そのために clipboardRead の権限を使う（2026-10-27 決定、フェーズ3の判断待ち2）。判定（src/client/clipboard-policy.ts）は、コピーから60,000ミリ秒以上たち、今の中身がコピーした文字列と同じ空でない文字列のときだけ「消してよい」と返す。比べる前に、両方の CRLF を LF にし、末尾の改行を取り除く（docs/判断待ち_codex.md #9。2026-10-17 決定）。
- Windowsのクリップボード履歴やクラウド同期には残る点を、利用者に周知する。

#### URL照合

- オリジンの完全一致で照合する。スキームはhttpsのみ、ホスト名は完全一致でwwwの有無も別扱い（1Passwordと同じ）、ポートも一致を必須とする（省略時は443）。
- 1アイテムに複数のURLを登録できる。
- httpsのURLは、パスやクエリを含めてそのまま保存する。自動入力の判定のときにオリジンを取り出して比べ、パスやクエリは照合に使わない（client-parts のレビューの判定で、「保存するのはオリジンのみ」から変更。docs/判断待ち_codex.md #4。2026-10-17 決定）。

#### 拡張機能の構成

- ポップアップ、Service Worker、入力時だけ注入するスクリプト、クリップボード消去用の補助ページ（オフスクリーンドキュメント）。
- 権限はidentity、storage、今のタブへの一時権限、スクリプト注入、クリップボード書き込み程度に絞る。クリップボードの読み取り（clipboardRead）とオフスクリーンドキュメント（offscreen）も使う（2026-10-27 決定、フェーズ3の判断待ち2）。
- 一覧・検索・編集・パスワード生成・CSVインポートと、暗号を伴う管理操作（承認、ローテーション）は、拡張機能の全画面ページ（タブで開く拡張機能自身のページ）で行う。
- 暗号処理は共通パッケージにまとめる。依存を増やさないため、WXTなどのフレームワークは使わない。manifestは手書きにし、ブラウザごとの差分は小さなビルドスクリプトで吸収する。

#### ロックと鍵の置き場所

- 復号済みの鍵はバックグラウンド側だけで持ち、注入するスクリプトには入力する1件だけを渡す。
- 鍵はService Workerのメモリに、取り出し不可の鍵オブジェクトとして置く。Service Workerは操作がないと30秒程度で停止しうるため、停止後はクイックロック解除（下記）またはマスターパスワードで復帰する。2026-10-29 追記：利用者が「ロック解除を保つ」を選んだときは、入力なしでも復帰する（下記）。
- ロックの条件は、明示的なロック操作、ブラウザの終了、一定時間の放置。ロックするとクイックロック解除とロック解除を保つ設定の保存も消す。
- 放置は45分（2026-10-29 に15分から延ばした。使ってみて、15分ではロックが早すぎたため）。最後の操作の時刻を chrome.storage.session に置き、Service Worker が起きたときと、メッセージを受け取るたびに確かめる。45分を過ぎていれば、その指示を処理する前にロックする。alarms の権限は足さない（2026-10-17 決定、フェーズ2の判断待ち4）。時刻を新しくするのは、利用者の操作から来るメッセージ（画面を開く、ロック解除、アイテムの操作など）だけで、status のような確認だけのメッセージ（同期のポーリングを含む）では新しくしない（PR #5 のレビュー DeepSeek #4）。時間のかかる処理（鍵の導出、通信）は、終わった時点でも放置の時間とロックの有無を確かめ、ロックされていれば鍵を捨てる（Codex #3）。
- 自前のアクセストークンとリフレッシュトークンは chrome.storage.session に置く。Service Worker が止まってもログインは続き、ブラウザを閉じると消える。ポップアップと全画面ページには渡さない（2026-10-17 決定、フェーズ2の判断待ち3）。2026-10-29 追記：「この端末を覚える」を選んだときだけ、戻るための端末のトークンを chrome.storage.local に置く（上記）。
- Service Worker停止後の鍵の状態は、テスト（E-14）で確認する。

#### クイックロック解除（4桁のパスコード）

1. 端末ごとに任意で設定する。最初は必ずマスターパスワードでロックを解除する。
2. 解除できたら、4桁のパスコードからPBKDF2-HMAC-SHA256（60万回。マスターパスワードと同じ下限。2026-10-18 決定、フェーズ2b の判断待ち2）で導出した鍵（端末ごとの乱数ソルト16バイト）でVault鍵を暗号化し、chrome.storage.sessionにだけ保存する。暗号文には形式とアルゴリズムIDを付け、AADは `v1|quick-unlock|<接続先>|<メンバーID>|<鍵の世代>`。サーバーには送らない。秘密鍵は保存しない。
3. Service Workerが停止した後は、パスコードで復号して復帰する。
4. 5回間違えるか、一定時間放置するか、ブラウザを閉じると保存を消し、マスターパスワードに戻る。失敗回数もchrome.storage.sessionで数える。回数は試す前に1つ増やして書き（同時に送られても5回を超えて試せない）、開けたら0に戻す。5回目の失敗で保存をまるごと消す。
5. chrome.storage.sessionは、拡張機能の信頼されたページからだけ読める既定の設定のまま使い、コンテンツスクリプトからは読めないようにする。
6. パスコードで戻った状態は Vault 鍵だけを持ち、秘密鍵は持たない。管理操作（承認、ローテーション）、鍵の作り直し、最初のVault、新しい世代のグラントを開くこと（ローテーションの後）には、常にマスターパスワードを求める（E-17）。

トレードオフ：パスコードで暗号化するため、Vault鍵を一度「取り出し可能な生の鍵」として扱う。また4桁なので、この保存領域を読める攻撃者（端末のメモリを読めるマルウェア）には総当たりで破られる。これは範囲外の「マルウェアに感染したPC」と同じ前提なので受け入れる。

#### ロック解除を保つ（2026-10-29 追記）

使ってみて、Service Worker が止まるたびにマスターパスワードかパスコードを入れるのが手間だったため足した。

1. 端末ごと・メンバーごとに任意で選ぶ。初めはオフ。オンにできるのは、マスターパスワードでロックを解除した状態からだけ。オフにはいつでもできる。
2. オンにすると、グラントを取り出し可として開き直し、生のVault鍵（32バイト）と鍵の世代を chrome.storage.session にだけ置く。暗号化はしない（包む鍵を同じ場所に置くことになり、守りが増えないため）。サーバーには送らない。秘密鍵と署名用秘密鍵は置かない。
3. chrome.storage.local には「オンかオフか」だけを、接続先とメンバー ID の組ごとに置く。オンなら、ブラウザを閉じた後の最初のマスターパスワードでの解除で、保存を置き直す。
4. Service Workerが止まった後は、メッセージを処理する前（放置の確認の後）に、保存から Vault 鍵を取り出し不可として読み込んで復帰する（E-19）。端末が最後に見た世代より古い世代の保存と、形の違う保存では復帰せず、消す。
5. ロック、ログアウト、45分の放置、ブラウザの終了で保存は消える（E-20）。置き場所はクイックロック解除と同じ接頭辞にし、同じロックの処理で消す。
6. 復帰した状態は、パスコードで戻った状態と同じく Vault 鍵だけを持つ。管理操作、鍵の作り直し、最初のVault、パスコードの設定、新しい世代のグラントを開くことには、マスターパスワードを求める（E-17）。

トレードオフ：オンの間は、ブラウザを開いたまま離れると、その端末を触れる人がアイテムをすべて見られる。端末のメモリを読める攻撃者は、パスコードの総当たりなしに Vault 鍵を読める。後者は範囲外の「マルウェアに感染したPC」と同じ前提。前者は利用者が選んだときだけの危険として、設定の画面に書く。

#### 配布

- Chrome：デベロッパーモードでのローカル読み込み。更新は手動配布。
- Firefox：AMOへ非公開で提出し、無料で署名だけもらう。
- Safari：常用には開発者アカウントでの署名が必要。

### データの置き場所とバックアップ

D1を唯一の正本とし、各メンバーPCの暗号化キャッシュとミニPCのバックアップで、オフラインと障害に備える。どこに置くデータも暗号文で、平文になるのは利用者の端末の中だけ。

| 置き場所 | 役割 | 書き込み |
| --- | --- | --- |
| D1 | 唯一の正本 | Workers経由のみ |
| 各メンバーPCの拡張機能 | 暗号化キャッシュ。オフラインでの閲覧・入力・コピー用 | オフライン中は読み取り専用 |
| ミニPC | 定期バックアップ。世代管理する | バックアップの取得のみ |
| D1の過去時点への復元機能 | 誤操作からの短期的な巻き戻し | — |

無料枠（D1の1日あたり読み取り500万行・書き込み10万行、Workersの1日10万リクエスト）はCloudflareアカウント単位で数えられ、2026年9月からD1は超過するとエラーになる。同じドメイン配下の他サービスと同じアカウントで運用する場合、他サービスの利用で枠を使い切ると停止しうる。

#### 同期

- ポップアップを開いたとき、または定期的に、D1から差分を取得する。
- 編集はリビジョン番号による楽観的ロックで行う。古い版を元にした更新はサーバーが拒否し、後勝ちの上書きを防ぐ。
- 削除は論理削除にして、他の端末に「消えた」ことを伝える。
- 端末は最後に見たVaultリビジョンを保存し、サーバーから受け取った値がそれより古ければ同期を止めて警告する（ロールバックの検知。端末を初期化した場合は検知できない）。
- 差分同期は change_seq（書いたときの Vault リビジョン）の索引を使い、全件走査を避ける（D1無料枠の読み取り行数対策）。`GET /v1/items?after=<change_seq>` で、それより大きいものを順に返す。更新日時（ミリ秒）で取ると、同じミリ秒に書かれた2件の片方を取りこぼしうるため（2026-10-18 決定、フェーズ2b の判断待ち1）。
- 端末は暗号文だけを chrome.storage.local にキャッシュする（接続先とメンバー ID の組ごと）。平文の一覧は Service Worker のメモリだけに置き、ロックで消す。unlimitedStorage の権限は足さず、容量（10MB）を超えたらキャッシュをやめてメモリだけで続け、画面で知らせる（2026-10-18 決定、フェーズ2b の判断待ち4）。
- 409 が返ったら自動で送り直さない。同期してサーバーの今の版を取り込み、今の版と自分の入力を並べて「今の版を使う」「自分の内容で上書きする」を利用者に選ばせる。上書きは、利用者が選んだときだけ新しいリビジョンで送る（2026-10-18 決定、フェーズ2b の判断待ち5）。
- 同期（の指示）は、放置のロックの時刻を新しくしない（確認だけの種類として扱う）。

#### ミニPCのバックアップ

- ミニPCがD1から取りに行く向きにする。Cloudflare側からミニPCへの入り口は作らない。
- 中身は暗号文だが、暗号化された秘密鍵とKDFのソルトを含むので、D1の漏洩と同じ重さで扱う。
- ディスクを暗号化し、バックアップを置くディレクトリへのアクセス権を最小限にする。
- ミニPCを2つ目の書き込み先にはしない。
- 復元手順を一度実際に試す。
- D1の過去時点への復元機能は無料プランでは7日間のため、ミニPCへの定期バックアップと併用する。

## API・インフラ

APIはWorkersとHonoで作るRESTで、pw-api.example.com/v1（ドメインは仮の表記） で公開する。無料プランの範囲で、ローテーションも1回のリクエストで完了させる。

### 構成

- Workers＋Hono。HonoはWeb標準のRequest/Responseをそのまま扱うので、「標準Web API中心」の方針と合う。
- サーバーの実行時依存はHonoのみ。
- 認証はBearerトークン。クッキーは使わない。

### 認可

| 操作 | 権限 |
| --- | --- |
| アイテムの閲覧・作成・更新・削除 | 全員 |
| 自分のセッション一覧の確認と無効化 | 全員（自分の分のみ） |
| メンバー一覧の閲覧 | 全員 |
| メンバーの承認・削除・ロール変更 | 管理者のみ |
| Vault鍵のローテーション | 管理者のみ |
| 監査ログの閲覧 | 管理者のみ |

全員が削除できるため、削除は論理削除にして監査ログに残す。唯一の管理者が自分を降格・削除する操作は拒否する。

### エンドポイント

| 区分 | メソッドとパス | 権限 |
| --- | --- | --- |
| 認証 | POST /v1/auth/discord（認可コードを渡す） | 未ログイン |
| 認証 | POST /v1/auth/refresh、POST /v1/auth/logout | ログイン済み |
| 認証 | POST /v1/auth/resume（端末のトークンとパスコードの値で戻る。2026-10-29 追記） | 未ログイン |
| 自分 | POST /v1/me/devices（この端末を覚える。5分以内のTOTPの確認が要る。2026-10-29 追記） | 全員（承認待ちを含む） |
| 自分 | GET /v1/me（自分の鍵、今の世代、照合用の管理者のメンバーID・鍵ID・署名用公開鍵、回復コードの残りの数）、PUT /v1/me/keys（鍵の登録。登録し直しは5分以内のTOTPの確認が要る） | 全員（承認待ちを含む） |
| 自分 | GET /v1/me/sessions、DELETE /v1/me/sessions/{id}（5分以内のTOTPの確認が要る） | 全員 |
| Vault | GET /v1/vault（鍵の世代と、自分宛ての署名付きのグラント） | 全員 |
| Vault | POST /v1/vault/init（最初のVault。グラントが1つもないときだけ。5分以内のTOTPの確認が要る） | 管理者 |
| アイテム | GET /v1/items?after=…（差分同期。change_seq より大きいもの） | 全員 |
| アイテム | POST /v1/items、PUT /v1/items/{id}、DELETE /v1/items/{id} | 全員 |
| インポート | POST /v1/items/import（複数件を一括作成） | 全員 |
| メンバー | GET /v1/members | 全員 |
| メンバー | POST /v1/members/{id}/approve、DELETE /v1/members/{id}、PUT /v1/members/{id}/role | 管理者 |
| ローテーション | POST /v1/vault/rotate | 管理者 |
| 監査ログ | GET /v1/audit-logs | 管理者 |
| 二要素認証 | POST /v1/auth/totp（ログイン時・管理操作前のコード確認） | ログイン済み |
| 二要素認証 | POST /v1/me/totp（登録開始。登録済みなら今のコードか回復コードを付けて作り直し）、POST /v1/me/totp/confirm（登録確定） | 全員（解除はない） |

GET /v1/me が返すのは必要な分だけにする（DeepSeek #5・#10）。拡張機能用のトークンには、自分の鍵を開くのに要る列（署名鍵の列は管理者だけ）。Web用のトークンには、IDと公開鍵だけで、暗号化した秘密鍵（ECDHと署名の両方）とKDFの設定は返さない。照合用の管理者の組はメンバーにだけ返し、有効な管理者の署名鍵がちょうど1つでなければ、どれかを選んで返さずに409にする。

承認APIはそのメンバー宛ての署名付きのグラントを必須とし、承認とグラントの保存を同時に行う。Webページ用のトークンで呼べるのはGETのみで、書き込みと管理操作は403になる。

### エラーと楽観的ロック

エラーはRFC 9457（Problem Details）の形式に揃え、内部の詳細（SQLのエラー文など）は含めない。

| ステータス | 意味 |
| --- | --- |
| 400 | リクエストの形式が不正 |
| 401 | 未ログイン、またはトークン切れ |
| 403 | 権限なし |
| 404 | 対象が存在しない |
| 409 | リビジョンの衝突、IDの重複 |
| 413 | サイズ超過 |
| 429 | レート制限 |

楽観的ロックは、同時編集で他人の変更を黙って上書きしないための仕組み。更新時に「どのリビジョンを元に編集したか」を送り、サーバー上のリビジョンと違えば409で拒否する。クライアントは最新版を取り直し、利用者にもう一度編集してもらう。E2EEではサーバーが中身を読めないので、サーバー側での自動マージはできない。

### バージョン管理

- URLにバージョン（/v1）を入れ、互換性のない変更はv2として追加する。v1はしばらく残す。
- 拡張機能はローカル配布で更新が手動のため、古いクライアントがv1で動き続けられることが特に重要。
- APIのバージョン（通信の約束事）と、暗号文の形式バージョン（データの約束事）は別々に管理する。

### ドメインとCORS

| 用途 | オリジン |
| --- | --- |
| Webページ | https://pw.example.com |
| API | https://pw-api.example.com |

- CORSで許可するのはhttps://pw.example.com の1つだけ。*.example.com のようなワイルドカードは使わない。仲間内の他サービスにXSSがあっても、そこからAPIを呼べないようにする。
- 拡張機能は、manifestでAPIドメインへの権限を宣言し、バックグラウンドからfetchする。CORSの許可リストに拡張機能を入れる必要はない。
- Authorizationヘッダーを使うのでプリフライト（OPTIONS）に応答する。資格情報付きリクエストの許可は不要。オリジンを動的に返す場合はVary: Originを付ける。
- 同じドメイン配下のサービスは別オリジンだが同一サイト扱い。クッキーを使わないので影響は小さい。
- 使用ドメインのDNSに、使われていないサービスを指すレコードが残っていないか確認する（サブドメイン乗っ取り対策）。
- Webページ（メンバー一覧、監査ログ、セッション一覧）はAPIを呼ぶためCORSの許可が必要。ただしWebページ用のトークンは読み取り専用にし、許可の影響を最小にする。

### 無料プランの制約とクエリの抑え方

| 制約 | 値 | 対応 |
| --- | --- | --- |
| 1回の呼び出しあたりのD1クエリ数 | 50 | JSONの一括処理で、ローテーションやインポートも数文に収める |
| D1の文字列・BLOB・1行の上限 | 2MB | 1回で送る暗号文の合計の上限になる。超えたら413 |
| SQL文の長さ | 100KB | 暗号文は必ずバインドする値として渡し、SQL文に埋め込まない |
| Workersの CPU時間 | 10ms | サーバーは暗号処理をしない。大きなJSONの検証時間はステージングで計測する |
| データベースサイズ | 500MB | 十分 |
| 過去時点への復元 | 7日間 | ミニPCへのバックアップと併用 |
| 1日あたりのD1読み取り・書き込み行数 | 500万行・10万行（アカウント単位。2026年9月から超過時はエラー） | 差分同期に索引を使う。同じアカウントの他サービスと共有のため使用量を監視する |

#### JSONによる一括処理

- D1のJSON関数（json_each）で、1つの値としてバインドしたJSON配列を行の集まりに展開し、1つの文で多数の行を作成・更新する。
- 対象はローテーション（全アイテムの書き換え、全メンバー分のグラント）とCSVインポート。
- 通常のAPIは、認証チェック（セッション、メンバー、ロールを1回の結合クエリで取得）を含めて2〜3クエリに収める。

#### ローテーションの1リクエスト化

D1のバッチはSQLのトランザクションとして実行され、途中の文が失敗すると全体が巻き戻る。次の処理を1つのバッチにまとめる。

1. 確認（失敗させる文）：Vaultリビジョンが管理者の取得時のまま、送られたアイテムの集合が削除されていない全アイテムと一致、グラントの宛先の集合が有効なメンバーの鍵の集合と一致。結果をrotation_guard表に挿入し、不一致なら制約違反でバッチ全体を巻き戻して409を返す。
2. 新しい世代の登録
3. 全メンバー分のグラントの書き込み（JSONで1文）
4. 全アイテムの書き換え（JSONで1文）
5. 古いグラントの削除、Vaultリビジョンと管理表の更新、rotation_guardの行の削除

条件付きのUPDATEが0件でもSQLエラーにはならないため、手順1のように制約違反でわざと失敗させないとバッチは巻き戻らない。

1回で送れる大きさの上限は、送信データ1.5MB（ログインアイテムで約1,000件）を目安とし、ステージングで実測して確定する。超える場合は413で拒否する。分割方式は、将来必要になったら追加する。

## アイテムと機能

アイテムはログインとメモの2種類で、ログインには自由なカスタム項目を付けられる。平文がシステムの外に出る経路を作らないため、エクスポートは作らない。

### アイテムの項目

アイテムの中身はすべて1つのJSONにまとめて暗号化する（種類も暗号文の中）。

| 種類 | 項目 |
| --- | --- |
| ログイン | タイトル、ユーザー名（メールアドレス）、パスワード、URL（複数可）、メモ、カスタム項目 |
| メモ（チームメモ） | タイトル、本文 |

JSONの形（src/client/item-data.ts。docs/判断待ち_codex.md #4。2026-10-17 決定）：

- ログインは `type, title, username, password, urls, notes, customFields`、メモは `type, title, body`。
- カスタム項目は `type`（text / hidden / date）、`label`、`value`。日付は厳密な `YYYY-MM-DD`。
- 知らない項目や、文字列であるべき所に文字列以外がある値は拒否し、確かめた値だけで新しいオブジェクトを作る。
- JSONは65,532バイトまで（64KBのパディングの枠から、先頭の長さの4バイトを引いた分）。

#### カスタム項目

| 種類 | 用途の例 | 扱い |
| --- | --- | --- |
| テキスト | 契約番号、担当者名 | 普通に表示 |
| 非表示（パスワード型） | PIN、秘密の質問の答え、APIキー | 伏せ字で表示し、コピー後1分で消去 |
| 日付 | 契約の更新日、パスワードの期限 | 日付として保存・表示 |

- カスタム項目は自動入力に使わず、コピーのみ（1Passwordと同じ方針）。
- 1アイテムあたり20項目程度を上限にする。
- TOTPは入れない。期限が近いアイテムを目立たせる機能は後から足せる。

### Proton Pass・1Passwordとの比較

| 観点 | Proton Pass | 1Password | 今回の設計 |
| --- | --- | --- | --- |
| アイテムの種類 | ログイン、エイリアス、メモ、パスワード、クレジットカード、IDなど | ログインのほか、データベース、サーバー、パスポートなど多数 | ログインとメモの2種類 |
| ログインの項目 | ユーザー名、パスワード、URL（複数可）、2FA、メモ | ユーザー名、パスワード、Webサイト、ワンタイムパスワードなど | ユーザー名、パスワード、URL（複数可）、メモ |
| カスタム項目 | テキスト、2FAシークレット、非表示、日付 | 各種アイテムに追加でき、セクションで整理できる | テキスト、非表示、日付 |
| URL照合 | — | URLごとに自動入力の動作を設定でき、wwwは別ホスト扱い | ホスト名の完全一致、wwwは別ホスト扱い |
| エクスポート | 暗号化JSON、暗号化なしZIP、CSV | — | 作らない |

### サイズとパディング

- 1アイテムの平文は最大64KB。
- パディングは512B、1KB、4KB、16KB、64KBの段階。ログイン情報はほぼ512Bに収まる。
- 上限を超えたら413で拒否する。

### パスワード生成

- 乱数はWebCryptoの乱数生成を使う。
- 剰余による偏りが出ないよう、範囲外の乱数を捨てて引き直す（棄却サンプリング）。
- 設定は長さ（既定20、上限65,532）、文字種、紛らわしい文字の除外。文字種は英小文字・英大文字・数字・記号 `!@#$%^&*()-_=+[]{}:,.?`。紛らわしい文字として `0 O 1 l I` を除く（docs/判断待ち_codex.md #1・#2。2026-10-17 決定）。
- 有効にした文字種は、それぞれ1文字以上必ず含める。満たすまで文字列全体を作り直し、条件を満たす文字列の中から一様に選ぶ。使える文字が2文字未満、または長さが有効な文字種の数より短ければ、作らずに拒否する。
- パスフレーズ方式を付ける場合は、単語リスト（EFFの単語リストなど）をデータファイルとして同梱する。
- 画面は、文字数のスライダー（8〜64文字、既定20）と、文字種・紛らわしい文字の除外のトグルにする。作った値は、利用者が「使う」を押したときだけパスワードの欄に入れる（2026-10-27 追記）。
- 強度の段階は、60ビット未満を「弱い」（赤）、80ビット未満を「普通」（黄）、それ以上を「強い」（緑）として、ビット数と一緒に出す（2026-10-27 追記）。
- 強度（エントロピーのビット数）を表示する。表示する値は `長さ × log2(使える文字の数)` で、文字種を必ず含める分を差し引いた厳密な値ではない（docs/判断待ち_codex.md #1）。

### CSVインポート

- 対応形式はProton Pass、1Password、ChromeのCSV。見る列は、ChromeとProton Passが `name, url, username, password, note`、1Passwordが `Title, Website, Username, Password, Notes`。見出しは大文字・小文字を区別せず、順番も問わない。使わない列の見出しの重複は無視し、使う列が重複・不足したらエラーにする（docs/判断待ち_codex.md #5。2026-10-17 決定）。実際のファイルとの照合はフェーズ3で行う。
- 解析は自前で実装する（引用符、フィールド内のカンマや改行に対応）。
- CSV全体の上限はUTF-8で5 MiB、物理行（見出しを含む）で10,000行。超えたら解析せず、行1のエラーとして返す。長いCSVや壊れたCSVで、メモリと処理時間が増えすぎないようにするための暫定の値（docs/判断待ち_codex.md #10。2026-10-17 決定）。
- 取り込む前にプレビューと重複の確認を挟む。重複の候補は、タイトル（小文字にする）・ユーザー名（小文字にする）・URLの集合が同じもの。既存のアイテムとも比べ、既存のどのパスワードとも違う行には印を付けて、画面で警告できるようにする。重複を自動で捨てる処理は作らない（docs/判断待ち_codex.md #6。2026-10-17 決定）。
- 壊れた行（不正な引用符、列の数の違い、不正なURL、サイズの超過）は行番号付きで報告し、続きを読み続ける。閉じ忘れの引用符が最後の行まで続いたら、最初の改行から後を読み直して回復を試みる。回復した行も要確認として示す（docs/判断待ち_codex.md #7。2026-10-17 決定）。
- TOTPやタグなど、対応しない列は取り込まない。対応しない列に値がある行は、プレビューで警告する（docs/判断待ち_codex.md #8。2026-10-17 決定）。
- プレビューと確認の画面では、CSV由来の値を文字として表示し、HTMLとして解釈しない。
- 送信はJSONの一括処理で1リクエストにまとめる。
- 一括作成（POST /v1/items/import）は、1回の送信を1.5MB・500件までにする。超えたら画面が分けて送る。1回の送信は1つのバッチで、全部入るか全部入らないかのどちらか。分けて送った途中で失敗したら、どこまで入ったかを画面に出す（2026-10-27 決定、フェーズ3の判断待ち5）。
- 取り込み後、元のCSVファイルを削除するよう画面で促す。

### エクスポートを作らない理由

- 平文がシステムの外に出る経路がなくなり、設計がシンプルになる。
- データを失う心配は、ミニPCへの暗号化バックアップで対応する。
- メンバーは全件を復号できるので、防御ではなく事故防止の意味。脅威モデルは変えない。

### 画面の分担

| 画面 | できること | 鍵を使うか |
| --- | --- | --- |
| 拡張機能のポップアップ | 検索、自動入力、コピー、ロック解除 | 使う |
| 拡張機能の全画面ページ（タブで開く） | 一覧・検索・編集、パスワード生成、CSVインポート、メンバー承認、ローテーション、ログイン、ロック解除（2026-10-27 追記） | 使う |

ログインとロック解除の全画面ページへの追加（2026-10-27 追記）：ポップアップは Discord の窓が開くと閉じるので、ログインの結果を見せられなかった。ポップアップの「Discord でログイン」は全画面ページを開き、ログインはそこで行う。ロック解除は両方でできる。どちらも拡張機能自身のページで、マスターパスワードを Service Worker に1回だけ送り、送ったら欄を空にする点は同じ。
| Webページ（pw.example.com） | メンバー一覧と状態、監査ログ、自分のセッション一覧と無効化 | 使わない |

Webページでパスワード一覧を見るには、Webページ上での復号が必要になり、配信されるJavaScriptを信頼するしかなくなる。そのため一覧は拡張機能の全画面ページで見る。

## 開発・テスト・診断

TypeScriptで公開リポジトリとして開発し、テストは全自動を目標にする。完成後に自己診断を行い、診断報告書の形式でレポートを書く。

### 開発体制

- 言語はTypeScript。サーバーと拡張機能、暗号処理の共通パッケージを同じリポジトリで管理する。
- インフラはCloudflareで固定。開発用と本番用でD1とWorkersを分ける。
- デプロイは最初は手元から手動。GitHub Actionsを使う場合は、CloudflareのAPIトークンをこのWorkersとD1だけを操作できる最小権限にする。
- 拡張機能を手で確かめるときのAPIは、開発用のWorkerを workers.dev にデプロイしたものを使う（暗号コアの固定は https の接続先しか受け付けないため。開発用の抜け道は作らない）。URLはGitの管理外の設定ファイルにだけ書く（2026-10-17 決定、フェーズ2の判断待ち5）。
- GitHub Actions で、push と pull request のたびに npm test と npm run typecheck を走らせる。外部のアクションは actions/checkout と actions/setup-node だけで、タグではなくコミットのSHAで固定する。権限は contents の読み取りだけで、シークレットは使わない（2026-10-17 決定、フェーズ2の判断待ち7）。

#### 依存の最小化

- 実行時の依存は、サーバーがHonoのみ、クライアントはゼロ（WebCrypto、fetch、拡張機能APIのみ）。
- 開発時の依存（TypeScript、wrangler、バンドラー、テストランナー、ブラウザの自動操作ツール）もサプライチェーン攻撃の経路になるため、ロックファイルで固定し、更新は差分を見てから取り込む。
- ブラウザの自動操作ツールは `@playwright/test`（版を固定。公開から2週間以上たった版）。ブラウザは `npx playwright install chromium` で取る Chromium（通常の Chrome は `--load-extension` が効かないため）。拡張機能を読み込んで動かすテストは `npm run test:browser` で、いつもの `npm test` とは分ける（2026-10-18 決定、フェーズ2b の判断待ち3）。
- WXTなどの拡張機能フレームワークは使わない。
- 提出版の依存は、実行時がHono（バージョンを固定）、開発時がtypescript（型チェック用）の1つだけ。どちらもロックファイルで固定する。wranglerとminiflareは提出版では入れない。
- TypeScriptは、Nodeの型除去（`--experimental-strip-types`）で直接実行する。型除去で動かない書き方（enum、namespace、コンストラクターの引数プロパティなど）は使わない。

#### 公開リポジトリの注意

- シークレットはWorkersのシークレットと、Git管理外のローカル設定ファイルに置く。
- GitHubのシークレットスキャン（プッシュ時のブロック）を有効にする。
- 拡張機能のIDを固定するための秘密鍵ファイルはコミットしない。

#### 提出版のテストの方法

- 暗号（C、P）は、Nodeの組み込みテストランナー（node:test）と、NodeのWebCryptoで動かす。
- API（S、Z）は、Honoの `app.request` で呼び出す。D1の代わりに、node:sqlite をD1と同じ形（prepare、bind、first、all、run、batch）で包んだものを使う。実際のD1では確かめていないことを、READMEに「APIのテストはSQLiteで行い、実際のD1では未確認」と書く。
- Discordを入れないので、Z-01の認証はテスト用の認証で代える（固定トークンとメンバーの対応表）。この認証は、テストからアプリを組み立てるときにだけ差し込める形にする。本番の入口に固定トークンは置かない。
- テストのための差し込み口（固定ノンス、使い捨て秘密鍵、テスト用の認証）は、すべてテスト専用の関数に閉じ込め、本番の経路からは呼べないようにする。
- 外部のテストベクタ（CFRGのHPKE、Wycheproof）は、必要な組だけを tests/vectors に置き、出典のURLとライセンスを同じ場所に書く。ライセンスが確認できないものは原則として置かない。例外として、CFRGのHPKEのベクタは、C-15に必要な1件（Base、KEM 0x0010・KDF 0x0001・AEAD 0x0002）だけを置く。ライセンス表記は確認できなかったので、IETF文書由来のコード部品の扱いに準じると解釈して引用し、権利者から求めがあれば削除する（2026-10-16 決定）。管理者署名の検証（C-22）には、WycheproofのECDSA P-256（SHA-256、IEEE P1363形式の署名）のベクタ（Apache-2.0）を置く（2026-10-17 決定）。

### 自己診断の計画

脅威モデルの項目に対応させて観点を決め、設計した防御が本当に効いているかを検証する。ツールはBurp Suiteを中心に使う。

- 認証：stateとPKCEの検証漏れ、リダイレクトURLの書き換え、トークンの失効
- 認可：IDOR、一般メンバーからの管理操作、削除済みメンバーやロールを外された人の継続利用
- 暗号：暗号文の差し替えや改ざんの検知、ノンスの再利用
- 入力：サイズ超過、不正なJSON、CSVの解析
- 拡張機能：iframeやHTTPページでの入力、ページからの偽メッセージ
- Webページ：CSP、XSS
- インフラ：CORSの設定ミス、セキュリティヘッダー、使用ドメインのサブドメイン乗っ取りの余地
- リポジトリ：過去のコミット履歴にシークレットが残っていないか

レポートは、発見事項ごとに深刻度、再現手順、影響、修正方法、修正後の再確認を書く。テストIDを根拠として参照する。

| 未承認メンバーのAPIアクセスが拒否される（Discord認証を入れない場合はテスト用の認証で代替） | Z-01 |

### マイルストーン

日付ではなく完了条件で管理する。

1. Discordログイン、Botによるロール確認、セッション発行が動く
2. 暗号コアがテストベクタのテストに通る
3. 拡張機能でアイテムの一覧・作成・編集・削除ができ、同期と409が動く
4. 自動入力、クリップボードコピー、パスワード生成、カスタム項目ができる
5. 承認、削除、ローテーションとWebページができる
6. CSVインポートができる
7. 自己診断を行い、レポートとREADMEを書く

その後にFirefox、Safariの順で対応する。
